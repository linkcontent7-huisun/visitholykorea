## 9/11 — GPS 현재 위치 기반 정렬 추가 (분석 보고서 1순위 항목)

9/10 분석 보고서(`docs/프로젝트-핵심기능-구조-테스트-분석-2026-09-10.md`)가 지적한
"실제 GPS 를 안 읽고 선택한 지역의 중심좌표만 쓴다"를 고쳤다. **기존 출발지(시·도)
선택 기능은 그대로 두고, 그 위에 "현재 위치 사용"을 추가**하는 방식으로 갔다 —
지역 선택이 이미 여러 화면(홈·탐색·여권 미리보기)의 거리 정렬 기준이라, 갈아엎기보다
얹는 쪽이 안전하다.

| 한 일 | 파일 |
| --- | --- |
| GPS 상태(`gpsLocation`·`gpsStatus`)와 요청/해제 함수를 설정 컨텍스트에 추가 | `settings-context.ts`, `SettingsProvider.tsx` |
| `navigator.geolocation.getCurrentPosition` 래핑 — 미지원·거부·오류 상태 구분 | `SettingsProvider.tsx` |
| 메뉴 화면에 "현재 위치 사용" 항목 추가(출발지 select 바로 위, 켜지면 select 비활성화) | `MenuPage.tsx` |
| 홈·탐색·여권 미리보기의 거리 정렬 — `regionCoords(origin)` 단독 사용을 `gpsLocation ?? regionCoords(origin)` 로 교체(GPS 우선) | `HomePage.tsx`, `ExplorePage.tsx`, `EmptyPassportPreview.tsx` |
| 번역 키 7개(6개 국어) — 버튼·상태 문구 | `dictionary.ts` |

**의도적으로 안 한 것** — GPS 좌표를 저장(localStorage)하지 않는다. 위치는 이동하는
값이라 세션마다 새로 물어보는 게 정확하고, 오래된 좌표를 들고 있다가 엉뚱한 곳을
"내 주변"이라고 보여주는 사고를 막는다. 꺼졌다 켜지면(새로고침) 다시 물어본다.

**확인한 것** — `npm run verify` 통과(타입·린트 0 신규 에러, 테스트 353/353).
로컬 dev 서버 브라우저 프리뷰로 실측:
- 메뉴 화면에서 "현재 위치 사용" 클릭 → 프리뷰 샌드박스가 위치 권한을 자동 거부하는
  환경이라 "위치 권한이 거부되었습니다" 안내가 정확히 뜨는 것을 확인(에러 처리 검증됨).
  **실제 기기에서 권한을 허용했을 때의 성공 경로(좌표 획득 → 정렬 반영)는 이번
  세션에서 못 봤다** — 다음 세션이 실기기나 실제 브라우저 권한 허용 환경에서 확인할 것.
- 출발지를 "서울"로 선택 → 기존 지역 기반 정렬 회귀 없음 확인(서울 소재 성지가
  먼저 노출: 우포도청 터·김범우의 집터 등).
- 콘솔에 `ERR_NAME_NOT_RESOLVED`/`ERR_NETWORK_IO_SUSPENDED` 에러가 있었으나
  Supabase/외부 리소스 접근이 막힌 프리뷰 샌드박스 환경 탓으로 보인다(우리 코드가
  아니라 HMR 웹소켓·외부 이미지 호출) — React 렌더링 에러는 없었다.

**다음에 하면 좋은 것** — 현재는 메뉴 화면에만 GPS 버튼이 있다. 분석 보고서가
지적한 "추천 카드에서 목적지 길찾기"까지 이어가려면, 흠 화면이나 나침반 결과에도
GPS 버튼을 노출하는 게 자연스럽다. 또한 `distance-label.ts`(`distanceLabel` 함수)는
아직 한국어 하드코딩이라 "현재 위치 안에 있어요" 문구가 다른 언어 모드에서도
한국어로 나온다 — 이어지는 영어 전면화 작업에서 같이 처리 대상.

## 🔴 9/9 — AI 가이드(미카엘) Edge Function 이 배포돼 있지 않다

전체 버튼 QA 중 발견. **배포 서버에 직접 요청을 보내 확인함** — 추측 아님:

```
curl -X POST https://kaahuoqzkgshihypzzyh.supabase.co/functions/v1/ai-guide ...
→ {"code":"NOT_FOUND","message":"Requested function was not found"}
```

`supabase/functions/ai-guide/` 코드는 저장소에 있지만 Supabase 프로젝트에
**한 번도 배포된 적이 없다**(또는 배포 후 지워짐). 그래서 홈의 "AI 가이드"
버튼과 검색창의 "미카엘에게 물어보기" — 실제 사용자가 지금 누르면 전부
"죄송합니다, 이용할 수 없습니다"만 뜬다. 실패 시 안내문구(2026-09-07 추가)는
정상 작동해서 완전히 막막하진 않지만, **핵심 기능 하나가 통째로 죽어 있다.**

**막힌 것** — 배포하려면 `supabase login`(Supabase 접속 토큰)이 필요한데
이 세션엔 그 권한이 없다(`npx supabase projects list` → 인증 필요 에러).
`supabase/config.toml` 자체가 없어서 `supabase init` 부터 해야 한다.

### 9/10 추가 확인 — Supabase 대시보드에서 직접 봄(웹 브라우저로 로그인 상태 확인)

- **Edge Functions 페이지**: "Deploy your first Edge Function" — 배포된 함수 **0개** (위 curl 결과와 일치, 재확인됨)
- **Secrets 페이지**: "No custom secrets created" — **`GEMINI_API_KEY` 도 설정된 적이 없다**
  (`.env.local` 에도 이 키는 없음 — 로컬에 값 자체가 없다)
- `npx supabase --version` → `2.117.0` — **CLI 자체는 이 세션에서도 실행된다.**
  이전 기록의 "권한이 없다"는 로그인이 안 된 상태였을 뿐, npx 실행 자체는 됨.
- `npx supabase login --help` 확인 — `--token` 플래그로 **비대화형 로그인 가능**.
  즉 Personal Access Token 문자열만 있으면 브라우저 없이 로그인된다.

**정말 막힌 것은 두 개의 값이다. 둘 다 사장님 개인 계정 인증이 필요해서
에이전트가 대신 발급받을 수 없다** (API 키를 AI 세션에 노출하는 것도 이 프로젝트
규칙상 피해야 함 — 클라이언트/대화에 비밀 키를 두지 않는다):

| 필요한 값 | 어디서 발급 | 무엇에 쓰나 |
| --- | --- | --- |
| Supabase Personal Access Token | https://supabase.com/dashboard/account/tokens → "Generate new token" | `supabase login --token <값>` |
| Gemini API Key | https://aistudio.google.com/apikey → "Create API key" | Supabase Secrets 에 `GEMINI_API_KEY` 로 등록 |

**다음 세션(또는 사장님)이 할 일** — 아래 순서면 CLI 한 번으로 끝난다:
1. 위 두 값을 발급받는다 (사장님이 직접 — 로그인 필요한 페이지라 에이전트가 못 함)
2. **Gemini 키는 Supabase 대시보드에서 직접 등록하는 편이 더 안전하다** —
   Edge Functions → Secrets → Name: `GEMINI_API_KEY`, Value: 발급받은 키 → Save
   (터미널에 키를 남기지 않아도 됨)
3. `npx supabase login --token <Supabase 토큰>` (이 토큰은 로그인 1회용이라 터미널 기록에 남아도 재사용 위험이 상대적으로 낮지만, 끝나면 `history -c` 권장)
4. `npx supabase link --project-ref kaahuoqzkgshihypzzyh`
5. `npx supabase functions deploy ai-guide`
6. 배포 후 curl 로 재확인 — `NOT_FOUND` 대신 정상 응답이 와야 끝난 것이다:
   ```
   curl -X POST https://kaahuoqzkgshihypzzyh.supabase.co/functions/v1/ai-guide \
     -H "Content-Type: application/json" -H "apikey: <VITE_SUPABASE_ANON_KEY>" \
     -d '{"question":"명동성당 역사 알려줘"}'
   ```

## 9/7(2) — 멀티 에이전트 오케스트레이션: 되는 것과 안 되는 것 (실측)

**결론부터: 배관은 작동한다. 막힌 것은 Windows 의 격리 기능이다.**
다음에 이 벽에 다시 부딪히지 않도록 실측만 적는다.

### 되는 것 — Orca orchestration

Claude 와 Codex 는 **Orca 를 통해 실제로 대화할 수 있다.** 오래 "통로가 없다"고
알고 있었는데 틀렸다. `~/.agents/skills/orchestration` 스킬이 설치돼 있었고,
Claude Code 만 설치 목록에서 빠져 있었을 뿐이다. `~/.claude/skills/` 로 복사하면
즉시 인식된다.

```
orca orchestration run-create   → Run 생성, 지시자 결속
orca orchestration task-create  → 작업 정의
orca orchestration worker-start → Codex 기동 + 작업 주입
orca orchestration check        → worker_done 수신
orca terminal create/read/close → 터미널 직접 제어
```

**T-009(솔뫼·배론·약현 스페인어)를 이 방식으로 끝냈다.** 사람이 지시서를
붙여넣는 단계가 없었다. 커밋 `fce1671`.

### 🔴 안 되는 것 — Windows 에서는 「울타리 + 안 묻기」가 성립하지 않는다

Codex 샌드박스는 리눅스·맥의 OS 기능에 기댄다. Windows 에는 그 기능이 없다.
그래서 조합이 둘뿐이다.

| 실행 옵션 | 결과 |
| --- | --- |
| `--sandbox workspace-write --ask-for-approval on-request` | 울타리는 있으나 **명령마다 사람이 승인 클릭**. Orca 가 에이전트의 대리 클릭을 막는다(`agent_prompt_blocked`) |
| `--sandbox workspace-write --ask-for-approval never` | **모든 명령이 차단된다.** Codex 가 "환경이 모든 터미널 명령 실행을 정책상 차단"이라며 아무 일도 못 한다 |
| `--dangerously-bypass-approvals-and-sandbox` (Orca 기본) | 클릭 없이 돌지만 **울타리가 없다** — 노트북 전체와 인터넷이 열린다 |

**Orca 가 Windows 에서 YOLO 를 기본값으로 쓰는 이유가 이것이다.**
T-005·T-008·T-009 는 전부 YOLO 로 돌았다.

> ⚠️ **설정 파일만 보고 "안전하다"고 판단하지 말 것.** `~/.codex/config.toml` 에
> `sandbox_mode`·`approval_policy` 를 넣어도 명령줄 옵션이 덮어쓴다. 실제 실행
> 상태는 프로세스로 확인한다:
> `Get-CimInstance Win32_Process -Filter "Name='codex.exe'" | % { $_.CommandLine }`

또 하나: Orca 는 Codex 를 **자기 전용 CODEX_HOME** 으로 돌린다
(`AppData\Roaming\orca\codex-accounts\<id>\home`). 다만 `~/.codex/config.toml`
의 내용을 복사해 가므로 그쪽을 고치면 반영은 된다(2026-09-07 확인).

### 다음에 시도할 것 — 우선순위 순

1. **별도 worktree 에서 돌리기** (`worker-start --worktree new-child`).
   git 이 추적하는 파일만 있는 새 체크아웃을 준다 → **`.env.local` 이 그 폴더에
   아예 없다.** 규칙으로 부탁하는 대신 물리적으로 없앤다. Windows 에서도 된다.
2. **WSL 안에서 Codex 실행.** 리눅스 샌드박스가 살아나 「울타리 + 안 묻기」가
   동시에 된다. Orca 도 managed WSL 세션을 지원한다(스킬 문서에 `ORCA_CLI_COMMAND` 언급).
3. **`.env.local` 의 키 교체.** 걱정의 실체는 그 파일 하나다. 배포까지 손대야
   하므로 9/14 이후.

### 비용에 대한 판단

**도슨트 번역은 애초에 다중 에이전트가 필요한 일이 아니었다.** JSON 몇 개에

## 9/6 — 관리자 콘솔 (사진 교체 · 글 수정 · 사진 승인)

**왜 만들었나** — 성지 정보를 고치는 길이 노트북 CLI 스크립트뿐이었다.
그런데 비어 있는 대표 사진 155곳은 결국 현장에서 찍어야 하고, 찍은 사진을
노트북 앞으로 돌아와 올리는 일은 실제로는 잘 일어나지 않는다.
**휴대폰에서 그 자리에서 바꾸는 것**이 이 화면의 존재 이유다.

**들어간 것**

| 무엇 | 어디 |
| --- | --- |
| 권한 등급 `member / editor / admin` + RLS | `supabase/migrations/20260906000000_create_admin_console.sql` |
| 관리자 로그인 · 문지기 | `src/features/admin/components/AdminGate.tsx` |
| 「채울 곳」 대기열 + 사진 승인함 | `src/pages/AdminPage.tsx` (`/admin`) |

| 첫 관리자 임명 | `npm run admin:grant -- <이메일>` |

**권한을 좁게 준 지점 (의도한 것이므로 나중에 "빠졌다"고 채우지 말 것)**

- **성지 추가·삭제 정책을 만들지 않았다.** update 만 열려 있어, 화면에서
  무엇을 눌러도 208곳이 사라지지 않는다.
- **관리자에게 회원 정보를 보여주지 않는다.** 승인함은 `admin_pending_photos`
  뷰만 보고, 그 뷰에 `user_id` 와 이메일이 없다.
- **모든 수정은 `site_revisions` 에 이전 값이 남는다** (DB 트리거라 화면이
  빠뜨릴 수 없다). 편집 화면에서 한 번에 되돌릴 수 있다.
- **service_role 키는 앱에 넣지 않았다.** `VITE_` 값은 브라우저 번들에
  그대로 들어가므로, 권한 판단은 전부 DB 의 RLS·security definer 함수가 한다.
- 화면 문구는 **한국어만**이다. 운영자만 보는 화면이라 6개 국어 사전을
  두 배로 만들 이유가 없다. 운영자가 늘면 그때 옮긴다.

#### AI 로 성지 사진을 만들지 않는다 (2026-08-27 결정)

2차적저작물이라 저작권이 안 풀리고, 무엇보다 **AI 가 그린 배티 순교성지는
배티 순교성지가 아니다.** 실제 순교지 자리에 지어낸 그림을 올리는 것은
CLAUDE.md 의 "더미 데이터를 화면에 남기지 않는다"에 정면으로 걸린다.
**사진이 없는 편이 가짜 사진보다 낫다.**
인스타 사진은 게시자에게 DM 으로 허락을 받는 것이 유일하게 안전한 길이다.

> `data/research/image_sourcing_summary.md` 는 **195곳 기준의 옛 집계**라
> 숫자를 쓰면 안 된다. 위 표가 최신이다.

```sql
select count(*) filter (where image_url is not null) as 사진있음,
       count(*) as 전체
from holy_sites;
```

촬영 로드맵은 `docs/30-content-ops/인스타그램-서울-콘텐츠-플랜.md` 에 5회차 동선으로 있다.

조사에서 발견 — 혼자 성지 사진 프로젝트를 하는 개인 계정이 있다(24번째 성지 진행 중).
핸들은 확인 못 했다. 인스타에서 `천주교 성지 사진 프로젝트` 로 찾아 협업을 검토할 만하다.
**무단 사용 금지. 정식 연락이 먼저다.**

## 작업 환경 — 어디서 무엇을 하는가

세션이 두 종류라 헷갈리기 쉽다. **할 수 있는 일이 다르다.**

|                        | 노트북 파일 | 외부 인터넷   | 쓰는 곳                             |
| ---------------------- | ----------- | ------------- | ----------------------------------- |
| 로컬 CLI · 데스크톱 앱 | 볼 수 있음  | 전부 됨       | DB 작업, OneDrive 정리, 배포 확인   |
| 웹 (claude.ai/code)    | **못 봄**   | 허용 도메인만 | 저장소 안에서 끝나는 코드·문서 작업 |

웹 세션은 GitHub 저장소만 복제해온 클라우드 컨테이너에서 돈다.
OneDrive 든 `.env.local` 이든 노트북 안의 것은 구조적으로 접근이 안 된다.
인터넷은 허용 목록에 있는 도메인만 나간다 — 2026-08-19 실측으로
supabase.com·vercel.app·TourAPI(data.go.kr) 는 차단, 문서 사이트류는 일부 열림.
환경 설정(claude.ai/code 의 환경 선택기)에서 허용 도메인을 늘릴 수는 있지만,
비밀값 저장소가 없어 DB 비밀번호를 웹 환경에 넣는 것은 권장되지 않는다.
