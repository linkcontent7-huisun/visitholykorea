# 11장. 6단계 검증·배포 — "됐다"고 말해도 되는 조건

> **3장 사건 3**: 한 달 동안 키가 노출돼 있었다. 아무도 번들을 안 열어봤다.
> **3장 사건 4**: 한 달 동안 기능이 작동 안 했다. 화면에 숫자가 떠서 된 줄 알았다.
> **3장 사건 8**: 마감 사흘 전 배포가 막혔다. 한도를 안 읽었다.
>
> 세 사건의 공통점: **확인할 수 있었는데 안 했다.**
> 이 장은 확인을 건너뛸 수 없게 만드는 방법이다.

---

## 11-1. 검증의 3층

**아래 층이 통과해야 위 층을 본다.** 건너뛰지 않는다.

| 층 | 무엇 | 명령 | 잡는 것 |
| --- | --- | --- | --- |
| 1층 | **기계 검사** | `npm run verify` | 타입·규칙·동작 |
| 2층 | **실물 확인** | 브라우저로 직접 | 화면이 실제로 되나 |
| 3층 | **배포본 확인** | 배포 주소에서 | 배포된 것이 맞나 |

> **가장 흔한 실수**: 1층만 통과시키고 "됐다"고 하는 것.
> `verify` 는 **타입이 맞는지**를 보지 **기능이 되는지**를 보지 않는다.

## 11-2. 1층 — 기계 검사

```bash
npm run verify     # typecheck && lint && test
```

성지웹 실측: **450개 테스트 / 62파일, 52초** `[npx vitest run, 2026-09-23]`.

### 🔴 종료 코드가 가려지는 함정

> **성지웹에서 실제로 겪은 사고**: `명령 | tail` 로 결과를 줄여 보면
> **exit code 는 `tail` 것만 보인다.** 앞 명령이 실패해도 "성공"으로 읽힌다.

```bash
# ❌ 실패를 못 본다
npm run verify | tail -20

# ✅ 파일로 받고 종료 코드를 따로 확인한다
npm run verify > verify.log 2>&1; echo "exit=$?"
tail -30 verify.log
```

### 검사를 늘린다 — 규칙을 기계에 맡긴다

| 검사 | 무엇을 막나 | 성지웹 |
| --- | --- | --- |
| `typecheck` | 타입 불일치 | ✅ |
| `lint` | 규칙 위반 | ✅ |
| `test` | 동작 깨짐 | ✅ 450개 |
| `translate:check` | 미번역 문구 | ✅ 검사 4개 `[2d9d68e]` |
| `db:check-security` | DB 권한 구멍 | ✅ |
| `docent:check` | 콘텐츠 형식 오류 | ✅ |

> **사람이 지키는 규칙은 깨진다. 기계가 지키는 규칙만 남는다.**
> 같은 실수를 두 번 하면, 고치지 말고 **검사를 하나 만든다.**

## 11-3. 2층 — 실물 확인

**브라우저를 실제로 열어 핵심 동작을 끝까지 해본다.**

> **왜 이게 필요한가**: 3장 사건 4에서 화면에는 "실측 집중률 57%" 가 떠 있었다.
> 테스트도 통과했다. **그런데 데이터는 한 번도 안 왔다.**
> 테스트는 "코드가 의도대로 도나"를 보지 "값이 맞나"를 보지 않는다.

### 확인 목록

- [ ] **핵심 동작을 처음부터 끝까지** 해본다 (6장 ③에서 고른 그것)
- [ ] **다른 언어**로 열어본다 — 한국어가 남아 있나
- [ ] **큰 글자 모드**에서 안 깨지나
- [ ] **휴대폰 폭**에서 안 깨지나
- [ ] **로그아웃 상태**에서 열어본다
- [ ] **데이터가 없는 항목**을 일부러 열어본다 (시골 성지처럼)

> 성지웹은 이 확인을 반복하려고 스킬을 따로 만들었다 `[.claude/skills/chrome-analyze]`.

### 값이 맞는지 확인하는 법

화면의 숫자를 믿지 않는다. **그 숫자가 어디서 왔는지 역으로 따라간다.**

```bash
# 예: 화면에 뜬 값이 실제 API 응답과 같은지
curl "<API 주소>" | head -40
```

> 성지웹은 이 방식으로 *"집중률은 실시간이 아니라 **일 단위 예측**"* 을 확인했다.
> 응답 행에 `baseYmd`(날짜)만 있고 시간대가 없었다 `[9/21 서울 중구 30일 × 55곳 실측]`.
> **문서에 "실시간"이라고 쓴 것을 그제야 고쳤다.**

## 11-4. 3층 — 배포본 확인

### 배포된 것이 **최신 코드인지** 확인한다

```bash
# 배포 커밋 확인 (Vercel 대시보드 또는)
curl -s https://<도메인>/ | grep -o 'index-[a-zA-Z0-9]*\.js'
```

> **함정**: 번들 문자열로 화면 기능을 확인하면 안 된다.
> *"pages 는 lazy chunk 라 `index-*.js` 에 없음"* `[이어서-할-일.md]`.
> **화면을 렌더해서 확인한다.**

### 비밀이 새지 않았는지 확인한다 — **매 배포마다**

```bash
curl -s https://<도메인>/assets/index-*.js > bundle.js
grep -o "SERVICE_KEY\|SECRET\|API_KEY" bundle.js | sort -u
```

> **3장 사건 3이 한 달 걸린 이유가 이 3줄을 안 돌려서다.**

### 서버 함수가 배포됐는지 확인한다

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://<프로젝트>.supabase.co/functions/v1/<함수이름>
# 401 = 배포됨(인증 필요)   404 = 배포 안 됨
```

> 성지웹은 이 확인으로 `naver-auth` 가 **배포조차 안 된 것**을 발견했다 `[9/14 점검]`.

## 11-5. 배포 한도를 관리한다

> **3장 사건 8**: 제출 사흘 전 Vercel 배포 한도(100회/24시간)에 걸려
> **한 줄짜리 수정도 못 했다.** 실측 114건 `[이어서-할-일.md 9/21 11:30]`.

### 문서 커밋이 배포를 부르지 않게 한다

```json
// vercel.json
{
  "ignoreCommand": "git diff --quiet HEAD^ HEAD -- . ':(exclude)docs' ':(exclude)data'"
}
```

> **성지웹은 아직 적용 안 했다** `[2026-09-23 미적용]`. 다음 프로젝트에서는 첫날 넣는다.

### 그 밖의 습관

| 습관 | 왜 |
| --- | --- |
| 문서 커밋은 **몰아서** 한 번에 | 배포 건수 절약 |
| 마감 전날은 **코드 커밋을 줄인다** | 한도를 남겨둔다 |
| 배포 실패하면 **30분 뒤 재시도** | 한도는 시간이 지나면 풀린다 |

## 11-6. 커밋과 푸시

### 커밋 메시지 — 무엇을 왜

성지웹의 좋은 커밋 메시지 예 `[615642e]`:

```
feat(crowding): 인근 혼잡도 재설계 — 집중률+오늘 축제 3단계 라벨, 시군구 코드로 집중률 첫 작동

- features/quiet → features/crowding. 산식은 집중률 0.7 + 오늘 축제 0.3
- 집중률 호출에 signguCd 가 없어 한 번도 데이터를 받은 적이 없었다 → ldongCode2 로 시군구 코드를 받아 넣는다
- 화면: 색 점 + 문장 하나. 값 없으면 안 그린다

verify 통과(47 파일 · 380 테스트). 헤드리스 Chrome 으로 조용·보통·붐빔·없음 실측.
```

배울 것:
- 제목에 **무엇이 바뀌었나**
- 본문에 **왜** 와 **무엇을 발견했나**
- 마지막에 **어떻게 검증했나** — 숫자로

### 🔴 여러 창을 쓸 때는 경로를 지정해 커밋한다

> **성지웹 규칙**: 세션들이 git index 를 공유하므로 **`git commit -- <경로>` 로만** 커밋한다.
> **`git add .` 과 `git commit -a` 금지.** 다른 창의 미완성 작업이 같이 올라간다.

```bash
# ✅
git commit -m "..." -- docs/80-백서/

# ❌
git add . && git commit -m "..."
```

### 커밋 전에 다른 창의 작업을 확인한다

```bash
git status --short     # 내가 안 건드린 파일이 있나
git pull               # 창을 열자마자 항상
```

## 11-7. "됐다"고 말해도 되는 조건

**이 다섯 개가 전부 참일 때만** 완료라고 말한다.

1. `npm run verify` 가 **실제로 통과했다** (종료 코드를 직접 확인)
2. **브라우저에서 핵심 동작을 끝까지** 해봤다
3. **배포 주소에서** 같은 것을 확인했다
4. 배포 번들에 **비밀 문자열이 없다**
5. `docs/이어서-할-일.md` 를 **그 자리에서** 고쳤다

> **근거 없는 "통과"는 통과가 아니다.**
> "기록에 그렇게 적혀 있어서"는 근거가 아니다 — 직접 돌린 출력이 근거다.

## 11-8. AI 에게 검증을 시킬 때

| 시켜야 할 것 | 시키면 안 되는 것 |
| --- | --- |
| "verify 를 돌리고 **출력을 그대로 보여줘**" | "verify 통과했어?" (믿게 됨) |
| "배포 화면을 **열어서 캡처**해줘" | "배포 됐어?" |
| "이 숫자가 **어디서 나왔는지** 명령으로 보여줘" | "이 숫자 맞아?" |

> **성지웹에서 실제로 쓴 방법**: 완성된 문서를 다른 세션·다른 AI 에게 던져
> **"이 문장 중 저장소에서 확인 안 되는 것을 찾아라"** 고 시켰다.
> 9/21 설명서 3자 대조에서 **실물 위험 4건**이 그렇게 나왔다 `[435160b]`.

## 11-9. 6단계 완료 체크리스트

- [ ] `verify` 를 **종료 코드까지 확인**해 통과시켰다
- [ ] 같은 실수가 두 번 났을 때 **검사를 하나 만들었다**
- [ ] 브라우저에서 **핵심 동작을 끝까지** 해봤다
- [ ] **다른 언어·큰 글자·좁은 폭·로그아웃 상태**를 확인했다
- [ ] 화면의 숫자를 **원본까지 역추적**해 확인했다
- [ ] 배포본에서 같은 것을 확인했다
- [ ] 배포 번들에 **비밀 문자열이 없다**
- [ ] 서버 함수가 **배포됐는지(401 vs 404)** 확인했다
- [ ] 문서 커밋이 배포를 안 부르게 설정했다
- [ ] `git commit -- <경로>` 로만 커밋했다
- [ ] `이어서-할-일.md` 를 그 자리에서 고치고 푸시했다
