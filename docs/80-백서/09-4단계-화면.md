> **3장 사건 6**: 다국어 사전 한 파일을 **104번** 고쳤다. 9월에만 98번.
> 원인은 "일단 한국어로 만들고 나중에 번역" 이었다. **그 나중이 98번이었다.**
>

## 9-1. 화면 만드는 순서

**핵심 동작 한 개(6장 ③)를 끝까지 되게 만든 다음** 나머지로 간다.

| 순서 | 무엇 | 왜 |
| --- | --- | --- |
| 1 | **핵심 화면 하나를 끝까지** | 데이터→화면→동작이 실제로 되는지 확인 |
| 2 | 그 화면의 **빈 상태·오류 상태** | 나중에 하면 안 한다 |
| 3 | 목록 화면 | 핵심 화면으로 들어가는 입구 |
| 4 | 로그인·계정 | 필요한 시점에 |
| 5 | 부가 화면 | |
| 6 | 다듬기·접근성 | |

> **성지웹이 안 한 것**: 1을 끝내기 전에 3·5를 넓게 만들었다.
> 8월에 쉼터·지도·순례길·즐겨찾기·도슨트를 줄줄이 신설했고 `[feature 첫 커밋 날짜]`,
> 9월에 그중 상당수를 지웠다 `[4장]`.

## 9-2. 문구는 **처음부터** 사전에 넣는다

이게 이 장에서 가장 값나가는 한 줄이다.

### 하면 안 되는 것

```tsx
<button>기록하기</button>          // ❌ 한국어가 코드에 박힘
```

### 처음부터 이렇게

```tsx
<button>{t('recordButton')}</button>   // ✅
```

```ts
// dictionary.ts
recordButton: { ko: '기록하기', en: 'Record' },
```

> **"나중에 번역할 거니까 일단 한국어로"의 비용**: 104회 재작업 + 미번역 검사기 4개를 따로 만들어야 했다 `[2d9d68e]`.
> **처음부터 넣으면 추가 비용이 0이다.** `t('...')` 를 쓰는 게 `기록하기` 를 쓰는 것보다 어렵지 않다.

### 다국어를 안 쓸 프로젝트라도 사전을 쓴다

라디오작가는 한국어만 쓸 수도 있다. 그래도 문구를 한 파일에 모으면:
- 말투를 바꿀 때 한 곳만 고친다
- 같은 말이 화면마다 다르게 적히는 일이 없다
- 나중에 다국어가 필요해져도 **코드를 안 고친다**

### 검사기를 같이 만든다

```
npm run translate:check   ← 사전에 없는 문구가 코드에 박혀 있으면 실패
```

> **8장 8-6의 원칙**: 사람이 지키는 규칙은 깨진다. 기계가 지키는 규칙만 남는다.

## 9-3. 만들기 전에 **이미 있는지 본다**

> **4장 유형 4**: `PhotoCardViewer` 를 오전에 만들고 오후에 지웠다.
> 이유: *"장소 상세 페이지와 동작이 달라 혼란스러웠다"* `[cd6715c]`.
> **같은 일을 하는 `PhotoLightbox` 가 이미 있었다.**

새 컴포넌트를 만들기 전에 두 가지를 묻는다:

1. **같은 동작이 다른 화면에 이미 있나?** → 있으면 그걸 쓴다
2. **비슷한데 조금 다른가?** → 새로 만들지 말고 **기존 것에 옵션을 추가**한다

성지웹의 좋은 사례:
> *"`DirectoryEntryCard` 에 `hideDistance`/`mapProviders` 옵션 추가,
> 다른 4개 화면은 그대로"* `[4de41d5]`
>
> 새 카드를 만들었으면 관리할 카드가 둘이 됐을 것이다.

## 9-4. 빈 상태·오류 상태를 **같이** 만든다

화면 하나를 만들 때 **네 가지 모습**을 같이 만든다.

| 상태 | 화면 |
| --- | --- |
| 불러오는 중 | 뼈대(skeleton) 또는 짧은 안내 |
| 데이터 있음 | 정상 |
| **데이터 없음** | "아직 없어요" + **다음에 할 일 안내** |
| **오류** | "불러오지 못했어요" + 다시 시도 |

> **성지웹 사례**: 기록이 비었을 때 빈 카드에 **단추**를 넣었다 `[1381f32]`.
> 빈 화면만 보여주면 사용자가 멈춘다.

> **7장 7-8과 연결**: 데이터 없음과 0은 다르다. 없으면 **안 그린다**, 0으로 계산하지 않는다.

## 9-5. 접근성을 나중에 하지 않는다

성지웹 사용자의 85%가 50대 이상이다 `[수요조사 n=23, 2026-09-15]`. 이게 화면 규칙을 정했다.

| 규칙 | 왜 |
| --- | --- |
| **고정 px 금지, rem 기반 크기** | 큰 글자 모드가 작동해야 함 |
| 단추는 손가락 크기 (최소 44px 상당) | |
| 색만으로 구분하지 않음 | 색 구분이 어려운 사용자 |
| 입력창 대비 확보 | |
| 모달은 포커스를 가둔다 | 키보드 사용자 |
| 자동 넘어가는 캐러셀에 **멈춤 단추** | |

`[CLAUDE.md 접근성 항목 + 커밋 f547893 「접근성 감사 상위 4건」]`

> **성지웹은 9/20에 접근성 감사를 따로 했다.** 한 커밋에 모달 포커스·대비·라벨·캐러셀 멈춤을 몰아서 고쳤다.
> **처음부터 rem 을 썼으면 그 커밋이 없었다.**

## 9-6. AI 와 화면을 만드는 대화법

### 지시를 구체적으로 — "완료 조건"까지 쓴다

| 나쁜 지시 | 좋은 지시 |
| --- | --- |
| "도슨트를 개선해줘" | "명동·절두산·전동 3곳의 도슨트 원고에 스페인어를 추가한다. 완료 조건: (1) 세 파일에 `narrationEs` 가 모든 포인트에 있다 (2) 스페인어로 앱을 열면 스페인어 원고가 나온다 (3) verify 통과. **범위 밖**: 다른 성지 원고, 화면 문구" |

`[.claude/rules/orchestrator.md 의 실제 예시]`

> 지시가 모호하면 AI 는 **일을 늘린다.** 「범위 밖」을 안 쓰면 묻지 않은 것까지 고친다.

### 화면 작업은 **한 번에 하나씩**

같은 파일을 두 세션이 동시에 만지면 충돌한다. `SiteDetailPage.tsx` 가 72번 고쳐진 이유 중 하나다.

### 다 만들었으면 **화면을 눈으로 본다**

> **성지웹의 뼈아픈 교훈**: 배포 확인을 번들 문자열로 했다가 틀렸다.
> *"배포 확인은 번들 문자열이 아니라 **화면을 렌더해서**
> (pages 는 lazy chunk 라 `index-*.js` 에 없음)"* `[이어서-할-일.md]`

브라우저를 실제로 열어 확인한다. 성지웹은 이걸 위해 스킬을 따로 만들었다 `[.claude/skills/chrome-analyze]`.

확인할 것:
- 핵심 동작이 끝까지 되나
- **다른 언어로 열었을 때** 한국어가 남아 있지 않나
- 큰 글자 모드에서 안 깨지나
- 폭이 좁은 화면(휴대폰)에서 안 깨지나

## 9-7. 한 화면이 커지면 자른다

| 신호 | 대응 |
| --- | --- |
| 파일이 200줄을 넘는다 | 조각을 `features/*/components/` 로 |
| 한 커밋에서 그 파일의 10곳 이상을 고친다 | 이미 늦었다. 자른다 |
| 같은 파일이 주 5회 이상 고쳐진다 | 설계가 잘못됐다는 신호 |

> **매주 이 명령을 돌린다** (2장 2-1):
> ```bash
> git log --since="1 week ago" --format= --name-only -- src | sort | uniq -c | sort -rn | head -10
> ```
> 튀어 오르는 파일이 **지금 잘못 설계돼 있는 파일**이다.

## 9-8. 4단계 완료 체크리스트

- [ ] **핵심 화면 하나**를 데이터부터 동작까지 끝냈다
- [ ] 모든 문구가 **처음부터 사전**에 들어갔다 (코드에 박힌 한국어 없음)
- [ ] 문구 누락을 잡는 **검사기**가 있다
- [ ] 새 컴포넌트를 만들기 전에 **기존 것을 찾아봤다**
- [ ] 화면마다 **빈 상태·오류 상태**를 같이 만들었다
- [ ] 크기를 **rem** 으로 썼다 (고정 px 없음)
- [ ] 브라우저에서 **실제로 눈으로** 확인했다 (다른 언어·큰 글자·좁은 폭 포함)
- [ ] 200줄 넘는 화면 파일이 없다
