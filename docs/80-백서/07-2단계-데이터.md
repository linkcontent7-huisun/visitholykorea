# 7장. 2단계 데이터 — 화면보다 데이터가 먼저인 이유

> **화면은 데이터 모양을 따라간다. 반대는 안 된다.**
> 데이터를 안 보고 만든 화면은 데이터가 도착하는 순간 다시 만들어야 한다.
>
> 3장 사건 4가 그 증거다 — 집중률 화면을 만들었는데, **데이터가 한 번도 도착하지 않았다.**
> 그런데도 화면에는 "실측 집중률 N%" 가 떠 있었다.
>
> 걸리는 시간: **3~5일** (데이터를 모으는 시간은 별도).

---

## 7-1. 순서 — 반드시 이 순서로

```
① 데이터를 한 건 손에 넣는다   ← 진짜 데이터. 가짜로 시작하지 않는다
② 그 한 건을 파일로 저장한다    ← 나중에 대조할 기준
③ 표(테이블)를 설계한다
④ 마이그레이션으로 표를 만든다
⑤ 데이터를 넣는다 (시드)
⑥ 읽어오는 통로(repository)를 만든다
⑦ 그 다음에 화면
```

**⑥까지 끝나야 화면을 시작한다.**

## 7-2. ① 진짜 데이터 한 건을 먼저 본다

> **4장 유형 3**: 데이터를 확인 안 하고 만든 기능은 전부 다시 만들었다.

외부 API 를 쓸 거면 **화면을 만들기 전에 한 번 호출해서 응답을 눈으로 본다.**

```bash
# 예: 응답을 파일로 저장해 보관한다
curl "https://api.example.com/...&serviceKey=..." > docs/20-architecture/샘플응답-2026-09-23.json
```

응답을 보면서 확인할 것:

| 확인 | 왜 |
| --- | --- |
| 필드 이름과 타입 | 화면이 기대하는 모양과 다를 수 있다 |
| **없을 수도 있는 필드** | 시골 성지는 TourAPI 결과가 얇다 `[이어서-할-일.md]` |
| 시간 단위 | 성지웹은 "실시간"인 줄 알았는데 **날짜 단위 예측**이었다 `[crowding-score.ts]` |
| 한 건이 아니라 **여러 건** | 첫 건만 보면 예외를 못 본다 |
| 빈 응답 | 데이터가 없는 경우가 얼마나 흔한가 |

> **성지웹 실측**: 집중률은 206곳 중 **32곳만** 등재돼 있다.
> 즉 이 기능은 **84%의 경우 아무것도 못 보여준다.** 이걸 만들기 전에 알았어야 했다.

## 7-3. ③ 표를 설계할 때 정하는 6가지

성지웹의 `holy_sites` 마이그레이션이 좋은 본보기다. 실제 파일 `[supabase/migrations/20260804090000_create_holy_sites.sql]` 에서 배울 것:

### (1) 맨 위에 "이게 무엇이고 왜 여기 있나"를 쓴다

```sql
-- 성지 마스터 테이블.
-- 앱이 직접 수집·큐레이션한 자체 데이터다(TourAPI 응답이 아니므로 저장·캐싱에 제약이 없다).
```

> **한 줄이 규칙 전체를 담고 있다.** 다음 세션이 이 주석만 봐도 "저장해도 되는 데이터"임을 안다.

### (2) 저장해도 되는 데이터 / 안 되는 데이터를 **표 단위로** 가른다

| 구분 | 성지웹 | 규칙 |
| --- | --- | --- |
| 우리가 모은 것 | `holy_sites` | DB 저장·캐시 자유 |
| 외부 API 응답 | TourAPI | **저장 금지**, 매번 호출 |

> **이 구분을 흐리면 공모전 실격 위험**이었다 `[ADR 0002]`.
> 라디오작가에도 같은 축이 있다 — 우리가 쓴 원고 vs 외부에서 받아온 자료.

### (3) 중복을 DB 가 막게 한다

```sql
-- 같은 성지가 두 번 들어가는 사고를 막는다(시드 재실행 시에도 안전).
create unique index if not exists holy_sites_name_location_key
  on public.holy_sites (name, coalesce(location, ''));
```

> **코드로 막지 말고 DB 로 막는다.** 시드 스크립트를 두 번 돌려도 안전해진다.

### (4) 자주 거르는 축에 인덱스를 건다

```sql
create index ... on public.holy_sites (diocese);
create index ... on public.holy_sites (emotion_tag);
```

기획 6-3 ⑤ 화면 목록에서 "어떤 데이터가 필요한가" 를 적었으면, **거르는 축이 거기 다 나와 있다.**

### (5) 권한을 표 만들 때 같이 정한다 (RLS)

```sql
alter table public.holy_sites enable row level security;

-- 성지 정보는 누구나 읽을 수 있다. 쓰기는 service_role(관리자)만 가능하다
create policy "holy_sites_public_read" on public.holy_sites for select using (true);
```

> **나중에 붙이면 늦는다.** 성지웹은 9/14 에 DB 권한 전면 검토를 따로 해야 했다
> `[docs/20-architecture/DB-권한-검토-2026-09-14.md]`.

### (6) 진짜 데이터는 마이그레이션과 분리한다

```sql
-- 실제 성지 데이터는 supabase/seed/01_holy_sites.sql 로 분리해 두었다.
```

**구조(표 만들기)와 내용(데이터 넣기)을 섞지 않는다.** 표는 한 번, 데이터는 계속 늘어난다.

## 7-4. 원본과 파생을 분리한다 — 가장 중요한 설계 결정

성지웹의 `holy_site_translations` 주석이 이 원칙을 그대로 설명한다
`[supabase/migrations/20260805110000_create_holy_site_translations.sql]`:

```
화면 문구(버튼·라벨)는 코드의 사전(shared/i18n/dictionary.ts)에 있고,
성지 설명·역사 같은 콘텐츠는 여기 있다. 둘은 갱신 주기가 완전히 다르다 —
문구는 배포할 때 바뀌고, 콘텐츠는 취재하면서 계속 늘어난다. 섞으면 둘 다 관리가 어려워진다.

원문(한국어)은 holy_sites 에 그대로 두고, 이 표에는 번역만 쌓는다.
번역이 없으면 앱은 한국어 원문으로 떨어진다(폴백). 빈 화면을 보여주는 것보다 낫다.
```

여기서 배울 네 가지:

| 원칙 | 성지웹 | 라디오작가라면 |
| --- | --- | --- |
| **갱신 주기가 다르면 표를 나눈다** | 화면 문구 / 콘텐츠 번역 | 프로그램 설정 / 회차 원고 |
| **원문은 건드리지 않고 파생만 쌓는다** | 한국어 원문 + 번역 표 | AI 초안 + 작가 수정본 |
| **없으면 원본으로 떨어진다 (폴백)** | 번역 없으면 한국어 | 수정본 없으면 초안 |
| **번역 안 하는 것을 정한다** | 주소는 번역 안 함 (택시 기사에게 통해야) | 고유명사·인용문 |

## 7-5. **AI 가 만든 것과 사람이 고친 것을 반드시 구분한다**

라디오작가에 그대로 쓸 설계가 성지웹에 이미 있다.

```sql
-- AI 초벌 번역인지, 사람이 감수했는지.
-- 종교 용어는 오역이 곧 신뢰 문제라 이 구분을 숨기지 않는다.
translation_status text not null default 'machine'
  check (translation_status in ('machine', 'reviewed')),
reviewed_by text,
reviewed_at date,
```

세 칸이 전부다: **상태 · 누가 봤나 · 언제 봤나.**

> **이 칸이 없으면 무슨 일이 생기나**: 성지웹의 es·fr·pt·it 206곳은 기계 번역 상태다.
> 이 칸이 있었기 때문에 **"무엇이 아직 검수 안 됐는지"를 명령 한 줄로 셀 수 있다**
> (`npm run translate:status` → 영어 감수 완료 9곳 `[2026-09-23]`).
> 이 칸이 없었다면 206곳을 눈으로 세야 했다.

**라디오작가는 이 구조가 서비스의 핵심이다.** AI 초안 → 작가 검수 → 제출.
`draft_status: 'ai' | 'edited' | 'submitted'` + `edited_by` + `edited_at` 로 시작한다. → [13장](13-라디오작가-적용.md)

## 7-6. ④ 마이그레이션 — 표를 바꾸는 유일한 방법

**Supabase 대시보드에서 손으로 표를 고치지 않는다.** 파일로 남겨야 다음 세션이 안다.

```
supabase/migrations/
  20260804090000_create_holy_sites.sql        ← 날짜+시각_무엇을
  20260805110000_create_holy_site_translations.sql
  20260918150000_ai_chat_messages.sql
```

성지웹은 7주에 **36개**를 썼다 `[ls supabase/migrations, 2026-09-23]`.

> **규칙**: 새 표를 추가하면 마이그레이션 파일과 타입 파일(`shared/types/database.ts`)을 **같이** 고친다 `[CLAUDE.md]`.
> 하나만 고치면 코드가 DB 와 어긋난다.

## 7-7. ⑥ 읽어오는 통로 — repository 한 곳으로 모은다

**화면이 DB 를 직접 부르지 않는다.** 8/4 재구축의 핵심 결정이었다 `[5879fe4]`.

```
화면 (SiteDetailPage.tsx)
  ↓ 훅을 부른다
use-site.ts  (TanStack Query)
  ↓ repository 를 부른다
sites.repository.ts   ← 여기서만 supabase 를 직접 부른다
  ↓
Supabase
```

**repository 가 하는 일은 딱 하나**: DB 행(`region_province` 같은 snake_case)을
도메인 타입(`regionProvince` 같은 camelCase)으로 바꾸는 것.

> **왜 이게 중요한가**: DB 컬럼 이름이 바뀌어도 **repository 한 파일만** 고치면 된다.
> 화면이 직접 불렀다면 21개 화면을 다 뒤져야 한다.

### 캐시 키는 한 곳에서 만든다

```
src/shared/api/query-keys.ts   ← 29번 수정된 파일
```

29번 고쳤다는 건 캐시 키 규칙이 계속 바뀌었다는 뜻이지만, **한 파일에 모여 있어서 29번으로 끝났다.**
흩어져 있었으면 그 몇 배였을 것이다.

## 7-8. 데이터가 없을 때를 먼저 정한다

> **3장 사건 4의 진짜 교훈**: 데이터가 없을 때 **0점**이 되면, 실패한 것이 1등이 된다.

새 데이터를 쓸 때마다 이 표를 채운다.

| 상황 | 화면은? |
| --- | --- |
| 데이터가 있다 | 정상 표시 |
| **데이터가 없다** | **안 그린다** (0으로 계산하지 않는다) |
| 호출이 실패했다 | "정보를 불러오지 못했어요" — 없는 것과 구분한다 |
| 일부만 있다 | 있는 것만 보여주고 나머지는 조용히 뺀다 |

> 성지웹 재설계 후 규칙: *"집중률 없는 시군구는 등급을 내지 않는다(축제 0건 ≠ 조용)"* `[615642e]`.
> **없음과 0은 다르다.** 이 한 줄이 기능 하나를 다시 만들게 한 교훈이다.

## 7-9. 2단계 완료 체크리스트

- [ ] 외부 API 응답을 **실제로 받아 파일로 저장**했다
- [ ] 데이터가 **없는 경우가 얼마나 흔한지** 세어봤다 (성지웹: 집중률 32/206)
- [ ] 표마다 맨 위에 "이게 무엇이고 왜 여기 있나" 주석을 썼다
- [ ] **저장해도 되는 데이터 / 안 되는 데이터**를 표 단위로 갈랐다
- [ ] 중복을 DB 의 unique index 로 막았다
- [ ] RLS(권한)를 표 만들 때 같이 정했다
- [ ] 구조(마이그레이션)와 데이터(시드)를 분리했다
- [ ] **AI 가 만든 것 / 사람이 고친 것**을 구분하는 칸을 뒀다
- [ ] repository 를 만들었고 **화면은 DB 를 직접 부르지 않는다**
- [ ] **데이터가 없을 때 화면이 어떻게 되는지** 표로 정했다
