# 기능설명서

2026 관광데이터 활용 공모전 — 웹·앱 구현 부문 1차 심사(기능 심사) 제출용.
`원본-공모전제출/기술보고서.md`의 심사 제출자료 체크리스트 중 "서비스 기능설명서"
항목에 대응한다.

## 1. 서비스 개요

**VisitHolyKorea(순례ON)** 는 한국 가톨릭 성지 208곳을 다루는 순례 웹앱이다(Web·Android·iOS
단일 코드베이스, Capacitor).

기존 관광 앱은 같은 데이터로 "어디가 인기 있나"를 보여준다. 이 서비스는 같은 데이터로
정반대를 묻는다 — "오늘 어디가 비어 있나." 붐비는 관광지 자체를 없애자는 게 아니라, 그
옆에 있는 한적한 성지를 도보권으로 엮어 "혼잡을 경유하되 쉼표를 찍는" 완결된 코스로
제안한다.

대상: 여유로운 여행을 원하는 자유여행객, 심리적 재충전이 필요한 사람, 종교와 무관하게
걷기·사색 여행에 관심 있는 사람, 성지순례객과 외국인 관광객(다국어 지원).

## 2. 지정과제 연계 내용

지정과제 2번(오버투어리즘 / 유명 관광지 쏠림 대응)에 접수된 서비스다
(`원본-공모전제출/기획서.md`).

일반적인 오버투어리즘 대응은 "명소 A 대신 B"식 단순 대체 추천에 그친다. 이 서비스는
한국관광공사 TourAPI의 **실시간 축제·명소 데이터를 매일 합산해 성지별 붐빔 지수(0~100)를
계산**하고(`src/features/quiet/api/crowding-score.ts`), 지수가 낮은(조용한) 성지를
그날그날 추천한다(`src/features/quiet`, 홈 화면 "오늘의 쉼표" 섹션). 대체 추천 자체도
정적 목록이 아니라 매 조회 시 TourAPI를 다시 불러 계산한 결과다
(`src/features/quiet/api/alternatives.ts`).

### 3-1. 감정 태그(해시태그) 연계 코스 매칭 — 상세

체크리스트가 별도로 요구하는 "해시태그 연계 기능"에 해당한다. 구현은
`src/features/courses/api/course-matching.ts`.

동작 흐름:

1. 사용자가 감정 태그(위로·새출발·평온·치유·감사 5종) 하나를 선택
2. 해당 태그가 붙은 성지 후보를 `holy_sites`에서 조회 (`fetchSitesByEmotion`)
3. 좌표가 있는 성지는 그 좌표를 기준으로 TourAPI 반경 검색을 실시간 호출해
   도보권 관광지를 1곳 페어링 (`getNearbyAttractions`)
4. 성지·관광지 페어를 "쉼표 순례길" 코스 카드로 조립 — 콘텐츠 완성도 점수로 정렬하되
   동점 구간은 매번 셔플해 같은 코스만 반복 노출되지 않게 함
5. 아직 좌표가 없는 성지는 페어링 없이 "성지 단독 카드"로 내려가고, 좌표가 채워지면
   코드 수정 없이 자동으로 페어링이 살아나는 구조

## 4. 한국관광공사 OpenAPI(TourAPI) 활용 정보

구현: `src/shared/api/tour-api.ts` (KorService2, `https://apis.data.go.kr/B551011/KorService2`).

사용 엔드포인트:

| 엔드포인트 | 함수 | 용도 |
| --- | --- | --- |
| `areaBasedList2` | `getAreaBasedAttractions` | 지역 코드 기준 인기 관광지 |
| `locationBasedList2` | `getNearbyByLocation` / `getNearbyAttractions` | 좌표 기준 반경 내 관광지 검색(성지 상세 "주변 정보", 코스 매칭 페어링) |
| `searchKeyword2` | `searchAttractionsByKeyword` | 이름으로 관광지 검색(붐빔 대체 추천의 시작점) |
| `searchFestival2` | `getNearbyFestivals` | 성지 주변 10km, 오늘 이후 열리는 축제·행사 |
| `searchFestival2` (전국) | `getOngoingFestivals` | 오늘 진행 중인 전국 축제 — 붐빔 지수 계산의 핵심 입력 |

### 실시간 전용 · 미저장 원칙

공모전 규정상 TourAPI 응답은 저장·재사용 대상이 아니라 매 요청 실시간으로 호출해야 한다는
전제 아래 다음과 같이 강제하고 있다(`docs/20-architecture/adr/0002-tourapi-usage.md`):

- `shared/api/tour-api.ts`의 함수는 결과를 어디에도 저장하지 않는다. 저장·캐싱이 허용되는
  것은 우리가 직접 수집한 `holy_sites` 데이터뿐이다.
- TanStack Query 훅(`use-nearby-tour.ts`)은 `staleTime: 0, gcTime: 30초, retry: 0`으로
  설정되어, 화면에 들어올 때마다 실제로 API를 다시 호출한다.
- 서비스워커 런타임 캐시(`vite.config.ts`의 workbox `runtimeCaching`)는 Supabase
  `holy_sites` 요청만 대상으로 하고 TourAPI 도메인은 캐시 대상에서 제외했다.
- 홈 화면 1회 로드가 다수의 TourAPI 호출(축제·붐빔 후보·코스 등)을 동시에 일으키므로,
  응답 캐싱이 아니라 **순수 동시 요청 수 제한**(세마포어 4개, `createConcurrencyGate(4)`)만
  두어 초당 요청 한도(에러코드 23) 초과를 피한다. 이는 매 요청을 실시간으로 다시 보내는
  것과 모순되지 않는다.

미해결 항목 1건: `holy_sites.image_url` 일부가 TourAPI 유래(`tong.visitkorea.or.kr`)
이미지다. ADR 0002가 제출 전 직접 촬영 이미지로 교체할 것을 권고하고 있으며, 아직 정리
중이다(`docs/10-product/로드맵.md` 1단계).

## 5. AI 순례 가이드 '미카엘' — 데이터 범위 제한

`supabase/functions/ai-guide/index.ts` (Deno Edge Function). 클라이언트가 아니라 Edge
Function에서 Gemini(`gemini-2.5-flash`)를 호출해 API 키가 브라우저 번들에 노출되지 않는다.

질문과 관련된 `holy_sites` 레코드(이름·위치·설명 기준 검색)를 최대 5건 컨텍스트로 넣고,
시스템 프롬프트에 "컨텍스트에 없으면 모른다고 답하라"를 명시해 종교 성지의 역사·전례
정보를 성지 DB 범위 밖에서 지어내지 않도록 제한한다. 코드는 완성되어 있으나 Edge Function
실배포는 아직 진행 전이다(`docs/10-product/로드맵.md` 2단계).

## 6. 접근성

`src/shared/i18n/SettingsProvider.tsx` 가 다음을 전역 상태로 관리하고 localStorage에
저장한다.

- 큰 글자 모드: `html[data-text-size]` 속성으로 전역 폰트 스케일 적용(고정 px가 아닌 rem
  기반 Tailwind 크기 사용)
- 한/영 다국어 전환: UI 문구는 `dictionary.ts`, 성지 콘텐츠 번역은 `holy_site_translations`
  테이블에서 별도 관리

## 8. 서비스 발전성

`docs/10-product/로드맵.md` 2~4단계에서 발췌.

- AI 하루 코스 자동 생성 — 성지 + TourAPI 관광지·맛집·숙박을 조합한 코스 자동 구성
- 마음 나침반 응답 저장 — 현재는 화면 안에서만 쓰이고 사라지는 응답을 추천 개인화에 활용
- `catholic_directory`(CBCK 주소록 5,918건) 활용 — 성지 주변 피정의집·본당 미사시간 안내 확장
- 즐겨찾기(찜하기) 완성 — 현재 버튼만 있고 동작하지 않음
- 비신자·외국인용 관점 토글, 다국어 확장
- 타 종교·해외 성지로 확장 가능한 데이터 모델 리팩터링

## 9. 제출 전 준비가 필요한 항목

아래는 이 문서(코드/문서 저장소)만으로는 채울 수 없는, 실제 운영·제출 절차에서 처리해야
하는 항목이다.

- **서비스 테스트 계정** — 저장소 안에 시드 계정이나 데모 로그인 안내가 존재하지 않는다.
  제출 전 별도로 테스트 계정을 만들어야 한다.
- **대표 사진** — 208곳 중 14곳만 확보(`docs/10-product/로드맵.md` 1단계). 나머지는 현장
  촬영이 필요하다.
- **TourAPI 운영계정 전환** — 개발계정 일일 한도 1,000건으로는 하루 45회 접속 시 서비스가
  멈춘다. 운영계정(100,000건) 전환 신청을 9월 초까지 완료해야 승인이 심사 전에 끝난다.
- **화면 스크린샷 / 데모 영상** — 포털 제출 양식에 별도로 첨부해야 하는 바이너리 자료라
  이 문서에는 포함하지 않았다.
