# 인근 혼잡도 재설계 — 붐빔 지수를 재기획 기준으로 바꾸기

작성 2026-09-16 · **9/16 사장님 결정: §4·§10 방향으로 구현** (축제 화면은 삭제 예정)

사장님 요청: "재기획 기준으로 붐빔 지수를 어떻게 바꿔야 할지 정리. 이름은 혼잡도·밀집도 쪽으로.
관광지가 아니라 DB 의 특정 장소(성지)에 대해 구할 수 있나. SK 장소혼잡도 말고 관광공사 API 4종
(지역별 관광 수요 강도 · 지역별 관광 자원 수요 · 빅데이터 지역별 방문자수 · 관광지 집중률)으로
상세 페이지에 '인근 지역이 조용 / 보통 / 붐빔' 을 표시하고 싶다."

관련: `2026-09-14-전면-재기획.md` §4-1(금지 표현) · `2026-09-15-오늘의-성지-일정-스펙.md` §8 ·
`docs/DSH/2026-09-15-노력-대비-성과-우선순위.md` A-2 · `docs/이어서-할-일.md` 9/15(2) 실측.

## 0. 한 줄 결론

- **성지 자체의 사람 수를 재는 데이터는 4종 어디에도 없다.** 집중률에 **이름으로 올라 있는 성지 32곳**만 예외다.
  나머지는 전부 **시·군·구 단위** 값이다. 그래서 문구의 주어는 재기획 A-2 그대로 **"인근 지역"** 이어야 하고,
  이 한계는 화면에 그대로 적는다.
- 지금 산식의 두 축(명소 개수 · 식당 개수)은 "사람"이 아니라 "시설"을 센다. 이것을 관광공사 **방문자수(이동통신 실측)** 와
  **집중률(관광지별 예측)** 로 바꾸면, "관광데이터로 혼잡을 추정한다"는 말이 처음으로 사실이 된다.
- **실호출 완료(9/16 14:30, §6)**: 집중률·방문자수는 되고, 수요 강도·자원 수요는 개발 계정에서 0행이라 뺀다. 방문자수는 30일 지연.

## 3. 새 산식 제안 — 두 신호, 세 등급

지금(`crowding-score.ts`): 축제 50 + 명소 밀도 30 + 식음·숙박 밀도 20 → 0~100 → 5등급, 집중률 있으면 60% 가중(한 번도 작동 안 함).

제안:

```
오늘 신호 (0~100)  = 집중률 (있으면)  … 관광지별 예측
                     없으면 오늘 축제 압력만 (기존 festivalPressure 그대로, 50점 만점 → ×2)
상시 신호 (0~100)  = 이 시군구의 최근 방문자수(외지인 b + 현지인 a)를 전국 229 시군구 안에서 백분위로
                     … "원래 사람이 많이 오는 지역인가"
인근 혼잡도        = 오늘 신호 0.6 + 상시 신호 0.4  →  조용 <30 · 보통 30~59 · 붐빔 ≥60
```

- **집중률을 성지에 붙이는 규칙** — ① 성지 이름 ↔ `tAtsNm` 매칭(공백 제거 · 3자 이상 포함, 일정 스펙 §8-2 와 같은 함수)이 되면 **그 값**을 쓰고 근거에 「관광공사 예측 집중률 N% · 이 성지」. ② 안 되면 **같은 시군구 관광지 집중률의 중앙값**을 쓰고 근거에 「인근 관광지 N곳 집중률 중앙값 M%」. 최댓값은 쓰지 않는다(9/14 감사에서 과대추정으로 판명). ③ 시군구에 데이터가 없으면(광주·전남) 오늘 신호는 축제만.
- **방문자수 백분위** — 같은 요일 효과를 피하려고 **가장 최근 7일 합**(★ 지연 확인 후 조정)을 쓰고, 전국 시군구 분포 안에서 위치를 낸다. 절대 인원수는 화면에 안 적는다(데이터랩 안내: "총량 활용 비권장, 추세용").
- **뺀다** — 명소·식음 개수 축(`infraDensity`). 시설 수는 사람 수의 근거로 약하고, 이걸 빼면 상세 페이지의 `locationBasedList2` 호출도 「주변 관광 정보」 절과 겸용 1회로 줄어든다.
- **수요 강도·자원 수요** — 점수에 넣지 않는다. 값이 실제로 오면 근거 줄 하나로만: 「이 지역 관광 수요 강도 상위 N%(관광공사 월 지수)」. 0행이면 안 쓴다.

가중치 0.6/0.4 와 경계값 30/60 은 **실호출 후 성지 몇 곳(명동·솔뫼·배론·삼성산·해미)으로 손으로 맞춰 본 뒤 확정**한다. 지금은 자리표시자다.

## 4. 화면 — 결정판 (9/16 사장님 확정, 오후에 라벨로 단순화)

**색 점 + 문장 하나짜리 라벨.** 카드가 아니다 — 다른 UI 어디에나 붙이는 작은 부품(`CrowdingLabel`).
등급은 세 단계, 숫자는 없다. 근거·면책 문장은 화면에 내지 않고 `title`(마우스 올렸을 때)로만 남긴다.

```
● 인근 지역이 조용해요        ← 초록 · 노랑 · 빨강 점 + 문장. 이게 전부다
```

| 자리              | 어떻게                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------ |
| 성지 상세 히어로  | 주소 아래 감정 태그 줄 맨 앞에(사진 위라 반투명 흰 배경판)                                             |
| 일정 화면 오전 줄 | 성지 이름 아래 같은 라벨                                                                               |
| 값이 없을 때      | **아무것도 그리지 않는다** — 조회 중·실패·집중률 없는 지역(광주·전남). 라벨은 말할 수 있을 때만 말한다 |
| 오후 관광지 줄    | 「관광공사 예측 집중률 · 여유 / 보통 / 붐빌 예정」 텍스트 그대로(퍼센트 없음)                          |

**🔴 구체적인 수치는 화면에 내지 않는다** (9/16 사장님 지시) — 퍼센트·점수·건수·km 전부.
근거 문장(`reasons`)은 산식이 계속 만들지만(발표·디버그용) 화면 부품은 쓰지 않는다.

- 후보 카드 「인근이 조용해요 · 추정」 태그: 유지, 판정은 새 산식의 「조용」.
- 버린다: `CrowdingBadge` 5등급 색 배지·점수 표기, 명소·식당 개수 축, 「아주 조용 · 매우 붐빔」 구분, 축제 카드의 배지, 카드형 「인근 혼잡도」(오전에 만들었다가 라벨로 교체).


**이 층을 만들려면 (결정 필요)**

1. 미사 시간을 텍스트에서 열로 — `holy_sites.mass_times`(원문) + 파싱 결과(`mass_schedule` jsonb: 요일·시각·비고). 서울 13곳은 있고, 41곳은 주소록에서 옮길 수 있고, 나머지는 성지 공식 안내에서 사람이 채운다. 출처는 `site_sources` 에.

3. 상세 페이지에 "이 성지" 블록 — 값이 하나도 없으면 블록을 안 그린다(더미 금지).

## 10. 최소 기능 — 관광공사 API 만으로 되는가 (9/16 사장님 질문)

**된다.** 이미 승인·연결된 두 API 로 충분하고, 새 API 승인은 필요 없다.

| 층               | 데이터                                                                  | 상태                                                                                                              |
| ---------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 이 성지 (32곳만) | 집중률 `tatsCnctrRatedList` — 성지 이름 매칭                            | 승인 O · 프록시 허용 O · 앱 결합 코드는 `signguCd` 누락·좌표 매칭으로 **작동 안 함** → 고쳐야 함 (일정 스펙 §8-4) |
| 인근 지역        | 같은 시군구 관광지 집중률 **중앙값** + 오늘 축제 `searchFestival2` 15km | 축제는 지금도 작동. 집중률은 위와 같은 수정                                                                       |

최소 산식: `집중률(중앙값 또는 성지 값) × 0.7 + 축제 압력(0~100) × 0.3` → 조용 <30 · 보통 30~59 · 붐빔 ≥60. 상시 신호(방문자수 백분위)는 **2차**.

- 시군구에 집중률이 없으면(광주·전남 6곳) 등급을 내지 않고 「관광공사 집중률 데이터가 없는 지역 · 오늘 인근 행사 있음/없음」만 적는다. 축제 0건을 "조용"으로 읽지 않는다.
- 상세 1회당 호출 ≤ 2 (집중률 시군구 6시간 메모리 캐시 · 축제 날짜 캐시). 개발 계정 1,000건이면 하루 500회 이상 열람 가능.
- 뺀 것: 명소·식당 개수 축, 방문자수, 수요 지수, 서울 실시간, 미사 시간 열.

**할 일 (코드)** — ① `getCongestionRates` 에 `signguCd` 전달(주소 → 시군구 코드, `congestion-coverage.ts` 의 옛 코드 별칭 재사용) ② `matchingCongestion` 을 좌표 대신 이름 매칭 + 시군구 중앙값으로 ③ `combineCrowdingScore` 산식·경계 교체, 테스트 갱신 ④ `SiteDetailPage` 「인근 혼잡도」 블록(`getCrowdingForSite` 재사용) ⑤ `PlanResult` 오전 줄은 같은 훅 ⑥ 문구 「인근 혼잡도 · 예상」 ko/en. 예상 1일. ①②의 API 쪽 동작은 §6 에서 확인됐다.
