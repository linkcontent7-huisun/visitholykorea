# 공모전 출품 컨셉 — "관광 지도를 뒤집는다"

> 2026 관광데이터 활용 공모전(웹·앱 개발 부문) 제출용 컨셉.
> 앞선 [비판검토](2026-08-리부트-비판검토.md)의 제약을 전부 지킨다 —
> 전면 리부트 없음, 기존 코드 재사용, 8주 내 완성 가능, TourAPI가 구조적으로 필수.
> [기록중심 전환](2026-08-기록중심-전환-검토.md)의 아이디어도 이 안에 들어온다.

---

## 1. 한 문장

> **모든 관광 앱은 같은 데이터로 "어디가 인기 있나"를 보여준다.
> 우리는 같은 데이터로 정반대를 묻는다 — "오늘 어디가 비어 있나."**

서비스명: **오늘의 쉼표** (기존 "쉼표 순례길"의 완성형)

---

## 2. 왜 이 각도인가

기존 앱의 "쉼표 순례길"은 이미 _"○○ 인파를 뒤로하고, 도보 12분 △△성지로"_ 라는 카피를 쓴다.
**그런데 그건 문구일 뿐이고, 붐비는지 아닌지를 실제로 계산하지 않는다.**

이 컨셉은 그 카피를 **진짜 계산**으로 바꾸는 것이다. 새 아이디어가 아니라 기존 컨셉의 완성이라
구현 위험이 낮고, 브랜드가 흔들리지 않는다.

동시에 이 각도는 **한국관광공사의 실제 정책 과제**와 정면으로 맞는다 —
오버투어리즘 분산, 지역 관광 활성화, 잘 알려지지 않은 자원의 발굴.
심사위원 입장에서 "우리 데이터로 우리 문제를 푼다"고 읽힌다.

---

## 3. 어떻게 작동하는가 (TourAPI가 없으면 성립하지 않는 구조)

### 오늘의 붐빔 지수

성지 208곳 각각에 대해 **매일 다시 계산**한다.

| 단계 | 쓰는 TourAPI                          | 무엇을 얻는가                                  |
| ---- | ------------------------------------- | ---------------------------------------------- |
| ①    | `searchFestival2`                     | 오늘 진행 중인 전국 축제·행사와 그 위치        |
| ②    | `locationBasedList2` (성지 좌표 반경) | 성지 주변 명소·음식점·숙박 (전체 유형 한 번에) |
| ③    | 둘을 합산                             | **성지별 오늘의 붐빔 지수 (0~100)**            |

지수가 낮은 곳 = **오늘 조용한 자리**.

> `areaBasedList2`(지역 인기순)도 후보로 검토했지만 쓰지 않았다.
> `locationBasedList2` 로 이미 반경 내 밀도를 얻을 수 있어 호출만 늘고 정보는 겹쳤다.
> **오퍼레이션 수를 자랑하는 것보다 계산에 실제로 쓰이는 편이 낫다.**

### 그래서 화면에 뜨는 것

> **오늘, 전국에서 가장 조용한 순례지 세 곳**
>
> _공세리성지 · 오늘 조용함_
> _반경 3km에 오늘 열리는 행사 없음. 가장 가까운 인파는 12km 밖._

그리고 반대 방향의 안내도 가능하다.

> _가려던 해미읍성은 오늘 축제 중입니다. 걸어서 15분 거리 해미순교성지는 조용합니다._

**핵심**: 이 화면은 TourAPI를 끄면 **빈 화면이 된다.** 장식이 아니라 엔진이다.
그리고 매일 결과가 바뀌므로 **캐싱하면 서비스 자체가 성립하지 않는다** — 실시간성이 요건이 아니라 필연이다.

---

## 4. 여기에 붙는 두 개의 축

### 축 2 — "조용한가"에 더해 "갈 수 있는가"

성지순례 이용자 상당수가 고령이다. 조용하다는 것만으로는 부족하다.
경사·주차·화장실·도보 거리를 함께 보여준다.

한국관광공사는 **무장애 여행 정보('열린관광 모두의 여행')**를 운영한다.
연계 가능하면 TourAPI 활용 폭이 넓어지고, 사회적 명분도 선명해진다.
→ **다만 이 데이터가 TourAPI 오퍼레이션으로 제공되는지는 확인이 필요하다**(7장).

### 축 3 — 다녀온 사람이 다음 사람에게

지수는 어디까지나 **추정**이다. 실제로 조용했는지는 다녀온 사람만 안다.
그래서 방문자가 한 줄을 남긴다.

> _"평일 오후, 저 말고 아무도 없었어요."_

이 한 줄이 다음 사람의 판단 근거가 되고, 추정 지수를 보정한다.

```
TourAPI (오늘 붐비는 곳)
      ↓
우리 DB (조용한 성지)
      ↓
사용자 방문 + 한 줄 기록
      ↓
다음 사람의 판단 근거 ─┐
      ↑                │
      └────────────────┘
```

**이 루프가 이 서비스의 발전성 논리다.** 쓰는 사람이 늘수록 추정이 정확해진다.
그리고 이 지점에서 [기록 중심 전환](2026-08-기록중심-전환-검토.md)의 아이디어가
공모전 논리 안으로 자연스럽게 들어온다 — 기록이 곧 데이터가 된다.

## 5. 심사 배점별 대응

| 항목                   | 배점 | 이 컨셉의 답                                                                                           |
| ---------------------- | ---- | ------------------------------------------------------------------------------------------------------ |
| **서비스 구현성**      | 30   | 새로 만드는 건 지수 계산과 한 줄 기록뿐. 나머지는 이미 작동한다. 8주 안에 확실히 끝난다                |
| **서비스 기획력**      | 30   | "관광 데이터로 관광객을 분산시킨다"는 역발상. 산티아고·국가유산·VisitSeoul 어디에도 없다               |
| **데이터 활용 적절성** | 20   | TourAPI 2개 오퍼레이션이 **화면이 아니라 계산에 들어간다.** 끄면 화면이 비고, 캐싱하면 성립하지 않는다 |
| **서비스 발전성**      | 20   | 성지 → 사찰·서원·고택·수목원 등 **조용한 유산 전체**로 확장 가능. 데이터 모델은 종교 중립적이다        |

"이 지역의 붐비는 곳 옆에 이런 조용한 자리가 있다"는 구조는 지역 단위로 그대로 복제된다.

## 6. 8주 실행 계획

| 주차 | 할 일                                                                       |
| ---- | --------------------------------------------------------------------------- |
| 1–2  | 붐빔 지수 계산 로직, 홈 화면을 "오늘의 쉼표"로 재구성                       |
| 3–4  | 대안 제시 UX(_"A는 붐빕니다 → B는 조용합니다"_), 스탬프에 한 줄 기록 붙이기 |
| 5–6  | 접근성 정보, **대전교구 한 코스 실제 방문 검증**(사진·좌표·지수가 맞는지)   |
| 7–8  | 기능 동결. 데모 영상, 발표자료, 버그 수정                                   |

디자인은 전면 교체가 아니라 **부분 정리**만 한다 — 그라디언트 제거, 한글 폰트 교체,
"오늘의 쉼표"가 주인공이 되도록 홈 화면 정리. (비판검토 2-E)

## 7. 정직하게 짚어둘 것

앞서 두 번, 확인하지 않고 단정했다가 틀렸다. 이번엔 미리 적어 둔다.

### ⚠️ TourAPI에 실시간 혼잡도 데이터는 없다

확인 결과 TourAPI 국문 관광정보 서비스는 15종(지역기반·위치기반·키워드검색·행사·숙박·
공통·소개·반복·이미지·동기화·반려동물 등)을 제공하지만 **혼잡도는 없다.**
한국관광 데이터랩에 방문자 수 통계가 있으나 API 제공 여부는 확인되지 않았다.

**그러므로 우리가 만드는 것은 "추정 지수"다.** 이걸 숨기면 발표에서 반드시 무너진다.
오히려 정면으로 내세우는 편이 낫다:

> _"공사 데이터에는 혼잡도가 없습니다. 그래서 공사 데이터로 혼잡도를 만들었습니다."_

이건 변명이 아니라 **기획력 점수의 근거**다. 다만 산식은 발표자료에 투명하게 공개해야 한다.

### ⚠️ 무장애 정보 API는 확인 필요

'열린관광 모두의 여행'은 웹 서비스로 확인되지만, TourAPI 오퍼레이션으로 열려 있는지는
확인하지 못했다. **착수 전에 공공데이터포털에서 확인할 것.**
없으면 축 2는 우리 자체 조사 범위로 줄인다.

### ⚠️ 지수가 맞는지 검증하지 않으면 "그럴듯한 숫자"가 된다

1차 검증은 끝냈다(아래 8장). 다만 **책상 위 검증**이다.
5–6주차에 최소 5곳은 실제로 가서 현장과 맞는지 확인해야 한다.

## 8. 1차 실측 결과 (2026-08-05)

산식을 구현하고 실제 TourAPI로 성지 18곳을 계산했다. 재현: `npm run crowding`

**오늘 전국에서 진행 중인 행사 51건** (전국 조회 2회로 수집)

| 성지                   | 지수     | 등급      | 축제 / 명소 / 체류 |
| ---------------------- | -------- | --------- | ------------------ |
| 인제 소양로 성당(내면) | 0        | 아주 조용 | 0 / 0 / 0          |
| 신리성지               | 3.5      | 아주 조용 | 0 / 3.5 / 0        |
| 퇴강 성당              | 6.6      | 아주 조용 | 0 / 6.6 / 0        |
| 솔뫼성지               | 7.9      | 아주 조용 | 0 / 3.5 / 4.4      |
| 해미순교성지           | 12.5     | 아주 조용 | 0 / 9.4 / 3.1      |
| 공세리성지성당         | 15.5     | 조용      | 0 / 13.9 / 1.6     |
| 갈매못 순교성지        | 18.7     | 조용      | **15.2** / 3.5 / 0 |
| 천호성지               | 38.5     | 보통      | 17.8 / 13.9 / 6.8  |
| 황새바위 순교성지      | 46.0     | 보통      | 0 / 28.3 / 17.7    |
| 범어 주교좌대성당      | 46.2     | 보통      | 0 / 28.1 / 18.1    |
| 죽림동 주교좌 성당     | **74.0** | 매우 붐빔 | 28.4 / 29.1 / 16.5 |

### 이 결과가 말해주는 것

**① 도심과 농촌이 갈린다.** 범어(대구 수성구)·황새바위(공주 시내)·죽림동(춘천 도심)은
명소·식음 밀도만으로 이미 28점대인 반면, 신리·솔뫼(당진 논밭)는 3~8점이다.

**② 축제를 실제로 잡아낸다.** 오늘 축제 점수가 붙은 곳은 근거가 명확했다.

- 갈매못 순교성지 15.2점 → 보령머드축제. 갈매못은 보령시 오천면, 대천 축제장까지 약 10km
- 죽림동 주교좌성당 28.4점 → 춘천 썸머워터 페스티벌

**③ 같은 도(道) 안에서도 정반대가 나온다.** 강원도의 인제 소양로 성당은 0점,
춘천 죽림동 주교좌성당은 74점. **"강원도로 가세요"가 아니라 "오늘은 인제로 가세요"**가 된다.
이 해상도가 이 서비스의 값어치다.

**④ 호출 수 설계가 통한다.** 다만 처음 계산은 틀렸으니 실측값으로 적어 둔다.

전국 축제 조회는 "1회"가 아니라 **2회**다. 60일치를 페이지당 300건씩 받는데
전국 축제가 300건을 넘어 2페이지가 나온다(페이지당 100건일 때는 4회였다).

| 구간                              | 호출     |
| --------------------------------- | -------- |
| 전국 축제 (1단계)                 | 2회      |
| 후보 12곳 인프라 (2단계)          | 12회     |
| **오늘의 쉼표 합계**              | **14회** |
| (참고) 기존 쉼표 순례길 코스 추천 | 8회      |
| 홈 화면 1회 로드 총합             | **22회** |

유형별로 따로 물었다면 후보 12곳만으로도 72회였다. 성지가 208곳으로 늘어도
2단계는 후보 수만 따라가므로 **14회 그대로**다 — 이게 이 설계의 핵심이다.

다만 홈 1회 로드에 22회는 가볍지 않다. **인증키 일일 한도 확인이 착수 전 필수**이고(9장),
초과하면 후보 수를 12 → 8로 줄이는 것이 가장 손쉬운 조정이다.

### 아직 남은 것

- **현장 검증**: 위 숫자는 API가 말하는 붐빔이다. 실제로 조용했는지는 가 봐야 안다
- **가중치 조정**: 지금 값(축제 50 / 명소 30 / 체류 20)은 첫 설정이다.
  현장 검증 후 조정하고, 조정 이력을 남긴다
- **TourAPI 등록 편차**: 시골 성지 주변은 애초에 TourAPI 등록 자체가 적다.
  "조용하다"와 "데이터가 없다"를 구분하지 못하는 구간이 있을 수 있다 —
  이건 산식의 한계로 발표에서 밝힐 것

## 9. 착수 전 30분 확인 목록

1. 공공데이터포털에서 **무장애 관광정보 API** 존재 여부
2. **TourAPI 인증키 일일 호출 한도** — 성지 208곳 × 3개 오퍼레이션을 매일 계산하면 호출량이 는다.
   한도를 넘으면 서비스가 죽는다. 초과 시 계산 주기를 조정하거나 인기 성지 위주로 줄인다
3. `searchFestival2`의 좌표 기반 조회가 **전국 단위로도 동작하는지**
