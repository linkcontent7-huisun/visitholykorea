# 오버투어리즘 — 우리가 말할 수 있는 것과 없는 것

작성 2026-09-21 00:20 · 기능 설명서·발표자료에 넣을 근거 정리. 사장님이 정리한 분석(9/20 밤)에
코드·DB 실측(9/20)을 맞춰 넣었다. **숫자는 잰 날짜를 같이 본다.**

## 한 줄 주장

> 한국관광공사 **관광지별 집중률 예측**을 실시간으로 불러와 성지 주변 밀집도를 상·중·하로 보여주고,
> 붐비는 날·곳에는 같은 지역의 조용한 성지와 주변 볼거리를 대신 제안한다 —
> 유명 성지 열 곳에 몰리던 순례를 **206곳 · 30일**로 펼친다.

"해결"이 아니라 **좁지만 진짜인 기여**로 말한다. 우리 앱을 여는 사람은 이미 성지에 갈 사람이다.
홍대·경복궁의 일반 관광객은 우리 사용자가 아니므로 "일반 관광객을 지방으로 뺀다"는 주장은 심사에서 약하다.
우리가 실제로 움직일 수 있는 것은 **순례자의 동선을 수도권 밖·성수기 밖으로 늘리는 것**이다. 이 범위로 좁혀야 설득력이 있다.

## 구조적으로 유리한 점 (사실)

- **성지 자체가 비수도권에 있다.** 8/10 DB 스냅샷 기준 경기 36 · 충남 27 · 서울 26 · 강원 23 · 경북 22 · 전북 18 …
  서울·경기·인천 66곳(32%), **나머지 68%가 지방**. (스냅샷은 208곳 기준 — 9/18 근거 없는 2곳을 지워 지금은 206곳.
  비율은 다시 재지 않았다.) 관광 앱 대부분이 서울·부산·제주로 사람을 보내는데, 우리 목적지 목록의 기본값이 내포·전주·원주다.
- **순례자는 목적지가 정해진 여행자**라 유도가 잘 먹힌다. "명동 대신 어디"가 아니라 "명동 성당 다음엔 어디"로 물으면 된다.
- **이미 쓰는 관광공사 API** (`src/shared/api/tour-api.ts`, 9/21 기준):

  | API | 앱에서 하는 일 | 분산 축 |
  | --- | --- | --- |
  | 관광지별 집중률 예측 `TatsCnctrRateService` | 성지 시·군·구 관광지의 30일 예측 → 성지 상세 **주변 밀집도 상·중·하**, 오늘의 성지 일정 후보의 「인근이 조용해요」 표시 | 시간·공간 |
  | 지역 허브·연관 관광지 `LocgoHubTar`·`TarRlteTar` | 오후에 붐빌 때 "근처 {이름}도 있어요" 대안 | 공간 |
  | 위치기반 관광정보 `KorService2` | 성지 상세 「둘러볼 곳」(반경 5km 식당·볼거리), 일정의 점심·오후 | 체류 |
  | 두루누비 걷기길 · ODII 오디오 | 「이 근처 걷기길」 | 체류 |
  | 무장애 관광정보 `KorWithService2` | 호출 경로 미확인 — 쓴다고 말하지 않는다 | — |

- 순례 코스 11개(내포·최양업 신부의 길 등)와 시·도 랜딩(`/region/:시도`, 링크는 보류 중)이 있다.

> ⚠️ 옛 분석의 `/quiet`(고요 속으로)와 `/festivals`(축제 옆 성지)는 **이제 없다.** 9/15 팀 결정으로 `/quiet` 는
> 「오늘의 성지 일정」(`/compass`)이 이어받았고, 축제는 사장님이 삭제했다. 설명서에 옛 이름을 쓰지 말 것.

## 분산의 세 축 — 지금 있는 것 / 더 붙일 것

오버투어리즘 완화의 레버는 셋이다: **어디로(공간) · 언제(시간) · 얼마나 오래(체류).**
지금 앱은 첫 번째를 "오늘" 기준으로 다루고, 체류는 부분적으로 있다.

### 공간 — "지방으로 가는 게 더 쉽게"

| 있음 | 오늘의 성지 일정이 출발지·마음 상태로 후보를 내고, 밀집도 '하' 후보에 「인근이 조용해요」를 붙인다. 붐빌 때 오후 대안. |
| --- | --- |
| 붙일 것 ① | **지방 성지 1박 2일 묶음** — 코스 데이터는 있으니 `locationBasedList2` 로 식당·숙박을 실시간으로 붙이면 "갈 만한 하루"가 된다. |
| 붙일 것 ② | **기록 기반 다음 성지 제안** — `pilgrimage_stamps` 는 우리 데이터라 분석해도 된다. 기록이 서울·경기에 몰려 있으면 홈에 "다음은 갈매못·솔뫼 어떠세요". 이 서비스만 할 수 있는 개인화된 분산. |
| 붙일 것 ③ | **대중교통 접근** — 사용자 85%가 50대 이상. 차 없는 사람에게 지방 성지는 "못 가는 곳". 가장 가까운 역·터미널, 본당 순례버스 정보가 없으면 ①②가 무용지물. (데이터 출처 미확인 — TourAPI 에 없으면 직접 수집.) |

### 시간 — 지금 가장 싸게 얻을 수 있는 것

| 있음 | 집중률 API 가 **30일치**를 주는데(`tour-api.ts` `getCongestionRates`), `crowding-score.ts` 는 **가장 이른 날(오늘)만** 쓴다. |
| --- | --- |
| 붙일 것 ④ | **"이번 달 어느 날이 조용한가"** — 이미 받고 있는 데이터를 날짜별로 보여주기만 하면 "주말 말고 화요일에 가세요"가 된다. 실시간 호출·메모리만 쓰므로 ADR 0002 를 지킨다. **비용 대비 효과가 제일 크다.** |
| 붙일 것 ⑤ | **전례력 연동** — 순교자 성월(9월)·성지 축일 미사는 붐빈다. 성지 일정 탭에 "이 날은 미사로 붐빔 / 이 주는 조용함". |

### 체류·동기 — 순례자를 지방에 머물게

| 있음 | 둘러볼 곳(5km) · 이 근처 걷기길 · 주변 성당·공소 · 오후 일정 대안. |
| --- | --- |
| 붙일 것 ⑥ | **교구별 완주 배지** — 부산 3 · 울산 3 · 전남 6곳처럼 성지가 적은 지역은 "그 교구 다 돌기"가 현실적 목표. 기록 기능과 바로 이어진다. |
| 붙일 것 ⑦ | **"실제로 조용했나" 한 줄** — 방문 기록 저장 때 「한적했어요 / 보통 / 붐볐어요」 하나만 더 받으면 예측치를 보정할 실데이터가 쌓인다. "쓸수록 정확해진다"는 발전성 논리의 실체. (출품 컨셉 축 3) |

### 측정 — 심사와 운영 둘 다에 필요

| 붙일 것 ⑧ | **분산 효과 대시보드** — 기록의 `site_id → region` 으로 "이 앱을 통한 방문 중 비수도권 비율"을 집계. 지금은 사용자 1명이라 숫자가 없지만, **측정 장치가 있다는 것 자체**가 "기여한다"는 주장의 근거가 된다. |
