# 기술 아키텍처

## 길 위에서 나를 만나는 감정 기반 성지순례 추천

---

## 1. 전체 시스템 구성도

```
[원본 자료]                    [콘텐츠 관리]              [운영 자동화]           [프로덕션]              [사용자]
교구별 종합자료집(한글)  →   Notion DB           →      Make.com          →    Supabase          →   웹앱 프론트엔드
(대전/서울/대구 등)          "대한민국 성지 자료"        (검증 요청/알림)        (PostgreSQL)            (사용자가 보는 화면)
                              - 성지명, 소재지                                   - 실시간 조회용 DB
                              - 감정 태그(신규)                                  - 웹앱이 직접 쿼리
                              - 조사 상태(사람 검수)

                                                                                        ↑
                                                                              [외부 API]
                                                                    한국관광공사 TourAPI (필수)
                                                                    - 지역별 인기 관광지
                                                                    - 관광지 상세정보(교통/숙박)
```

## 2. 계층별 역할

### 2-1. 콘텐츠 원본 → Notion (콘텐츠 관리 계층)

- 교구별 자료집(hwp/pdf)에서 성지 정보를 추출해 Notion DB 행으로 구조화
- 사람이 검수하는 "조사 상태" 워크플로우 유지 (미조사→조사중→검증필요→조사완료)
- **신규 추가 필요**(코스 포맷 대응):
  - `감정 태그` (Multi-select: 위로/새출발/평온/치유/감사)
  - `짝지은 관광지` (Text) — TourAPI 인기 관광지 중 도보권 짝
  - `코스 제목` (Text) — 예: "위로가 필요한 날, 수원 성지 걷기 코스"
  - `코스 부제` (Text) — 예: "화성행궁 인파를 뒤로하고, 도보 20분"
  - `도보 소요시간` (Number, 분 단위)

### 2-2. Make.com (운영 자동화 계층)

- 이미 구축됨: "성지 정보 검증 요청" 파이프라인 (Notion Watch → Router 3분기 → Discord 알림)
- 역할: 콘텐츠 품질 검증 후 "조사완료" 상태가 된 행만 다음 단계(Supabase)로 넘어가도록 게이트 역할
- 추가 구성 필요: Notion "조사완료" 상태 → Supabase 테이블 upsert 모듈

### 2-3. Supabase (프로덕션 데이터 계층)

- PostgreSQL 기반, 웹앱이 직접 쿼리하는 실사용 DB
- Notion은 "편집/검수용", Supabase는 "서비스 운영용"으로 역할 분리 (Notion API는 트래픽이 많은 실서비스 조회에 부적합하기 때문)
- 최소 테이블 설계:

```sql
-- sites (성지 정보)
CREATE TABLE sites (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,               -- 성지명
  region TEXT,                       -- 지역
  address TEXT,                      -- 소재지
  history TEXT,                      -- 역사적 의미
  mass_time TEXT,                    -- 미사 시간
  latitude DOUBLE PRECISION,
  longitude DOUBLE PRECISION,
  emotion_tags TEXT[],               -- 감정 태그 배열 ['위로','평온']
  nearby_attractions TEXT,           -- 주변 관광지 (TourAPI 보완 가능)
  nearby_lodging TEXT,               -- 주변 숙박시설
  paired_spot TEXT,                  -- 짝지은 관광지명 (TourAPI 인기 관광지, 도보권)
  course_title TEXT,                 -- 코스 제목 (예: "위로가 필요한 날, 수원 성지 걷기 코스")
  course_subtitle TEXT,              -- 코스 부제 (예: "화성행궁 인파를 뒤로하고, 도보 20분")
  walk_minutes INTEGER,              -- 도보 소요시간(분)
  is_visitable BOOLEAN DEFAULT true,
  updated_at TIMESTAMPTZ DEFAULT now()
);

-- 감정 태그로 빠르게 검색하기 위한 인덱스
CREATE INDEX idx_sites_emotion_tags ON sites USING GIN (emotion_tags);
CREATE INDEX idx_sites_region ON sites (region);
```

### 2-4. 한국관광공사 TourAPI (외부 데이터 계층, 필수 요건)

- 활용 목적: ①지역별 인기(혼잡) 관광지 파악, ②추천 성지 주변의 교통/숙박 등 보조 정보 제공
- 주요 활용 엔드포인트 (확인 필요, 3장 참고):
  - 지역기반 관광정보 조회 (`areaBasedList`)
  - 위치기반 관광정보 조회 (`locationBasedList`) — 특정 성지 좌표 주변 정보 보완용
  - 키워드 검색 (`searchKeyword`)
- 인증: 발급받은 서비스키를 웹앱 백엔드(또는 서버리스 함수)에서만 사용 (프론트엔드에 노출 금지 — 보안 요건)

### 2-5. 웹앱 프론트엔드 (사용자 계층)

- **권장 스택**: 코딩 최소화를 위해 AI 기반 노코드/로우코드 웹앱 빌더 활용 권장
  - 예: v0.dev, bolt.new, lovable.dev 등 — 프롬프트로 화면 생성 후 Supabase 연동
  - 또는 project1 과제에서 다룬 것처럼 Figma 목업 → 코드 변환(V0/ChatGPT) 활용
- 화면 구성(최소):
  1. 감정 선택 화면
  2. 지역 입력 화면
  3. 추천 결과 화면 (성지 카드 + 이유 메시지)
  4. 성지 상세 화면 (정보 + 주변 관광지)
- API 호출 흐름: 프론트 → (Supabase 클라이언트로 직접 조회 or 서버리스 함수) → Supabase/TourAPI → 결과 렌더링

## 3. 데이터 흐름 요약 (사용자 요청 1건 기준)

```
사용자가 "위로" + "경기도" 선택
   ↓
① 프론트엔드 → TourAPI 호출: 경기도 인기 관광지 목록 조회
② 프론트엔드/서버리스 함수 → Supabase 쿼리:
   SELECT * FROM sites WHERE region='경기도' AND '위로' = ANY(emotion_tags)
   ↓
③ 결과 결합: 성지 정보(Supabase) + 주변 정보(TourAPI) → 화면 렌더링
```

## 4. 보안/제약 고려사항

- TourAPI 서비스키는 `.env` 등으로 관리, 저장소에 커밋 금지 (과제3에서 다룬 "민감정보 비노출" 원칙과 동일)
- Supabase는 RLS(Row Level Security) 기본 적용 — 읽기 전용 공개 API 키만 프론트에 노출
- 개인정보(사용자 위치 등)는 저장하지 않고 요청 처리 시에만 사용 (최소 수집 원칙)

## 5. 기술 스택 요약표

| 계층        | 도구                                               | 비고                                        |
| ----------- | -------------------------------------------------- | ------------------------------------------- |
| 콘텐츠 관리 | Notion                                             | 기존 구축된 "대한민국 성지 자료" DB 재사용  |
| 자동화/검증 | Make.com                                           | 기존 "성지 정보 검증 요청" 파이프라인 확장  |
| 프로덕션 DB | Supabase (PostgreSQL)                              | 웹앱이 직접 조회하는 실서비스 DB            |
| 외부 API    | 한국관광공사 TourAPI                               | 공모전 필수 요건, 인기관광지/교통/숙박 보완 |
| 프론트엔드  | AI 웹앱 빌더 (v0/bolt.new 등) 또는 Figma→코드 변환 | 코딩 최소화                                 |
| 배포        | Vercel 등 무료 호스팅                              | 프론트엔드 빌더가 보통 자체 배포 제공       |
