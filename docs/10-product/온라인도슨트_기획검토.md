# 온라인 도슨트 — 기획 검토와 설계

작성 2026-08-21. 상태: **검토 완료, 파일럿 1곳으로 진행 권장**

---

## 0. 무엇을 만들려는가

순례자가 성지에 도착해 앱에서 `시작`을 누르면, 이어폰으로 음성 안내가 시작된다.
입구부터 순서대로 걸으며 건물·벽화·스테인드글라스·성물에 대한 설명을 듣는다.
박물관의 도슨트 투어를, 도슨트 없이, 성지에서.

---

## 1. 이 기획은 좋다 — 근거 다섯

**① 공백이 실재한다.**
박물관·미술관에는 오디오 가이드가 있다. 성지에는 거의 없다.
있어도 특정 시간의 단체 해설뿐이라, 혼자 조용히 다니려는 순례자는 쓸 수 없다.

**② 매체가 행위와 맞는다.**
순례는 본질적으로 **걷는** 일이다. 화면을 보며 걸을 수는 없지만 들으며 걸을 수는 있다.
게다가 **성당 안에서 폰 화면을 들여다보는 것은 무례해 보이지만, 이어폰은 자연스럽다.**
이건 사소한 차이가 아니라 이 기능이 성립하는 이유다.

**③ 기존 자산 위에 얹힌다.** 새로 만드는 게 아니다.

| 이미 있는 것 | 도슨트에서 하는 역할 |
|---|---|
| `holy_sites` 208곳 + 좌표 | 어느 성지인지, 어디인지 |
| `holy_site_translations` | **다국어 대본의 그릇** |
| `pilgrimage_stamps` (순례 여권) | 투어 완주 → 스탬프 |
| `pilgrimage_routes` | 성지 간 이동, 도슨트는 성지 **안** |
| `map` | 정류장 표시 |

**④ 2027 WYD와 정확히 맞물린다.**
외국인 순례자는 한국어 안내판을 못 읽는다.
**오디오는 번역·합성으로 확장 가능한 유일한 매체다.** 안내판은 못 바꾸지만 오디오는 만든다.
`docs/50-research` 와 사업계획서 1-3절의 논리가 여기서 제품이 된다.

**⑤ 비신자에게 문이 열린다.**
"기도하러 가는 곳"이 아니라 "근대 건축과 역사를 듣는 곳"이 된다.
산티아고 순례자의 60%가 비종교적 동기라는 그 지점이다.

## 2. 그러나 — 이대로 하면 실패한다

### ⚠️ 위험 1. 콘텐츠 제작량 (가장 큰 위험)

산술을 해보면 규모가 드러난다.

```
성지 1곳 = 정류장 6~10개
정류장 1개 = 2~3분 = 대본 500~800자
성지 1곳 = 대본 4,000~8,000자 ≒ 25분 분량

208곳 × 25분 = 약 87시간 분량
208곳 × 6,000자 = 약 125만 자
```

**현재 `holy_sites.description` 은 곳당 한 문단 수준이다.**
도슨트 대본은 그것과 **완전히 다른 층위**의 콘텐츠다.
"208곳에 도슨트를 넣는다"는 계획은 **1인 창업자가 감당할 수 없다.**

> **결론: 208곳으로 시작하면 100% 실패한다. 1곳으로 시작해야 한다.**

### ⚠️ 위험 2. 사실 오류 — 이 기능에서 가장 치명적

*"이 스테인드글라스는 성모영보 장면을 표현합니다"* 라고 말했는데 아니면,
그 순간 앱 전체의 신뢰가 무너진다. 종교 시설이라 더 그렇다.

**AI로 대본을 생성하면 반드시 지어낸다.**
특정 성당의 특정 창, 특정 벽화는 인터넷에 자료가 거의 없다.
자료가 없으면 LLM은 그럴듯하게 채운다.

이 저장소의 `CLAUDE.md` 에 이미 같은 원칙이 있다 —
*"AI 답변은 성지 DB 안으로 제한한다. 컨텍스트에 없으면 모른다고 답하라."*
도슨트에도 그대로 적용해야 한다.

> **원칙: 도슨트 대본은 AI가 쓰지 않는다.**
> 현장 방문 + 성지 발행 자료 + 교구 자료를 근거로 **사람이 쓰고 출처를 남긴다.**
> AI는 다듬기와 번역에만 쓴다.

### ⚠️ 위험 3. 실내에서 GPS가 안 잡힌다

성당 **안**이 핵심 콘텐츠인데, 실내에서는 위치 정확도가 수십 미터로 벌어진다.
"제대 앞에 서면 자동 재생" 은 **작동하지 않는다.**

| 방식 | 실내 | 비용 | 판정 |
|---|---|---|---|
| GPS 자동 트리거 | ❌ | 0 | 야외 정류장에만 보조로 |
| **수동 `다음` 버튼** | ✅ | 0 | **기본값으로 채택** |
| QR 코드 | ✅ | 인쇄물 + 시설 허락 | 2단계 |
| 블루투스 비콘 | ✅ | 기기 + 설치 + 배터리 | 지금은 과함 |

> **결론: 수동 진행이 기본. GPS는 "이 성지에 도착하셨나요?" 정도의 보조.**

### ⚠️ 위험 4. 교회의 허락 — 위험이자 기회

성지 관리자 입장에서 *"우리 성지를 마음대로 해설하는 앱"* 은 반가운 게 아니다.
교리·역사 오류가 있으면 항의가 온다.

**뒤집으면 이것이 최대 해자다.**
교구나 성지의 **감수·승인을 받은 도슨트**는 누구도 흉내 낼 수 없다.
경쟁자가 기술로 따라와도 승인은 못 따라온다.

> **파일럿 성지와는 반드시 사전 협의하고, 대본 감수를 요청한다.**
> 승인받으면 앱 화면에 *"○○성지 감수"* 를 표기한다. 그 한 줄이 제품의 격을 바꾼다.

### ⚠️ 위험 5. 전례 중 사용

성당은 관광지이기 전에 기도하는 곳이다.
미사·성체조배 중에 도슨트를 트는 것은 실례다.

> `holy_sites` 에 이미 `mass_times` 컬럼이 있다(2026-08-18 추가).
> **미사 시간대에 시작을 누르면 경고를 띄운다.**
> 첫 정류장 안내에 순례 에티켓을 넣는다.

### ⚠️ 위험 6. 오프라인

배론성지(제천 산속), 성거산 같은 곳은 데이터가 안 터진다.
**현장에서 스트리밍하는 설계는 현장에서 실패한다.**

> **투어 시작 전 오디오 전체를 미리 받는다.** 이건 선택이 아니라 필수다.

### ⚠️ 위험 7. 저작권

근현대 성당의 스테인드글라스·벽화는 **작가 저작권이 살아 있을 수 있다**(사후 70년).
사진을 쓰려면 확인이 필요하다. 음성 설명 자체는 문제되지 않는다.

> 1단계는 **오디오 중심**으로 가고, 사진은 라이선스가 확인된 것만 쓴다.
> `catholic_directory` 에서 이미 쓰고 있는 `image_license` 관례를 따른다.

## 3. 종합 판단

**진행할 가치가 있다. 단, 범위를 좁혀서.**

| | |
|---|---|
| 하지 말 것 | 208곳 전체를 대상으로 설계·착수 |
| 할 것 | **성당 1곳을 끝까지 완성**해서 되는지 확인 |

파일럿 하나가 끝나면 알게 되는 것들이 있다 —
대본 한 곳 쓰는 데 실제로 며칠 걸리는지, 사람들이 끝까지 듣는지,
수동 진행이 실제로 불편하지 않은지. **그걸 모르고 208곳을 계획할 수 없다.**

### 파일럿 후보

| 성지 | 장점 | 단점 |
|---|---|---|
| **전주 전동성당** ★권장 | 1914년 로마네스크, 스테인드글라스 있음. **한옥마을 관광객이 이미 온다** → 비신자 반응을 볼 수 있다 | 대전에서 1시간 30분 |
| 합덕성당 (당진) | 1929년 등록문화재, **대전교구**. 솔뫼·신리와 묶임. 순례자의집 있어 협의 쉬움 | 방문객이 적어 반응 측정이 어렵다 |
| 명동대성당 | 가장 유명, 교황청 공인 순례길 | 서울. 관리 주체가 크고 협의가 느리다 |

**전동성당을 권한다.** 이 기능의 핵심 가설이 *"비신자도 듣는다"* 인데,
그걸 검증할 수 있는 유일한 후보다.

## 4. 설계

### 4-1. 데이터 구조

```sql
-- 성지 하나에 대한 투어(언어 무관 뼈대)
create table docent_tours (
  id            uuid primary key default gen_random_uuid(),
  site_id       uuid not null references holy_sites(id) on delete cascade,
  title         text not null,          -- "전동성당 건축과 순교의 자리"
  summary       text,
  duration_min  int,                    -- 예상 소요 25
  distance_m    int,                    -- 총 이동 거리
  supervisor    text,                   -- "천주교 전주교구 전동성당 감수"  ← 해자
  supervised_at date,
  is_published  boolean default false,
  created_at    timestamptz default now()
);

-- 정류장 (걸음의 단위)
create table docent_stops (
  id            uuid primary key default gen_random_uuid(),
  tour_id       uuid not null references docent_tours(id) on delete cascade,
  seq           int not null,           -- 1,2,3...
  name          text not null,          -- "정면 파사드"
  indoor        boolean default false,  -- 실내면 GPS 자동진행 끔
  lat           double precision,       -- 야외만. 실내는 null
  lng           double precision,
  arrive_hint   text,                   -- "정문 앞 계단 아래에 서세요"
  move_hint     text,                   -- "안으로 들어가 오른쪽 벽을 보세요"
  image_url     text,
  image_license text,                   -- 확인된 것만
  unique (tour_id, seq)
);

-- 언어별 대본과 오디오 (다국어 = WYD 대비)
create table docent_scripts (
  id          uuid primary key default gen_random_uuid(),
  stop_id     uuid not null references docent_stops(id) on delete cascade,
  lang        text not null,            -- 'ko','en','ja','zh'
  script      text not null,            -- 실제 낭독 대본
  sources     text,                     -- ★ 근거 출처. 비워두면 발행 금지
  audio_url   text,                     -- Supabase Storage
  audio_sec   int,
  voice       text,                     -- TTS 음성 종류 또는 '사람녹음'
  unique (stop_id, lang)
);
```

**`sources` 를 필수로 둔 것이 이 설계의 핵심이다.**
출처가 비어 있으면 발행할 수 없게 막는다. 위험 2에 대한 구조적 방어다.

### 4-2. 화면 흐름

```
성지 상세 화면
  └ [🎧 도슨트 듣기]  ← 투어가 있는 성지에만 표시

  ① 준비 화면
     - 소요 25분 · 정류장 8곳 · 이동 400m
     - "○○성지 감수" 배지
     - [오디오 미리 받기]  ← 오프라인 필수
     - ⚠️ 미사 시간이면 경고 (mass_times 조회)
     - 순례 에티켓 안내 (모자·정숙·촬영)

  ② 재생 화면 — 화면을 볼 필요가 없어야 한다
     ┌──────────────────────────┐
     │  3 / 8   정면 파사드        │
     │                          │
     │  "정문 앞 계단 아래에        │
     │   서서 위를 올려다보세요"     │  ← arrive_hint (큰 글씨)
     │                          │
     │  ▶  ━━━━━●────  2:14/3:02 │
     │                          │
     │  [◀ 이전]  [다음 ▶]        │  ← 큰 버튼. 걸으며 누른다
     │  [대본 보기]               │  ← 소리를 못 듣는 상황 대비
     └──────────────────────────┘

  ③ 완주
     - 순례 여권 스탬프 지급 (pilgrimage_stamps)
     - 인근 맛집·숙박 (holy_sites.nearby_* 이미 있음)
     - 감상 기록 (records 기능 재사용)
```

**설계 원칙: 화면을 안 봐도 되게 만든다.**
화면을 계속 봐야 하면 이 기능은 존재 이유가 없다.
큰 버튼, 굵은 글씨, 잠금화면에서도 조작 가능하게.

### 4-3. 진행 방식

```
기본        수동 [다음] 버튼          — 실내외 모두 확실
보조        야외 정류장 GPS 30m 근접 시
            "다음 지점에 도착하신 것 같아요. 재생할까요?" (자동 재생 아님)
자동 아님    실내는 GPS를 아예 쓰지 않는다
```

### 4-4. 오디오 만들기

```
① 대본 작성 (사람)      현장 방문 + 성지 자료 + 교구 자료. 출처 기록
② 감수 (성지·교구)      ← 승인받으면 배지 표기
③ TTS 합성             한국어 먼저, 이후 영·일·중
④ Supabase Storage 업로드
⑤ docent_scripts.audio_url 연결
```

TTS는 이미 쓰는 스택 안에서 고른다.
**Gemini 를 이미 Edge Function 으로 부르고 있으므로**(`supabase/functions/ai-guide`),
같은 자리에 TTS 호출을 붙이면 새 인프라가 필요 없다.
사람 녹음은 파일럿에서 한국어만 시도해볼 수 있다 — 미디어콘텐츠 제작이 본업이므로.

> ⚠️ **번역도 검수가 필요하다.** 전례 용어("제대", "감실", "십자가의 길")는
> 기계 번역이 자주 틀린다. **한국어교원 2급 자격이 여기서 쓰인다.**

### 4-5. 오프라인

- 준비 화면에서 **투어 전체 오디오를 한 번에 내려받는다**
- 서비스워커 캐시 또는 IndexedDB
- ⚠️ **TourAPI 응답은 캐시하지 않는다** (`CLAUDE.md` 원칙). 도슨트 오디오는 자체 데이터라 무방하다

## 5. 파일럿 실행 순서

| | 할 일 | 비고 |
|---|---|---|
| 1 | **전동성당에 연락** | 취지 설명 + 대본 감수 요청. 거절당해도 다음 후보로 |
| 2 | **현장 방문 1회** | 사진·메모·동선 확인. 스테인드글라스와 성물을 직접 본다 |
| 3 | **정류장 6~8개 확정** | 정면 → 내부 → 제대 → 스테인드글라스 → 순교터 → … |
| 4 | **대본 작성** | 정류장당 500~800자. **출처를 반드시 함께 적는다** |
| 5 | **감수 요청** | 성지 또는 교구 |
| 6 | **TTS 합성 + 업로드** | 한국어 먼저 |
| 7 | **앱에 붙이기** | 위 스키마 + 재생 화면 |
| 8 | **현장 테스트** | 본인이 직접 걸어보며 동선·타이밍 확인 |
| 9 | **영어판** | WYD 대비. 여기서 다국어 파이프라인을 검증 |

**4번에서 실제로 며칠이 걸리는지가 이 기능의 운명을 결정한다.**
그 숫자를 얻는 것이 파일럿의 진짜 목적이다.

## 6. 왜 이것이 사업계획서를 강하게 만드는가

- 지금까지 앱은 **"찾아주는" 앱**이었다. 도슨트가 붙으면 **"현장에서 쓰는" 앱**이 된다.
  체류 시간이 생기고, 재방문 이유가 생긴다.
- **유료화 지점이 자연스럽다.** 기본 앱은 무료, 도슨트는 권장 기여금 대상이 될 수 있다.
  (사업계획서 3-1 수익 모델의 "실비" 층과 연결)
- **WYD 대비의 구체적 산출물**이다. "다국어 안내를 준비한다"가 아니라
  "○○성당 영어 도슨트를 만들었다"가 된다.
- **교구 감수**는 1인 창업자가 가질 수 있는 가장 강한 진입장벽이다.
