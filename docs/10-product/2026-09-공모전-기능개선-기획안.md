## 2. 개선안 — 우선순위 순

### 🥇 개선 1. 순례자 사진을 성지 대표 사진으로 승격 (구현성 30점 직격)

**문제**: 사진 없는 157곳. 자동 수집 4경로(국가유산청·위키미디어·TourAPI·
좌표검색)는 8/28에 전부 소진했다. 남은 길은 현장 촬영뿐인데, 12일 안에
157곳을 도는 것은 불가능하다.

**기존 자산으로 푼다**: "순례자 이야기"(9/1 출시)로 **실방문자가 이미 사진을
올릴 수 있다.** 그런데 그 사진은 이야기 카드 안에만 갇혀 있고, 정작 비어 있는
성지 대표 사진 자리는 회색 그대로다.

**만들 것**:
- 성지에 대표 사진이 **없을 때만**, 순례자가 올린 사진 중 최신 1장을
  대표 자리에 보여준다. "순례자 ○○님이 보내온 사진" 출처를 함께 표기한다.
- 운영자 승인 플래그(`is_featured`)를 두어, 부적절한 사진이 대표가 되는
  것을 막는다. 승인 전에는 기존처럼 회색 썸네일.
- 신고 3건 자동 숨김(이미 구현)이 그대로 안전망이 된다.

**왜 이게 최선인가**: 예산·출장 없이 사진 커버리지가 오르고, **"사용자가
데이터를 함께 만드는 서비스"**라는 서사가 발전성 20점에도 동시에 걸린다.
베타 테스터 9명이 각 3곳씩만 다녀와도 27곳이 채워진다(24.5% → 37%).

**리스크**: 실사용자가 안 움직이면 사진도 0장이다. 개선 2와 반드시 함께 간다.

### 🥈 개선 2. 첫 스탬프까지의 길을 짧게 (구현성 + 실데이터)

**문제**: 스탬프 0개(8/29 실측). 심사위원이 여권 탭을 열면 **넛지 6종이
전부 빈 화면**이다. 별자리도 교구 진행 바도 데이터가 없으면 안 보인다.

> ⚠️ **더미 데이터로 채우지 않는다.** 심사 대상이 "개발 완료된 완성
> 서비스"라 가짜 스탬프는 실격 위험이자 이 프로젝트의 원칙 위반이다.

**만들 것**:
- **빈 여권 화면을 "설명하는 화면"으로**: 스탬프가 0개일 때, 앞으로 어떤
  기록이 쌓이는지 도장 실루엣(회색)과 한 줄 설명으로 보여준다. 실제 기록이
  아니라 **미리보기임을 명시**한다. 심사위원이 로그인 없이도 기능을 이해한다.
- **가까운 성지 한 곳을 첫 스탬프로 제안**: 위치 기반으로 "여기서 가장 가까운
  성지는 ○○ (12km)" 카드를 여권 빈 화면에 둔다.
- 베타 테스터 9명 온보딩 안내문(카톡 발송용) 작성 — 기능이 아니라 운영이지만
  이 개선의 절반이다.

### 🥉 개선 3. TourAPI 활용의 폭 넓히기 (데이터 활용 20점)

**현재**: 위치기반 관광정보 · 행사정보 · 키워드 검색을 실시간 호출한다.
안전하지만 **"관광공사 데이터로 무엇까지 할 수 있는가"를 보여주지는 못한다.**

**후보 (착수 전 API 제공 여부·필드 확인 필요)**:

| 후보 | 왜 우리 서비스에 맞는가 | 확인할 것 |
| --- | --- | --- |
| **무장애 여행 정보** | 신자 65세 이상 28.9%. 휠체어·경사로·장애인 화장실 정보를 성지 주변에 붙이면 **열린관광** 축이 열린다 | 해당 서비스가 성지 인근 좌표에서 결과를 주는지 |
| **반려동물 동반 여행** | 순례는 혼자·조용히 다니는 여행과 겹친다 | 데이터 밀도 |
| **숙박 정보(상세)** | 수익 모델(숙박 제휴)의 앞단. 지금은 목록만 | 실시간 호출 한도 영향 |

**원칙 재확인**: TourAPI 응답은 **저장하지 않는다**(ADR 0002). 어떤 후보를
붙이든 매 요청 실시간이며, 캐시·DB 적재를 하지 않는다. 호출 수가 늘면
개발계정 한도(1,000건/일)를 다시 넘길 수 있으므로 **운영계정 승인
결과를 먼저 확인**한다(8/28 신청, 심의 대기 중).

### 4순위. 시연 안정성 재검증 (구현성 — 방어)

## 2-1. 구현 결과 (2026-09-02, 웹 세션에서 하루에 끝냄)

기획한 네 가지 중 **웹 세션에서 가능한 부분은 모두 구현했다.** 남은 것은
사람·기기·현장이 필요한 일이다.

| 개선 | 상태 | 남은 일 (사람이 해야 하는 것) |
| --- | --- | --- |
| 1. 사진 승격 | ✅ 코드 완료 | **로컬 `npm run db:migrate`**(20260903000000) → 순례자가 사진을 올리면 `npm run photo:pending` 으로 보고 `photo:feature` 로 승인 |
| 2. 첫 스탬프 유도 | ✅ 완료 | 베타 테스터 9명 연락 (기능이 아니라 운영) |
| 3. 무장애 정보 | ⚠️ 조건부 완료 | **로컬 `npm run tourapi:check`** 로 경로 확인. 확인 전까지 화면에 안 나온다 |
| 4. 시연 안정성 | 🟡 부분 | 흰 화면 사고 **자동 가드 추가**(테스트). 실기기 확인은 로컬에서 |

**개선 1 설계 결정** — 자동 승격을 하지 않는다. 성지 대표 사진은 그 성지의
얼굴이라, 아무 사진이나 대표가 되면 성지의 격이 떨어진다. 승인 플래그
(`photo_featured`)가 기본 false 이고 운영자가 눈으로 보고 켠다.

**개선 3 설계 결정** — `KorWithService2` 경로를 웹 세션에서 검증할 수 없어서
(data.go.kr 차단), **실패하면 섹션이 통째로 사라지도록** 만들었다. 경로가
틀렸다면 앱에는 아무 일도 일어나지 않는다. 붐빔 지수가 실패를 드러내는 것과
반대로 한 이유는, 무장애 정보는 없다고 해서 틀린 화면이 만들어지지는 않기
때문이다.

**개선 4에서 실제로 한 것** — 9/1 흰 화면 사고(정규식 lookbehind, iOS 16.3
이하 SyntaxError)의 **재발을 막는 테스트**를 넣었다. 소스에 lookbehind 가
다시 들어오면 `npm run verify` 가 실패한다. `vite.config.ts` 의
`target: safari14` 는 문법 변환을 하지만 정규식 문법은 바꾸지 않으므로,
사람이 다시 쓰는 것을 막는 장치는 이것뿐이다.

> ⚠️ **웹 세션에서 못 하는 검증** — Supabase 자격이 없어 앱을 실제로 띄울 수
> 없다. 실기기 확인(안드로이드·아이폰)은 로컬 세션의 몫으로 남는다.
