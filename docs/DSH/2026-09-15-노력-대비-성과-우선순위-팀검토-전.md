## 판단 기준

**성과**는 심사 기준 셋에 얼마나 기여하는가로 본다.

| 심사가 보는 것 | 우리 앱에서 그것을 보여주는 곳 |
| --- | --- |
| 개발 완료된 **완성 서비스** | 배포본이 실제로 돌고, 빈 화면·더미가 없고, 휴대폰에서 깨지지 않음 |
| **관광데이터 활용** | 고요 속으로(붐빔) · 축제 · 상세의 주변 관광 · 두루누비 걷기 코스 — 전부 TourAPI 실시간 |
| 지정과제 **오버투어리즘 완화** | 고요 속으로 `/quiet` 한 화면이 답 |

**노력**은 시간 추정이다 (내 추정, 실측 아님). ★ 하나 = 30분 안팎, ★★★★★ = 며칠.

한 가지를 먼저 못 박는다 — **지금 배포본은 재기획 전 화면이다.** 재기획으로 만든 모든 성과가
아직 심사위원 눈에 안 보인다. 그래서 0순위는 기능이 아니라 **배포**다.

## 디자인 — 왜 AI 냄새가 나고, 무엇을 바꾸면 빠지는가

심사위원은 Vite + Tailwind + 보라 그라데이션으로 만든 앱을 수십 개 본다. "완성 서비스"라는 인상은
기능만큼 첫눈에서 갈린다. **냄새의 정체를 코드에서 찾았다** (2026-09-15 실측):

| 냄새 | 어디 | 근거 |
| --- | --- | --- |
| **Inter 글꼴** | `index.html` 12줄 · `--font-sans` | AI 생성 화면의 대표 글꼴. 한글이 없어 한글은 맑은 고딕으로 떨어진다 — 영문·한글이 다른 글꼴로 섞인다 |
| **Tailwind 기본 색 그대로** | `--color-brand-violet: #7c3aed` · `--color-brand-blue: #1e3a8a` | 각각 Tailwind `violet-600` · `blue-900` 값 그대로. 성지와 아무 상관없는 색 |
| **보라 그라데이션 카드** | 4개 파일 (홈 고요 속으로 카드에서 확인) | "AI 가 만든 랜딩" 1번 신호 |
| **`rounded-[28px]` 알약 카드** | 12개 화면 · 29개 파일 | 모든 카드가 같은 큰 반경 |
| **대문자 자간 라벨** "VISIT HOLY KOREA" | 홈 · 지역 랜딩 (`uppercase tracking-[.2em]`) | SaaS 템플릿 그대로 |
| **명조 제목이 실제론 안 쓰인다** | `--font-display: Gowun Batang` | CSS 에 정의만 있고 **`src/` 에서 쓰는 파일 0개.** 주석엔 "성지의 정적인 느낌"이라 적어놓고 적용을 안 했다. `chrome-analyze` 스킬 기준표의 "제목은 명조"도 실제 화면과 다르다 |

즉 **의도(명조 · 정적인 느낌)는 있었는데 적용이 안 됐고, 색과 글꼴이 도구 기본값 그대로다.**

### 좁은 패스 (1-6) — 반나절~하루, 로직 안 건드림

| 바꿀 것 | 어떻게 | 어디 |
| --- | --- | --- |
| 글꼴 | 본문: Inter → 한글 본문 글꼴(예: Pretendard 또는 시스템). 제목: `--font-display`(명조)를 **실제로 h1·h2 에 적용** | `index.html` · `globals.css` · 제목 컴포넌트 |
| 색 | 보라·남색 2개 값을 성지에 맞는 팔레트로 — 돌·흙·짙은 남색 + 금색 소량. 값 두 줄 | `globals.css` `@theme` |
| 그라데이션 | 단색(짙은 남색) 또는 실제 사진 | 4개 파일 |
| 반경 | `rounded-[28px]` → 토큰 `--radius-card`(12~16px)로 묶어 한 번에 | 29개 파일 (기계적 치환) |
| 라벨 | 대문자 자간 라벨 제거, 또는 명조 소문자·먹색으로 | 홈 · 지역 랜딩 |
| 검증 | 22개 화면 스크린샷 + 글자 「대」 모드에서 넘침 확인 | `chrome-analyze` 스킬 |

전부 CSS 변수·클래스 교체다. 기능 회귀 위험이 없고, 글꼴 교체로 줄바꿈이 달라지는 것만 「대」 모드에서 본다.

## 고요 속으로 — 붐빔은 관광지에만. 성지는 "대신 갈 곳"이지 "조용한 곳"이 아니다

### 지금 코드가 하는 것 (2026-09-15 실측)

| 단계 | 내용 | 파일 |
| --- | --- | --- |
| 붐빔 점수 산식 | 오늘 축제 압력 + 주변 인프라 밀도(명소·숙박 개수) + **관광공사 실측 집중률 60%** (T-020) | `src/features/quiet/api/crowding-score.ts` |
| 같은 산식을 **관광지에도, 성지에도** 적용 | 성지마다 TourAPI 로 주변 축제·명소·숙박을 세어 점수를 낸다 — 화면당 1+6회 호출 | `quiet-sites.ts` |
| 성지 카드에 **「아주 조용 ~ 매우 붐빔」 배지 + 점수** | `CrowdingBadge` | `QuietSiteCard.tsx` |
| 대안 순위 = **"등급이 실제로 내려가는 성지"** | 관광지 점수 − 성지 점수 = `relief`. 이게 기준 이상인 곳만 남기고 가까운 순 | `alternatives.ts` `rankAlternatives` |

### 무엇이 문제인가

**성지 점수는 "성지 안에 사람이 얼마나 있나"가 아니라 "성지 주변에 축제·명소·숙박이 얼마나 있나"다.**

- 명동성당은 명동 한복판이라 「붐빔」이 나온다 — 성당 안이 조용해도.
- 시골 성지는 주변에 아무것도 없어 「아주 조용」이 나온다 — 성지를 잰 게 아니라 주변이 빈 것뿐.
- 관광공사 집중률은 **관광지별 방문자 추이**라 관광지에는 맞는 데이터지만, 성지에 섞으면 "근처 관광지가 붐빈다"는 뜻이지 성지 얘기가 아니다.

심사위원이 **"이 성지가 조용하다는 걸 어떻게 아세요?"** 라고 물으면 답이 없다.
`crowding-score.ts` 머리말도 "추정"이라고 적어뒀지만, 화면의 배지는 추정으로 안 보인다.

### 바꾸는 방향 — 사장님 결정 (2026-09-15)

**붐빔은 관광지에만 보여준다. 성지에는 붐빔을 주장하지 않는다.**
성지는 "붐비는 그곳 **대신 갈 수 있는 근처 성지**"로 제시한다.

이게 오버투어리즘 서사에도 더 맞다 — 목적은 **사람을 붐비는 관광지에서 빼내는 것**이지,
성지가 조용하다고 증명하는 것이 아니다. 관광지가 붐빈다(실측) + 근처에 성지가 있다(우리 데이터)면
논리가 완성된다. 성지 점수는 필요 없다.

```
지금:  관광지 붐빔(추정) → 성지 붐빔(추정) → 둘의 차이가 큰 성지 → "조용한 성지"
바꿈:  관광지 붐빔(실측 집중률 중심) → 근처 성지, 가까운 순 + 방문 정보 갖춘 곳 → "대신 갈 곳"
```

### 두 단계로 나눈다

| | 무엇 | 노력 | 시기 |
| --- | --- | --- | --- |
| **1-8 최소 변경** | 성지 카드의 `CrowdingBadge`·점수를 **숨긴다.** 문구를 "조용한 성지" → "대신 갈 수 있는 근처 성지"로. 결과 종류(`RankOutcome`) 문장에서 "한적" 주장 제거. **순위 로직은 그대로** | ★★ (화면 + 사전 문구) | **제출 전** — 회귀 위험 낮음 |
| **3-7 본 변경** | 성지 점수 계산을 **하지 않는다.** `rankAlternatives` 를 **거리 + 방문 정보 완비(주소·연락처·좌표 있음) + 실제 방문 기록 있으면 가점** 으로. `relief` 개념 제거. `quiet-sites.ts` 의 성지별 TourAPI 호출 제거 | ★★★ (로직 + 테스트 3벌) | **제출 후 + 동료 합의** — T-R03 으로 막 손본 코드 |

1-8 을 먼저 하면 제출판에서 **거짓 주장이 사라진다.** 3-7 은 그 뒤 구조를 정리하는 것이다.

### 3-7 의 부수 효과 — TourAPI 호출이 준다

지금 고요 속으로 한 번에 **1(축제) + 6(성지별 주변 조회) = 7회**를 부른다. 성지 점수를 안 내면
관광지 쪽 조회만 남아 **1~2회**가 된다. 개발계정 한도가 1,000건/일이라(운영계정 전환 심의 미확인)
**하루 감당 인원이 5배쯤 는다.** 시연 당일 한도 초과 위험도 같이 줄어든다.

### 관광지 붐빔은 그대로 두되 "추정"을 더 정직하게

관광지 쪽도 실시간 데이터는 아니다 — 집중률(방문자 추이) + 오늘 축제 + 인프라 밀도의 **추정**이다.
이건 관광지에는 말이 되는 추정이니 유지하되, 배지 옆에 **"관광공사 집중률 기준 · 추정"** 을 붙여
근거를 보이게 한다(`crowding-score.ts` 가 이미 `reasons` 배열로 근거 문장을 만들고 있다 — 화면에 내보내면 된다).

### T-R10(나침반 합류)에 미치는 영향

나침반 갈래의 결과 카드에 "한적함(추정)"을 넣기로 했었는데, **같은 원칙으로 뺀다.**
두 갈래 공통 카드는 **성지 · 거리 · 왜 골랐나 · 데이터 한계** 네 칸이 된다. 지시서에 반영했다.

### 완료 조건 (1-8)

1. 고요 속으로 결과 화면에서 **성지 카드에 붐빔 배지·점수가 없다** (스크린샷).
2. 관광지(출발지) 쪽에는 붐빔 배지가 **그대로 있고, 옆에 근거 문장**이 보인다.
3. 화면 어디에도 "조용한 성지" · "한적한 성지" 문구가 없다. "대신 갈 수 있는 근처 성지" 류로 바뀌었다 (ko·en).
4. `alternatives.test.ts` · `crowding-score.test.ts` · `quiet-sites.test.ts` 가 **그대로 통과** (로직을 안 건드렸으므로).
5. `npm run verify` 종료 코드 0.

| 크기 | 사진은 webp · 화면 폭에 맞춰 요청 (9/14 `dc9f1cf` 에서 만든 방식 그대로). 5장 합쳐 500KB 안쪽 |
| 검증 | 375·1280 스크린샷 · 「대」 모드 · 「동작 줄이기」 켜고 자동 넘김이 멈추는지 |

### 언제

**2-3 결정이 난 뒤.** 배포(0-1)하고 동료분이 새 홈을 본 상태에서 "슬라이드를 넣을까"를
피드백 충돌 5건과 함께 정한다. 넣기로 하면 반나절이다 — 사진 고르는 시간이 코드보다 오래 걸린다.

## 하지 않는 것 — 노력 대비 성과가 나쁘거나 규칙에 걸린다

| 무엇 | 왜 |

| **AI 가이드 복원** | 재기획이 내건 조건 넷(출처 표시 · 정확성 검수 · 오류 신고 · 비용 한도)이 하나도 안 갖춰졌다. 성지 역사를 틀리게 답하면 신뢰가 바로 무너진다 — `CLAUDE.md` 3번. 노력 ★★★★, 위험은 그보다 크다 |

## 요약 — 6일을 이렇게 쓴다

1. **오늘**: 배포(0-1 · 0-2 · 0-3). 반나절.
2. **내일**: **카카오 · 구글 로그인 켜기(1-7)** — 콘솔 작업 뒤 실제로 눌러 확인. 배포본으로 시연 시나리오 3개(1-1), 실기기 5가지(1-2).
   로그인이 되면 그때 **베타 테스터께 연락(1-3)** — 카카오로 바로 들어오게.
3. **수**: 고요 속으로 성지 배지 숨기기(1-8, 오전) + AI 냄새 제거 좁은 패스(1-6, 오후). 스크린샷 22장으로 확인 후 푸시(자동 재배포).
4. **목~금**: 0% 교구 사진 1장씩(2-1 — 포토코리아에서 찾는 범위까지만). 2-3 에서 홈 슬라이드(2-5)를 넣기로 했으면 반나절. 남으면 네이버 로그인(2-4).
5. **토**: 제출 자료 · 스크린샷 · 설명서. 새 기능 없음.
6. **제출 후**: 고요 속으로 본 변경(3-7) → 나침반 합류(3-1) → 전면 리디자인(3-6). 3-7 이 먼저인 이유 — 나침반 갈래도 같은 카드를 쓰므로 카드 구조를 먼저 정한다.

**새로 만드는 것은 없다.** 이미 만든 것을 심사위원이 보게 하고, 빈 곳을 메우고, 깨지지 않게 하고, **도구 기본값 냄새를 빼는 것**이 전부다.
6일 동안 가장 위험한 일은 "하나 더 만들다가" 배포·검증을 못 하는 것이다.
