## 인근 붐빔 표시 — 고요 속으로 대신 상세 페이지에 (A-2)

### 왜 자리를 옮기나

초안에서 짚은 문제 — `crowding-score.ts` 의 점수는 **"성지 안에 사람이 얼마나 있나"가 아니라
"성지 주변에 축제 · 명소 · 숙박이 얼마나 있나"** 다. 성지 카드에 「조용」 배지로 붙이면 거짓 주장이 된다.

팀 결정: 숨기지 말고 **정직한 이름으로 정직한 자리에** 둔다. 상세 페이지에서
**"인근 지역이 조용 / 보통 / 붐빔"** — 이건 점수가 실제로 재는 것과 같은 말이다.

### 어떻게

| 항목    | 내용                                                                                                                                |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 자리    | 성지 · 성당 상세 페이지. 방문 정보 근처                                                                                             |
| 문구    | "인근 지역이 **조용**합니다 / **보통** / **붐빕니다**" — 성지가 아니라 **인근 지역**이라고 말한다                                   |
| 근거    | 옆에 작게: "관광공사 집중률 · 오늘 축제 N건 · 주변 관광 인프라 기준 · 추정" — `crowding-score.ts` 가 만드는 `reasons` 배열을 그대로 |
| 데이터  | 상세를 열 때 TourAPI 실시간 호출 (축제 1 + 주변 인프라 1). **저장하지 않는다**                                                      |
| 없을 때 | 좌표 없는 성지(1곳) · API 실패 → "인근 붐빔 정보를 불러오지 못했어요" (더미 금지)                                                   |

### 완료 조건

1. 상세 페이지에 인근 붐빔 문구와 근거가 보인다 (스크린샷 · 조용/보통/붐빔 세 경우 각 1곳).
2. 화면 어디에도 "조용한 **성지**" 류 문구가 없다 — 주어는 항상 "인근 지역".
3. `crowding-score.test.ts` 그대로 통과 (산식 안 건드림).
4. `npm run verify` 종료 코드 0.

## 브랜치 — 기능별로 나누되, 기준은 "같은 파일을 만지느냐"

```text
main            ← 배포본(Vercel 자동 배포). builter 는 9/15 PR #16 으로 여기 합쳐지고 지워졌다
└─ develop      ← 팀 공통 기준(통합) 브랜치. main 에서 새로 판다. 모든 작업 브랜치가 여기서 나가고 여기로 돌아온다
   ├─ feat/compass          A-1 고요 속으로 → 마음나침반
   ├─ feat/nearby-crowding  A-2 상세 인근 붐빔
   ├─ design/tokens         A-3 글꼴·색·반경·라벨
   ├─ design/layout         A-4 더보기·검색창·상세 사진
   ├─ feat/hero-slider      A-5 홈 슬라이드
   └─ data/site-fields      B-2 소요시간·규모 칸 (마이그레이션 + 타입)
```

B-1 · B-3 · B-4 는 **브랜치가 필요 없다** — DB 값만 바꾸는 일이라 코드가 안 변한다. 스크립트가 필요하면 `data/site-fields` 에 같이 넣는다.

### 순서 — 충돌을 피하는 방법

| 순서   | 브랜치                                                                       | 동시에 해도 되는 것                                              | 이유                                                                                  |
| ------ | ---------------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 1      | `design/tokens` **앞 절반** (글꼴·색 — `index.html` · `globals.css` 두 파일) | 전부                                                             | 두 파일뿐이라 아무와도 안 부딪힘. **바로 합친다**                                     |
| 1      | `feat/compass` (A-1)                                                         | `feat/hero-slider` · `data/site-fields` · `feat/nearby-crowding` | 탭·라우터·quiet 화면. 🔴 **`crowding-score.ts` 는 지우지 않는다** — A-2 가 쓴다       |
| 1      | `feat/nearby-crowding` (A-2)                                                 | 위와 같음                                                        | `SiteDetailPage.tsx` 한 곳                                                            |
| 1      | `feat/hero-slider` (A-5)                                                     | 위와 같음                                                        | 홈 히어로 영역만. A-1 이 홈 **카드**를 바꾸니 히어로를 **별도 파일**로 두면 안 부딪힘 |
| 2      | `design/tokens` **뒷 절반** (반경 29개 파일 치환 · 라벨)                     | 없음 — **A-1 합친 뒤 30분 안에 끝내고 바로 합친다**              | 29개 파일을 건드려서 열어 두면 모든 브랜치와 충돌                                     |
| 3      | `design/layout` (A-4)                                                        | `data/site-fields`                                               | `SiteDetailPage`(A-2 뒤) · `MenuPage` · `TopNav`. A-2 · 반경 치환이 합쳐진 뒤 시작    |
| 언제든 | `data/site-fields` (B-2)                                                     | 전부                                                             | 마이그레이션 + `database.ts` — 화면 파일 안 건드림                                    |

### 지킬 것 세 가지

1. **브랜치는 하루 안에 합친다.** 목요일까지 이틀 반이라 오래 열어 두면 합치는 데만 반나절 쓴다. 시작 전 `git pull origin develop` → 브랜치 생성, 끝나면 PR → `develop`.
2. **합치기 전 `npm run verify` 통과** — 브랜치마다 예외 없이.
3. **`main` 은 목요일에 한 번만.** `main` 에 합치는 순간 Vercel 이 배포한다 — 그래서 `develop` 을 따로 둔다. 중간에 `main` 에 올리면 심사위원이 반쯤 바뀐 화면을 본다.

먼저 할 일: `work/rebuild-0914`(9/15 문서·스크립트 수정)를 `main` 으로 PR 해서 합친 뒤 `develop` 을 만들고, 팀원은 거기서 브랜치를 딴다. (문서·스크립트뿐이라 배포돼도 화면은 안 바뀐다.)
