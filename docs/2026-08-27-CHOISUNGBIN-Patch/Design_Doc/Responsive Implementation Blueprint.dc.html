0. 이 문서를 읽는 방법

이 문서는 "지금 무엇이 문제인가 → 어떤 규칙으로 고칠 것인가 → 어떤 순서로 몇 개 파일을 고치는가 → 무엇을 보고 끝났다고 판단하는가"의 네 부분으로 이어집니다. 개발 경험이 없어도 1~5장만 읽으면 결정에 참여할 수 있고, 6장부터가 실제 작업 지시입니다. 낯선 낱말은 12장 용어 사전에 모아 두었습니다.

채택안(2026-09-06 확정): 시안 1b 웹 서비스형을 기본 골격으로, 지도 화면에만 1c 지도 우선 분할을 적용합니다. 1a 사이드 레일은 채택하지 않았습니다. 이에 따라 Phase 1~2(셸·홈)와 Phase 3의 탐색, Phase 5의 지도는 이미 실제 코드로 작성되어 프로젝트에 들어 있습니다 — 레포와 같은 경로의 src/… 파일과 적용 안내 PATCH-README.md를 그대로 덮어쓰면 됩니다. 아래 6장 Phase 1의 코드 예시는 1a 기준으로 쓰인 것이므로, 실제 구현은 패치 파일을 기준으로 보십시오. 2~5장의 원칙·브레이크포인트·3겹 구조와 7장 이후의 작업 목록·검수·위험은 채택안에서도 그대로 유효합니다.

1. 지금 상태 진단

현재 앱이 데스크톱에서 좁은 기둥으로 보이는 원인은 화면마다 흩어져 있지 않습니다. 딱 두 파일에 모여 있습니다.

src/app/layouts/AppLayout.tsx

바깥을 bg-gray-200로 칠하고 본문을 max-w-lg(512px)로 가운데 고정합니다. 넓은 화면에서는 max-w-4xl(896px)로 한 단계 넓어질 뿐이라, 1920px 모니터에서도 화면의 절반 이상이 회색 여백입니다. 즉 "데스크톱 대응"이 아니라 "휴대폰 화면을 크게 보여주기"입니다.

src/app/layouts/BottomNav.tsx

하단 탭이 셸과 같은 widthClass를 받아 폭을 맞춥니다. 셸의 폭 규칙을 바꾸면 이 파일도 함께 바뀌어야 합니다 — 두 파일은 한 쌍입니다.

반가운 사실이 하나 있습니다. 화면 폭을 판단하는 장치가 이미 들어 있습니다. src/shared/i18n/SettingsProvider.tsx는 (min-width: 1024px) 미디어 쿼리를 감시해 wideView 값을 제공하고, 창 크기 변경과 기기 회전에도 따라 바뀝니다. 새로 만들 필요가 없고, 기준선 1024px도 이미 정해져 있습니다.

그 밖의 화면 파일들(src/pages/*.tsx)은 대부분 px-6, grid-cols-2처럼 폭이 고정된 값을 쓰고 있습니다. 이것들은 부수고 다시 만드는 대상이 아니라, 앞에 브레이크포인트 접두사를 붙여 늘려 주는 대상입니다. 카드 컴포넌트(SiteGridCard, CourseCardItem, SiteListItem)는 이미 부모 폭을 따라 늘어나는 구조라 손대지 않습니다.

2. 다섯 가지 원칙

이 다섯 줄이 이후 모든 판단의 기준입니다. 애매한 상황이 오면 여기로 돌아옵니다.

  1. 모바일이 기준값이다. 지금 동작하는 모바일 화면이 기본이고, 데스크톱은 lg: 이상에서 덧붙이는 예외입니다. 기존 클래스를 지우지 않고 앞에 조건을 붙입니다. 이렇게 하면 모바일 회귀 위험이 거의 없습니다.
  2. 화면 하나, 컴포넌트 하나. 같은 화면을 데스크톱용·모바일용 두 파일로 나누지 않습니다. 두 벌이 되면 문구 수정이 한쪽에만 반영되는 사고가 반드시 생깁니다. 예외는 지도 화면 하나뿐이고, 그때도 목록 항목 컴포넌트는 공유합니다.
  3. 모양은 CSS로, 동작만 JS로. 열 개수·여백·표시 여부는 Tailwind 브레이크포인트로 처리합니다. wideView는 "데스크톱에서는 시트 대신 옆 패널로 연다"처럼 동작이 달라질 때만 씁니다. CSS로 되는 일을 JS로 하면 첫 화면이 한 번 깜빡입니다.
  4. 토큰은 고정한다. 색·서체·모서리 반경은 src/shared/styles/globals.css의 값을 그대로 씁니다. 이 작업에서 새 색을 만들지 않습니다. 반응형 작업과 리디자인을 섞으면 무엇이 문제를 일으켰는지 알 수 없게 됩니다.
  5. 접근성은 폭과 무관하다. 큰 글자 모드(html[data-text-size=lg], 118%)와 한/영 전환은 모든 폭에서 깨지지 않아야 합니다. 118%에서 글자가 두 줄로 늘어날 자리를 미리 비워 둡니다.

3. 브레이크포인트 규격

Tailwind 기본값을 그대로 씁니다. 새 브레이크포인트를 만들지 않습니다. 각 구간이 "무엇을 위한 폭인가"를 아래처럼 한 문장으로 못 박아 두면, 앞으로 새 화면을 만들 때 매번 다시 상의할 필요가 없습니다.

4. 세 겹으로 나눈 레이아웃

반응형 작업이 손에 잡히지 않는 이유는 "어디를 고쳐야 하는가"가 흐릿하기 때문입니다. 책임을 세 겹으로 나누면 각 파일이 무엇을 결정하는지가 분명해집니다. 아래 순서대로 위에서 아래로만 영향이 흐르고, 반대 방향은 없습니다.

1겹 · 셸 (Shell)

화면 전체의 뼈대. 내비게이션을 어디에 둘지, 본문 영역이 얼마나 넓은지를 결정합니다. 담당 파일: AppLayout.tsx, BottomNav.tsx, 신규 SideRail.tsx. 페이지 내용은 전혀 모릅니다.

2겹 · 페이지 (Page)

셸이 준 폭 안에서 블록을 배치합니다. 몇 열로 나눌지, 어느 블록을 우측 열로 보낼지가 여기서 결정됩니다. 담당 파일: src/pages/*.tsx 14개.

3겹 · 컴포넌트 (Component)

카드·목록 항목·버튼. 자기 폭을 스스로 정하지 않고 부모가 준 칸을 채웁니다. 이미 그렇게 되어 있으므로 이번 작업에서 거의 손대지 않습니다. 담당 파일: src/features/**/components/*.tsx.

이 구분이 곧 작업 순서입니다. 셸을 먼저 고쳐 넓은 캔버스를 확보하고, 그다음 페이지가 그 캔버스를 채우게 합니다. 순서를 뒤집으면 페이지를 두 번 고치게 됩니다.

5. 데스크톱에서 무엇이 달라 보이는가

넓어진 자리에 무엇을 넣을지의 답은 "모바일에서 스크롤을 내려야 보이던 것을 한눈에 보이게 한다"입니다. 새 기능을 만들지 않습니다. 구체적으로 세 가지가 달라집니다.

  1. 내비게이션이 항상 보인다. 하단 탭 5개(홈·지도·탐색·기록·더보기)가 좌측 236px 레일로 올라가고, 그 아래에 순례 여권 진행률(0/208)이 상주합니다. 스탬프가 늘어나는 것을 언제나 볼 수 있게 하는 것이 이 앱의 재방문 동력입니다.
  2. 보조 정보가 옆으로 간다. 홈에서 아래쪽에 있던 AI 가이드 미카엘·오늘의 쉼표·바로 가기 칩이 우측 300px 열로 이동해 스크롤과 함께 따라옵니다. 본문 피드는 히어로와 코스 카드에만 집중합니다.
  3. 목록과 지도를 동시에 본다. 지도 화면만 좌측 452px 목록 + 우측 지도의 2분할이 됩니다. 순례 계획은 결국 "어디서 어디로"의 문제이고, 이것이 모바일로는 만들 수 없는 유일한 가치입니다.

6. 단계별 구현 순서

각 단계는 그 자체로 배포 가능한 상태로 끝납니다. 중간에 멈춰도 앱이 깨지지 않고, 한 단계씩 검증하며 나아갈 수 있습니다. 소요는 1인 기준 추정입니다.

Phase 0 · 준비 (0.5일)

코드를 고치기 전에 세 가지를 확정합니다. 3장의 브레이크포인트 표를 팀 합의로 승인하고, 본문 최대 폭 1200px을 확정하고, 현재 모바일 화면 다섯 개(홈·지도·탐색·기록·성지 상세)를 390px 폭에서 캡처해 둡니다. 마지막 캡처가 "모바일이 변하지 않았다"를 증명하는 유일한 근거가 됩니다.

Phase 1 · 셸 교체 (1일)

이 단계가 전체 작업의 절반입니다. 파일 세 개만 다룹니다. 가짜 휴대폰 액자(bg-gray-200 + md:shadow-2xl)를 없애고, 1024px 이상에서 좌측 레일이 있는 2열 골격으로 바꿉니다.

{{ codeAppLayout }}

그림 1. 셸 교체 후 AppLayout. wideView로 클래스를 고르던 부분이 사라지고 CSS가 판단합니다.

이어서 BottomNav.tsx에서 widthClass 프롭을 제거하고 폭을 스스로 고정합니다 — fixed bottom-0 left-1/2 w-full max-w-lg -translate-x-1/2 lg:hidden. 탭 5개의 터치 영역은 세로 70px을 유지합니다(44px 최소 기준 충족).

신규 src/app/layouts/SideRail.tsx는 BottomNav의 탭 배열을 그대로 재사용합니다. 두 곳에 같은 배열을 복사하지 말고, 탭 정의를 src/app/layouts/nav-items.ts로 뽑아 양쪽이 같은 출처를 읽게 합니다. 탭을 하나 추가할 때 한 곳만 고치면 되도록 만드는 것이 이 파일 분리의 목적입니다.

{{ codeSideRail }}

그림 2. SideRail 골격. 활성 배경색은 BottomNav와 동일한 규칙(brand-blue, 탐색 탭만 brand-violet 원형)을 유지합니다.

이 단계가 끝나면 아직 홈 화면 내용은 좁은 채로 왼쪽에 붙어 있습니다. 정상입니다 — Phase 2에서 채웁니다. 여기서 반드시 확인할 것: 390px에서 화면이 Phase 0 캡처와 픽셀 단위로 같아야 합니다.

Phase 2 · 홈 화면 (1일)

src/pages/HomePage.tsx는 현재 섹션이 위에서 아래로 한 줄로 쌓여 있습니다. 이 순서를 유지한 채 컨테이너로 감싸고, 보조 섹션 세 개만 우측 열로 옮깁니다. JSX 순서를 바꾸면 모바일 순서도 함께 바뀌므로, 우측으로 보낼 블록은 모바일에서도 지금과 같은 위치가 되도록 그리드 배치(xl:col-start-2 xl:row-start-1)로 옮깁니다.

{{ codeHome }}

그림 3. 홈 2열 구조. 모바일에서 aside는 그냥 본문 아래에 이어지는 블록입니다.

헤더도 이 단계에서 손댑니다. 모바일의 sticky 검색 헤더는 데스크톱에서 상단 바가 되어 검색창(최대 520px)·큰 글자·KO/EN·로그인을 한 줄에 놓습니다. 로고는 레일로 옮겨졌으니 데스크톱 헤더에서는 감춥니다(lg:hidden).

Phase 3 · 목록 화면들 (1.5일)

탐색·검색·기록·메뉴·붐빔 피하기·축제·순례 코스·시·도 랜딩. 여덟 화면이지만 작업은 같은 두 줄의 반복이라 빠릅니다. ① 최상위를 공통 컨테이너로 감싸고 ② 격자 클래스에 브레이크포인트를 붙입니다. 같은 문자열을 여덟 번 쓰지 않도록 src/shared/components/ui/PageContainer.tsx를 하나 만들어 mx-auto w-full max-w-[1200px] px-6 lg:px-8를 담습니다.

마음 나침반이 예외인 이유를 기억해 두는 것이 중요합니다. 한 번에 한 질문에 답하는 화면은 넓힐수록 나빠집니다. "넓은 화면이니까 다 채운다"가 아니라 "채울 이유가 있는 것만 채운다"가 이 작업의 태도입니다.

Phase 4 · 성지 상세 (1일)

SiteDetailPage.tsx는 38KB로 가장 큰 파일이고, 사진·도슨트·미사 시간·주변 관광지·스탬프·순례자 사진이 한 줄로 쌓여 있습니다. 데스크톱에서는 좌측 본문(이야기·도슨트·순례자 사진) + 우측 380px 정보 패널(주소·미사 시간·스탬프 버튼·길찾기)로 나눕니다. 우측 패널은 xl:sticky xl:top-6으로 고정해, 긴 이야기를 읽는 동안에도 "가는 방법"이 늘 눈에 있게 합니다.

이 화면은 하단 탭이 없는 전체 화면 라우트입니다(router.tsx 참고). 데스크톱에서도 레일 없이 뜨면 길을 잃으므로, 이 단계에서 상세 라우트를 AppLayout 자녀로 옮길지 결정해야 합니다. 권장: 옮긴다. 모바일은 지금처럼 전체 화면(레일은 어차피 hidden)이고, 데스크톱만 레일을 얻습니다.

Phase 5 · 지도 2분할 (2~3일)

가장 값이 크고 비용도 큰 단계입니다. 현재 MapPage.tsx는 지도 → 선택 카드 → 교구 진행 → 검색 → 목록이 세로로 이어집니다. 1024px 이상에서 이 흐름을 좌우로 접습니다.

그림 4. 지도 2분할. 선택 상태(selectedId)는 이미 MapPage에 있으므로, 목록과 지도가 그 하나를 함께 읽게 하는 것이 작업의 핵심입니다.

1024px 미만은 현재 코드를 그대로 씁니다. 조건부 렌더링으로 두 구조를 분기하지 말고, 같은 JSX가 CSS로만 접히게 만드는 것이 유지 비용을 낮추는 길입니다.

8. 검수 방법

각 단계가 끝날 때마다 아래 일곱 폭에서 다섯 화면을 봅니다. 브라우저 개발자 도구의 반응형 모드에서 폭만 바꿔 가며 확인하면 됩니다. 판단 기준은 단순합니다 — 가로 스크롤이 생기지 않고, 글자가 잘리지 않고, 누를 것이 44px보다 작지 않으면 통과입니다.

주의 · Capacitor 네이티브 앱

Android·iOS 빌드는 휴대폰 폭에서 실행되므로 lg: 규칙이 절대 켜지지 않습니다. 즉 이 작업은 네이티브 앱을 바꾸지 않습니다. 대신 태블릿 앱(iPad, 안드로이드 태블릿)에서는 켜집니다. 하단 탭이 사라진 자리에 레일이 제대로 나오는지 태블릿 실기기에서 한 번은 확인해야 합니다. 아이패드 가로는 1024px을 넘습니다.

10. 완료 기준

아래 여덟 줄이 모두 참이면 이 작업은 끝난 것입니다.

  • 320~1920px 어느 폭에서도 가로 스크롤이 생기지 않는다.
  • 390px 화면이 작업 전 캡처와 같다.
  • 1024px 이상에서 좌측 레일이 상주하고 하단 탭은 보이지 않는다.
  • 1280px 이상에서 홈이 2열이고 우측 열이 스크롤을 따라온다.
  • 본문이 1200px를 넘게 늘어나는 화면이 없다(지도 제외).
  • 큰 글자 모드와 영어 전환에서 잘리는 글자가 없다.
  • iPad 가로에서 레일이 정상 동작한다.
  • npm run verify(타입·린트·테스트)가 통과한다.

11. 시안 파일과의 대응

이 설계도와 함께 제공되는 시안 파일 세 개는 각각 데스크톱 1280 + 모바일 390 한 쌍과 "적용 방법" 표를 담고 있습니다. Option 1c Map Split이 Phase 5의 목표 화면입니다. Option 1b Top Nav Web이 채택안이며 Phase 1~2의 목표 화면입니다. Option 1a Side Rail은 채택하지 않은 대안으로 남깁니다. 시안의 색·간격·모서리 값은 저장소 토큰에서 그대로 가져온 것이므로, 구현 중 값이 궁금할 때는 시안 파일의 해당 요소를 열어 확인하면 됩니다.
