# ADR 0002. TourAPI 는 실시간 호출만 하고 저장하지 않는다

- 날짜: 2026-08-04
- 상태: 채택 (강제 사항)

## 맥락

2026 관광데이터 활용 공모전은 한국관광공사 OpenAPI(TourAPI) 활용이 필수 요건이고,
"실시간 활용"을 핵심으로 본다. 응답을 DB에 저장해두고 재사용하는 방식은 실격 위험이 있다.

동시에 우리 앱에는 성능·오프라인 요구도 있다. 산간 성지가 많아 통신이 불안정하다.
두 요구가 충돌하는 것처럼 보이지만, 실은 **데이터 출처가 다르다**.

## 결정

데이터를 두 갈래로 명확히 나눈다.

|            | 우리 데이터                             | 남의 데이터              |
| ---------- | --------------------------------------- | ------------------------ |
| 무엇       | `holy_sites` 195곳 (직접 수집·큐레이션) | TourAPI 주변 관광지·축제 |
| 저장       | 자유롭게 저장·캐싱                      | **금지**                 |
| 서비스워커 | 런타임 캐시 대상                        | 캐시 대상에서 제외       |
| 코드 위치  | `features/*/api/*.repository.ts`        | `shared/api/tour-api.ts` |

`shared/api/tour-api.ts` 의 함수들은 결과를 어디에도 저장하지 않는다.
`vite.config.ts` 의 workbox `runtimeCaching` 도 Supabase `holy_sites` 요청만 대상으로 한다.

## 아직 정리하지 못한 것

`data/research/image_sourcing_*.sql` 로 `holy_sites.image_url` 에 넣은 이미지 중 일부가
`tong.visitkorea.or.kr` (한국관광공사) 주소다. 엄밀히 보면 TourAPI 유래 데이터를 저장한 셈이다.
제출 전에 다음 중 하나로 정리해야 한다.

1. 직접 촬영한 사진으로 교체한다 (권장 — 콘텐츠 전략상으로도 이게 맞다)
2. 상세 페이지에서 매번 실시간으로 이미지를 조회한다
3. 이미지 없이 대체 표시(⛪)로 둔다

## 파생 효과

TourAPI 를 상세 페이지 195곳 + 축제 정보까지 확장하면 호출량이 크게 는다.
인증키 일일 한도를 먼저 확인하고, 필요하면 "짧은 TTL 서버 프록시 + 레이트 리밋" 정도는
실시간성을 해치지 않는 선에서 검토한다.
