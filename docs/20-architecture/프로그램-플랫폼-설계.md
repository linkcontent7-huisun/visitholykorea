# 프로그램 플랫폼 설계 — 전국 성지에서 일어나는 일을 한 화면에

> 2026-08-27. 사용자가 정한 방향을 제품 설계로 옮긴 문서다.
> 기존 CRD([`제품요구사항과-기술아키텍처.md`](제품요구사항과-기술아키텍처.md))에
> **없던 축**이므로 따로 둔다.

---

## 1. 무엇을 만들려는가

> **"전국 성지에서 일어나는, 그리고 지역별로 성당·가톨릭 기관에서 일어나는 일들을
> 한 번의 클릭으로 비지트홀리코리아에서 확인하게 하고 싶다."**

지금 앱은 **장소**를 다룬다. 성지가 어디 있고 무엇이 있었는지.
앞으로는 **그 장소에서 열리는 일**을 다룬다.

### 진입이 양방향이다 — 이게 설계의 핵심

| 방향 | 사용자의 상황 |
| --- | --- |
| **장소 → 프로그램** | 순례를 가기로 했다. **가는 김에** 그곳에서 뭘 하는지 본다 |
| **프로그램 → 장소** | 프로그램이 마음에 든다. **그것 때문에** 순례를 시작한다 |

두 번째 방향이 새롭다. 지금 앱에는 없다.
그리고 이쪽이 **실사용자 1명** 문제를 푸는 열쇠다 —
"조용한 성지"는 이미 순례를 다니는 사람에게만 닿지만,
"이번 주말 대전에서 초 만들기 체험"은 순례를 안 다니던 사람에게도 닿는다.

---

## 2. 참고한 두 곳

### 문화상상연구소 — 하고 싶은 사업 모델

사회적기업. 지역의 여러 장소를 빌려 프로그램을 만들어 운영한다.
「둘러보공 놀아보세」로 **문화재청 2022 지역문화재 활용 우수사업 우수상**.

**주목할 것은 상이 아니라 「놀토」다.**
`mynolto.com` — *"내 손안의 역사가이드"*. 체험학습을 **예약**하고 명소 정보를
받는 앱·웹을 직접 운영한다. 즉 이 회사는 **프로그램 운영자이면서 동시에
프로그램 플랫폼**이다.

> 우리가 따라야 할 것은 프로그램 하나가 아니라 **그 구조**다.
> 다만 우리 장소는 지역 문화재가 아니라 **가톨릭 성지·성당·기관**이다.

### 왜관 — 전국으로 넓히고 싶은 원형

**성 베네딕도 문화영성센터** (경북 칠곡군 왜관읍 관문로 61 · 010-6791-0071 · osb.or.kr)

| 시기 | 프로그램 |
| --- | --- |
| 상시 | 그리스도교 영성 배우기 피정 |
| **전례 시기** | **전례피정** — 성모승천 · 성탄 · 부활 |
| 5~11월 | 한티 가는 길 · 군위 사유원 문화 피정 · 가을 문화 피정 |
| 여름 | 수도 생활 배움 피정 |
| 6~9월 | 평화 학교 |

### 🔴 여기서 나온 발견 — 프로그램이 전례력을 따라 돈다

왜관 프로그램의 축이 **전례력**이다. 성모승천·성탄·부활에 맞춰 열린다.

**그리고 우리 앱에는 이미 전례력 한정판 스탬프가 있다.**
장소·프로그램·스탬프가 **같은 축**으로 묶인다는 뜻이다.
계절 필터를 따로 만들 필요가 없다 — 전례력이 이미 그 역할을 한다.

이것은 네이버 지도나 트리플이 절대 못 하는 분류다.
**우리만 가질 수 있는 축이다.**

## 3. 데이터가 결정적으로 다르다

| | 출처 | 저장 |
| --- | --- | --- |
| 맛집·숙박·관광지 | TourAPI | **금지** (ADR 0002) |
| 성지 208곳 | 자체 수집 | 자유 |
| **프로그램** | **자체 수집 + 기관 등록** | **자유** |
| **등록 업장** | **업주가 직접 입력** | **자유** |

[`고객정의_역할지도_ICP.md`](../10-product/고객정의_역할지도_ICP.md) 가
스스로를 **"얇은 래퍼"** 라고 비판했다. TourAPI 를 감싸기만 해서는 남의 데이터
위에 얹힌 화면일 뿐이라는 뜻이다.

**프로그램 데이터가 그 비판에 대한 답이다.**
우리가 모은 것이므로 저장·검색·캐싱·통계가 전부 자유롭고,
TourAPI 가 끊겨도 남는다. 경쟁자가 베끼려면 같은 발품을 팔아야 한다.

## 4. 데이터 모델

### `programs` — 성지·성당·기관에서 열리는 일

```sql
create table public.programs (
  id            uuid primary key default gen_random_uuid(),

  -- 어디서 — 성지이거나(연결), 성지가 아닌 기관이거나(직접 입력)
  site_id       uuid references public.holy_sites(id) on delete set null,
  place_name    text not null,          -- "성 베네딕도 문화영성센터"
  diocese       text,                   -- 지역별 보기의 축
  region_province text,
  address       text,
  lat           double precision,
  lng           double precision,

  -- 무엇을
  title         text not null,
  summary       text,
  kind          text not null,          -- 피정 · 체험 · 공연 · 강의 · 미사 · 축제
  liturgical_season text,               -- 대림 · 성탄 · 사순 · 부활 · 연중  ← 우리만의 축

  -- 언제 — 일회성과 반복을 함께 담는다
  starts_at     timestamptz,
  ends_at       timestamptz,
  recurrence    text,                   -- "매월 첫 토요일" 같은 사람이 읽는 문장
  duration_label text,                  -- 반나절 · 당일 · 1박2일  ← 당일 체류 73.7%

  -- 참여
  capacity      int,
  fee_label     text,                   -- 금액이 아니라 문장. "무료" "1인 3만원" "문의"
  booking_url   text,
  phone         text,

  -- 출처와 신뢰
  source        text not null,          -- 'staff' | 'partner' | 'public'
  verified_at   timestamptz,            -- 사람이 확인한 시각. 없으면 화면에 "확인 전" 표시
  created_at    timestamptz not null default now()
);
```

**설계에서 지킨 것**

- `fee_label` 을 **금액이 아니라 문장**으로 둔다. 밀레마니 체험비를 아직 모르는데
  숫자 칸을 만들면 누군가 추측으로 채운다. 문장이면 "문의"라고 쓸 수 있다
- `verified_at` 이 비면 화면에 **"확인 전"** 을 표시한다. 틀린 정보를 사실처럼
  보이게 하지 않는다 — 붐빔 지수를 추정이라고 밝히는 것과 같은 원칙이다
- `site_id` 는 **nullable** 이다. 대전 도심 클러스터처럼 성지가 아닌 가톨릭 기관에서
  열리는 일도 담아야 한다

### `partner_places` — 업주가 직접 등록하는 업장

```sql
create table public.partner_places (
  id            uuid primary key default gen_random_uuid(),
  owner_id      uuid references auth.users(id) on delete set null,

  name          text not null,
  kind          text not null,          -- 식당 · 숙소 · 카페 · 공방 · 기념품
  address       text,
  lat           double precision,
  lng           double precision,
  phone         text,
  intro         text,                   -- 업주가 쓰는 소개
  image_url     text,

  -- 검수 — 등록했다고 바로 노출되지 않는다
  status        text not null default 'pending',  -- pending | approved | rejected
  reviewed_at   timestamptz,
  reject_reason text,

  created_at    timestamptz not null default now()
);
```

**왜 검수를 두는가** — 성지 옆에 아무 광고나 붙으면 그 성지의 격이 떨어진다.
이 앱의 자산은 신뢰다. 등록은 열되 노출은 닫는다.

## 5. 화면

### F16. 프로그램 목록 — `/programs`

**한 번의 클릭**이라는 요구를 만족시키는 화면이다.

- 기본은 **오늘 이후, 가까운 순**
- 필터: 지역(교구·시도) · 시기(**전례력**) · 유형 · 소요시간(반나절/당일/1박2일)
- 각 카드에서 바로 → 성지 상세 / 예약 링크 / 전화

### F17. 성지 상세 안의 "여기서 열리는 일"

장소 → 프로그램 방향. 기존 성지 상세에 구획 하나를 더한다.
`site_id` 로 연결된 프로그램 + 반경 안 기관의 프로그램.

### F18. 업장 등록 — `/partner`

업주가 스스로 등록한다. 로그인 → 입력 → 검수 대기 → 승인 후 노출.
**승인 전에는 지도에도 목록에도 나오지 않는다.**

### F19. 일정 담기 (검토 필요)

성지 + 프로그램 + 맛집·숙소를 담아 하루 일정으로 만든다.

> 🔴 **제약이 하나 있다.** TourAPI 응답(맛집·숙소)은 **저장할 수 없다**(ADR 0002).
> 일정을 DB 에 저장하려면 TourAPI 항목을 빼거나, `contentid` 만 두고 열 때마다
> 실시간 재조회해야 한다. **후자가 규정 위반인지 아닌지는 확인이 필요하다.**
> 확인 전까지는 **세션 안에서만 유지하고 저장하지 않는다.**

## 6. 어디서 데이터를 얻는가

| 경로 | 무엇 | 비용 |
| --- | --- | --- |
| ① 직접 수집 | 왜관·밀레마니·금산 등 알려진 곳 | 발품. 전화 두 통이 이미 병목 |
| ② 기관 등록 | 본당·수도회가 직접 올림 | 관계가 먼저 필요 |
| ③ 업주 등록 | 개인 영업자 (F18) | 검수 인력 |
| ④ 교구 주보·홈페이지 | 공개된 일정 | 수집 자동화 여지 |

**①로 시작한다.** 프로그램이 0건인 화면을 먼저 만들면 안 된다 —
더미를 두지 않는다는 원칙에 걸린다. **왜관 한 곳이라도 실제로 채운 뒤에 화면을 연다.**

## 7. 이것이 사업계획서에 주는 것

| 지금 계획서의 약한 곳 | 이 설계가 답하는 것 |
| --- | --- |
| "얇은 래퍼" 자기비판 | 자체 데이터를 갖는다. TourAPI 가 끊겨도 남는다 |
| 수익 모델이 프로그램 운영 하나 | **플랫폼 수수료·등록비**가 생긴다 |
| 파트너십이 "협의 중" | 기관이 **등록하는 자리**가 제품 안에 있다 |
| 실사용자 1명 | 프로그램은 순례 안 다니던 사람에게도 닿는다 |
| 경쟁 우위가 휴리스틱 | **전례력 축**은 지도앱이 못 만든다 |

## 8. 마감 전에 할 것 — 아무것도 없다

**공모전 마감(9/21 확인 필요) 전에는 이 설계를 구현하지 않는다.**

지금 가장 큰 위험은 여전히 **사진 169곳**과 **실사용자 1명**이고,
심사 기준이 "개발 완료된 완성 서비스"다.
프로그램 데이터가 비어 있는 새 화면을 여는 것은 위험을 키우는 일이다.

**대신 사업계획서에는 쓴다.** 설계가 이 정도로 구체적이면
"앞으로 하겠다"가 아니라 "이렇게 할 것이다"가 된다.

### 순서

1. 마감 전 — 계획서에 반영. 왜관·밀레마니에 전화(이미 병목으로 잡혀 있다)
2. 마감 후 — `programs` 마이그레이션 + 왜관 실데이터 채우기
3. 그다음 — `/programs` 화면
4. 관계가 생기면 — `partner_places` 와 검수
