# 1부. 제품 요구사항

## 1.1 한 문장

**모든 여행 서비스가 "인기순"을 보여줄 때, 같은 공공 데이터로
"오늘 비어 있는 곳"을 계산해 지친 사람에게 건네는 순례 웹앱.**

한국 가톨릭 성지 208곳을 다룬다. 웹·Android·iOS 를 한 코드베이스로 지원한다.

## 1.2 누구의 무슨 문제인가

| 사용자 | 문제 | 이 앱이 하는 일 |
| --- | --- | --- |
| 지친 성인 | 쉴 곳을 찾는데 유명한 곳은 붐빈다 | 오늘 한산한 성지를 계산해 보여준다 |
| 순례를 계획하는 신자 | 어디로 갈지, 문은 열려 있는지 모른다 | 208곳의 위치·소개·주변 본당·미사 시간 안내 |
| 성당에 온 비신자 | 건축·성상·스테인드글라스의 뜻을 모른다 | 도슨트 해설 (조사 체계 완성, 콘텐츠 축적 단계) |

**검증되지 않은 전제** — 위 네 가지는 아직 사용자에게 확인받지 못했다.
실사용자가 1명(개발자 본인)이다. 확인용 설문이 `docs/30-content-ops/2026-08-27-교인-수요조사-설문.md` 에 준비돼 있다.

### 미구현을 화면에 어떻게 표시하는가

**더미 데이터를 두지 않는다.** 가짜 핀·가짜 카운트·목업 카드를 만들지 않고,
미구현 영역은 "준비 중"임을 사용자에게 정직하게 표시한다.
심사 대상이 "개발 완료된 완성 서비스"로 한정되기 때문이기도 하지만,
그보다 한 번 들키면 나머지 화면의 진짜 데이터까지 의심받기 때문이다.

## 1.5 제약 — 어기면 서비스가 무너지는 것들

### C1. TourAPI 응답을 저장하지 않는다 🔴

한국관광공사 OpenAPI 응답은 매 요청 실시간으로 호출해야 하며,
DB 나 서비스워커 캐시에 넣어 재사용하면 **공모전 실격 위험**이 있다.

반면 `holy_sites` 는 우리가 직접 수집한 자체 데이터이므로 얼마든지
저장·캐싱해도 된다. **이 구분을 흐리지 말 것.** (ADR 0002)

### C2. 비밀 키를 클라이언트에 두지 않는다 🔴

`VITE_` 접두사가 붙은 값은 브라우저 번들에 그대로 들어간다.
Gemini API 키처럼 감춰야 하는 값은 Supabase Edge Function 시크릿으로 넣고,
앱은 함수를 호출한다. (ADR 0004)

### C3. AI 답변을 성지 DB 안으로 제한한다 🔴

종교 성지의 역사·전례 정보는 틀리면 신뢰가 바로 무너진다.
`supabase/functions/ai-guide` 는 질문과 관련된 성지 레코드를 컨텍스트로 넣고
**"컨텍스트에 없으면 모른다고 답하라"**를 시스템 프롬프트에 못 박아 두었다.
이 장치를 걷어내지 말 것.

### C4. AI 가 그린 성지 사진을 넣지 않는다 🔴

2026-08-27 결정. 2차적저작물이라 저작권이 안 풀리고, 무엇보다
**AI 가 그린 배티 순교성지는 배티 순교성지가 아니다.**
**사진이 없는 편이 가짜 사진보다 낫다.**

## 2.2 코드 구조 규칙

### 의존성 방향은 한쪽으로만

```
pages → features → shared
```

역방향 import 금지. 화면이 늘어나도 도메인 로직이 화면에 끌려다니지 않게 하려는 것이다.

### 경계에서만 변환한다

DB 행(snake_case) ↔ 도메인 타입(camelCase) 변환은 각 feature 의
`api/*.repository.ts` 안에서만 한다. **화면 컴포넌트가 `supabase` 클라이언트를
직접 부르지 않는다.**

### 단일 출처를 만든다

| 흩어지기 쉬운 것 | 모아둔 곳 |
| --- | --- |
| 라우트 경로 문자열 | `src/app/routes/paths.ts` |
| TanStack Query 캐시 키 | `src/shared/api/query-keys.ts` |
| 붐빔 산식 상수 | `src/features/quiet/api/crowding-score.ts` |
| 17개 시·도와 중심 좌표 | `src/shared/lib/regions.ts` |

캐시 키를 문자열로 흩어 놓으면 무효화 대상을 놓치기 쉬워서 계층 구조로 관리한다.

### features 목록

`ai-guide` `auth` `courses` `favorites` `map` `passport`
`quiet` `records` `rest` `routes` `sites`

## 2.4 붐빔 지수 산식 — 공개해도 되는 값들

TourAPI 에는 실시간 혼잡도가 없다. 그래서 공사가 주는 데이터
(오늘 열리는 축제·행사, 주변 관광 인프라 밀도)로 **붐빔을 추정**한다.
추정이라는 점을 숨기지 않는 대신, 산식을 한 파일에 모아 누구나 검증할 수 있게 뒀다.

### 세 축, 합계 100점

| 축 | 최대 | 반경 | 포화상수 k | 왜 |
| --- | --- | --- | --- | --- |
| 오늘의 축제·행사 | 50 | 15km | 1 | 그날의 붐빔을 가장 크게 좌우한다. 광역에서 사람을 끌어온다 |
| 주변 명소 밀도 | 30 | 3km | 8 | 축제가 없어도 상시 사람이 있는 정도 |
| 음식점·숙박 밀도 | 20 | 3km | 12 | 머무는 사람의 규모를 대신 보여주는 값 |

### 포화 곡선

```
score = max × (1 − e^(−value / k))
```

처음 몇 개가 붐빔을 크게 올리고, 이미 붐비는 곳에서는 몇 개 더 늘어도
체감이 크지 않다는 성질을 반영한다. 상한을 넘지 않는 것도 보장된다.

### 설계상 지킨 것

- **`crowding-score.ts` 에는 API 호출이 없다.** 순수 계산만 있어서 테스트로 고정된다.
  실제 조회와 조립은 `quiet-sites.ts` 가 한다.
- 화면에 **"공사 데이터에는 실시간 혼잡도가 없어, 오늘 열리는 행사와 주변 관광
  시설 밀도로 추정한 값입니다. 실제와 다를 수 있어요."** 를 항상 띄운다.

### 고쳐진 버그 (기록)

- **대체 추천이 등급을 안 낮추던 문제** — 경복궁(95.4점, 매우붐빔) 대신
  행주산성(76.5점, 역시 매우붐빔)을 권하고 있었다. 점수가 아니라 **등급을 먼저**
  비교하도록 고쳤다.
- **코스 페어링이 성지를 피해 성지로 보내던 문제** — TourAPI 주변 검색이
  가톨릭 시설까지 반환해서 생겼다.

## 2.5 TourAPI 취급

- **저장 금지** (C1). DB·서비스워커 캐시 어디에도 넣지 않는다.
- **동시 호출 제한** — 각 화면이 `Promise.all` 로 묶어 쏘기 때문에 막지 않으면
  20개가 거의 동시에 나가 에러코드 23 이 뜬다. 세마포어로 4개까지만 통과시킨다.
- **디바운스** — `/alternatives` 검색은 300ms.
- 운영계정 신청 URL: `https://visitholykorea-app.vercel.app` (승인 약 1주일)

## 3.2 남은 위험 — 큰 순서

### R1. 사진 169곳이 비어 있다 🔴

심사 기준이 "개발 완료된 완성 서비스"인데 열에 여덟은 빈 껍데기다.

### R2. 실사용자가 0에 가깝다 🔴

제품 가설이 하나도 검증되지 않았다. 설문이 준비돼 있으나 미발송.

### R3. 김범우 유배지가 두 곳으로 적혀 있다 🔴

DB 에 유배·선종지가 단양(원주교구)과 밀양(부산교구) 두 개로 있고 서로 아니라고 말한다.
**이제 영어로도 나가므로 앱이 두 언어로 자기를 반박한다.** 교구 확인 필요.

### R4. TourAPI 키 등급이 확인되지 않았다

~~운영계정 미신청~~ — **신청·발급 완료됐다** (사용자 확인 2026-08-20).
2026-08-27 에 발급 키로 실제 호출해 `resultCode 0000 / OK` 를 확인했다.

남은 것은 **등급 확인** 하나다. 개발계정과 운영계정은 API 응답이 같아서
호출만으로는 구분되지 않는다. 일일 한도가 1,000건이면 홈 화면 1회 로드가
21건이므로 **하루 45회 접속에서 서비스가 멈춘다.** 100,000건이면 약 4,545회다.
공공데이터포털 마이페이지에서 확인해야 한다.

### R5. 서비스 롤 키 손상

Edge Function 배포에는 필요하다.
