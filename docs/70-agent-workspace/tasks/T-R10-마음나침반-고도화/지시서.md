## Problem — 지금 무엇이 잘못됐나

### 문제 1. 8문항을 묻고 답 1개만 쓴다

`src/features/courses/components/HealingQuiz.tsx` 234줄:

```ts
const courses = await getRecommendedCourses(emotion, undefined, 1, originCoords, language);
```

퀴즈가 모으는 답은 여덟이다 — `emotion` · `concern` · `region` · `gender` · `style` ·
`timeBudget` · `party` · `note`. 추천을 바꾸는 것은 **`emotion` 하나**와 출발 좌표뿐이다.
나머지 여섯은 묻고 기록에 남기지만 **결과를 바꾸지 않는다.**

**이것이 2026-09-14 재기획에서 나침반이 내려간 이유다.** 재기획 132줄은 8문항을
"성지 찾기 조건으로 흡수"한다고 적었다 — 8문항을 물어도 결과가 감정 하나로 정해진다면
그 판단은 **지금 코드 기준으로 옳다.** 화면만 되살리면 같은 지적이 다시 나온다.

사용자 입장에서는 이렇게 보인다 — **여덟 번 답했는데 결과가 그만큼 나를 아는 것 같지 않다.**

### 🔴 문제 2. 추천이 데이터를 감당하지 못한다 (2026-09-14 SOLOMON 실측)

이쪽이 더 심각하다. **지금 추천은 "당신에게 맞는 곳"이라고 말할 근거가 없다.**

성지 데이터·추천 정보는 틀리면 신뢰가 바로 무너지는 영역이다. 근거 없는 추천에
근거 문장까지 붙이면 **틀렸다는 사실만 더 잘 드러난다.** 아래 넷을 먼저 고쳐야 한다.

## 실측 — 무엇을 어떻게 쟀나

2026-09-14 SOLOMON 이 코드와 DB 스냅샷(`data/archive/2026-08-supabase/snapshot_kaahuo_2026-08-10.json`,
208행)에서 직접 확인했다. **추측이 아니다.**

### ① 추천 후보가 전체가 아니다 — 여섯 곳만 본다

```
HealingQuiz                limit = 1
  → getRecommendedCourses    limit × 2 = 2
    → fetchCandidateSites      limit × 3 = 6
      → DB:  .eq('emotion_tag', 감정).limit(6)      ← 🔴 정렬 조건이 없다
```

「위로」를 고른 사람의 후보는 **61곳 중 6곳**이다. 나머지 55곳은 후보에도 들지 못한다.

더 나쁜 것은 `holy-sites.repository.ts` 157줄에 **`ORDER BY` 가 없다**는 점이다.
어떤 6곳이 올지 DB 가 보장하지 않는다 — **같은 답을 넣어도 결과가 달라질 수 있고,
어떤 성지는 영영 추천되지 않을 수 있다.**

### ② 감정 태그가 성지당 하나뿐이고, 분포가 기울어 있다

| 감정            | 성지 수 | 비율      |
| --------------- | ------- | --------- |
| 위로            | 61      | 29.3%     |
| 치유            | 45      | 21.6%     |
| 평온            | 44      | 21.2%     |
| 감사            | 33      | 15.9%     |
| **새출발**      | **21**  | **10.1%** |
| **(비어 있음)** | **4**   | 1.9%      |

절두산은 `치유` 로 고정돼 있다(마이그레이션 `20260807000000` 24줄). 그런데 순교성지는
위로도 되고 감사도 된다. **성지 하나에 감정 하나**는 "이 성지는 오직 이 감정"이라는
주장인데 근거가 없다.

그리고 「새출발」을 고른 사람은 늘 **21곳 안에서만** 받는다.
태그가 빈 **4곳은 어떤 감정으로도 추천되지 않는다** — 조용한 배제다.

### ③ 정렬 기준이 「적합도」가 아니라 「설명 길이」다

`course-matching.ts` 의 `contentQualityScore` 는 `description` 길이 + `history`·`seoTitle`·
`nearbyLodging` 존재 여부로 점수를 매긴다. **우리가 글을 많이 써둔 곳이 1등으로 올라온다.**
사용자가 무엇이라 답했는지와 상관이 없다.

### 🔴 ④ 근거를 보여주려 해도 댈 데이터가 없다

| 근거로 쓰고 싶은 것           | DB 에 있나         |
| ----------------------------- | ------------------ |
| 방문 소요 시간                | **칸 자체가 없다** |
| 실내/실외                     | **없다**           |
| 규모 (혼자 조용히 vs 넓은 곳) | **없다**           |
| 좌표 (거리 계산)              | 207 / 208 ✓        |
| 교구 · 분류                   | 208 / 208 ✓        |
| 감정 태그                     | 204 / 208          |

**"두 시간이면 충분한 곳" · "혼자 머물기 좋은 곳" — 이런 문장을 뒷받침할 값이 하나도 없다.**
지금 데이터로 그런 근거를 쓰면 **거짓말이 된다.**

## Goal — 무엇이 되면 끝인가

1. **묻는 만큼 결과가 달라진다.**
2. **추천 근거를 말하되, 데이터가 감당하는 것만 말한다.**
3. **고요 속으로 안에서 한 흐름이 된다** — 진입점을 늘리지 않고, 결과 카드도 같은 형식.

화면을 되살리는 것이 목표가 아니다. 되살릴 값어치를 만드는 것이 목표다.

## User Value — 누구의 무슨 문제를 푸는가

이 브랜치에는 성지를 찾는 길이 셋이고, **셋이 겹치지 않는다.** 나침반은 그중 고요 속으로의
한 갈래로 들어간다.

| 화면                                                     | 누구를 위한 것                                                                                     |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `/search` 성지 찾기                                      | **조건을 아는 사람** — 교구·행정지역·방문 목적·이동 조건                                           |
| `/quiet` 고요 속으로 · 「장소 검색」 갈래                | **목적지가 이미 있는 사람** — 가려던 관광지가 붐빌 때의 대안 (지금 그대로)                         |
| `/quiet` 고요 속으로 · **「아직 정하지 못했어요」 갈래** | **어디 갈지 모르는 사람** — 조건이 아니라 마음 상태로 묻는다. **옛 마음 나침반이 여기로 들어온다** |

나침반이 맡는 사람은 **"성지에 가고 싶은데 어디로 갈지 모르겠는" 사람**이다.
그 사람은 교구도 모르고 목적지도 없다. 조건을 묻는 화면은 그를 돕지 못한다.

주 사용자는 50대 이상 순례자다. 조건을 골라 좁혀가는 방식보다 **묻는 말에 답하면
안내받는 방식**이 이 연령대에 부담이 적다.

### 왜 독립 화면이 아니라 고요 속으로에 합치는가 (2026-09-15 결정)

| 이유                       | 뜻                                                                                                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **재기획과 싸우지 않는다** | 재기획 132줄이 나침반을 내린 이유가 "성지 찾기 조건으로 흡수"다. 고요 속으로의 갈래로 넣는 건 그 결정의 **연장**이지 번복이 아니다. 동료(2dion)의 T-R04 를 뒤집지 않는다 |
| **진입점이 늘지 않는다**   | 재기획이 홈 「오늘의 쉼표」를 뺀 이유가 중복 진입점이었다. 탭도 홈도 그대로                                                                                              |
| **약점을 강점이 메운다**   | 나침반의 문제는 "근거 없이 추천"이고, `QuietPage` 는 이미 **추천 근거 · 거리 · 데이터 한계**를 같이 보여준다. 결과를 같은 카드로 내면 R3 이 저절로 충족된다              |
| **공모전 서사가 한 화면**  | "붐빔(관광데이터) × 마음(우리 데이터)" — 지정과제와 차별점이 한 흐름. 시연도 한 번                                                                                       |
| **문항이 줄어든다**        | 8문항 → 마음 상태 하나 + 출발지 + 시간 여유 정도. R2 의 "못 쓸 문항은 빼라"가 자연히 이뤄진다                                                                            |

합쳐진 흐름의 초안:

```
고요 속으로
  "어디로 가실 생각이세요?"
   ├─ [장소·지역 검색]        → 붐빔 예상 → 주변 한적한 성지          ← 지금 그대로, 손대지 않는다
   └─ [아직 정하지 못했어요]   → 마음 상태 하나 (위로·새출발·평온·치유·감사)
                                 + 출발지 · 시간 여유
                              → 그 마음에 맞는 성지 중 출발지에서 가까운 곳
결과 카드는 두 갈래 공통: 성지 · 거리 · 왜 골랐나 · 데이터 한계
```

🔴 **성지에 붐빔·한적함을 표시하지 않는다 (2026-09-15 결정).** TourAPI 붐빔 데이터는 관광지 기준이지 성지 기준이 아니다 —
성지 점수는 "성지 주변에 축제·명소가 얼마나 있나"일 뿐 성지 안 사람 수가 아니다. 그래서 고요 속으로 전체가
**붐빔은 관광지에만, 성지는 "대신 갈 곳"** 으로 바뀐다 (`docs/DSH/2026-09-15-노력-대비-성과-우선순위.md` 「고요 속으로 — 붐빔은 관광지에만」 절).
나침반 갈래도 같은 원칙이다. 결과 카드에 한적함 칸이 없다.

## Requirements — 우선순위 순

### 🔴 P0 — 신뢰도. 코드만으로 되고, 지금 당장 가능하다

#### R1 추천 후보를 전체로 넓힌다

`.limit()` 으로 후보를 자르는 구조를 없앤다. 해당 감정에 맞는 **성지 전체**를 후보로 받아
점수를 매긴다. 208곳 전체라도 한 번에 받을 만한 크기다(다른 화면에서 이미 전체 조회를 한다).

정렬 조건 없는 `limit` 을 남겨두지 않는다. **어떤 성지도 "DB 가 늦게 돌려줘서" 배제되면 안 된다.**

#### R2 사용자의 답이 순위를 정하게 한다

정렬 1순위를 **사용자 답 기준 적합도**로 바꾼다. `contentQualityScore`(설명 길이)는
**동점 처리용 보조**로 내린다. 지금은 이것이 1순위라 답과 무관한 결과가 나온다.

여덟 문항 각각에 대해 **"이 답이 순위를 어떻게 바꾸는가"를 정의하고 구현한다.**
정의할 수 없거나 근거가 약한 문항은 **질문에서 뺀다.**

- 🔴 **`gender`(성별)는 빼는 쪽을 먼저 검토한다.** 결과에 쓸 근거를 대지 못하면
  **묻지 않는다.** 쓰지도 않을 개인정보를 묻는 것은 그 자체로 문제다.
  쓸 근거가 있다면 그 근거를 `설계.md` 에 적고 남긴다.
- 질문 수를 여덟으로 유지하는 것은 목표가 아니다. **다섯 문항이 전부 순위를 바꾸는 편이,
  여덟 중 하나만 쓰이는 것보다 낫다.**
- ⚠️ 지금 DB 에 없는 값(소요 시간·규모·실내외)을 **추정해서 점수에 쓰지 않는다.**
  쓸 수 있는 것은 거리·교구·분류·감정뿐이다. 그 범위에서 정의한다.

#### R3 근거는 있는 값으로만 쓰고, 말의 수위를 데이터에 맞춘다

결과 카드에 **어떻게 골랐는지 한 줄**을 넣는다. 단 **위 ④ 표에서 "있다"로 표시된 것만** 쓴다.

- 좋은 예: "위로 · 서울에서 12km · 순교성지"
- 🔴 나쁜 예: "두 시간이면 충분한 곳" · "혼자 머물기 좋은 곳" — **뒷받침할 데이터가 없다**
- 표현 수위를 낮춘다. **"당신에게 딱 맞는 곳"이 아니라 "이렇게 골랐습니다"** 로.
  과장하지 않으면 결과가 안 맞아도 신뢰가 깨지지 않는다.
- `/quiet` 이 이미 추천 근거와 **데이터의 한계**를 같이 보여준다(`QuietPage.tsx` 머리말 4·7번).
  나침반도 같은 수준이어야 한다 — 근거가 약하면 약하다고 말한다.

#### R4 결과 수 고정을 없앤다

`getRecommendedCourses(..., 1, ...)` 의 `1` 을 없앤다. 시간 여유가 있는 사람에게는 여러 곳을,
짧은 사람에게는 한 곳을.

### P1

#### R5 고요 속으로에 두 번째 갈래를 만든다

`/quiet` 첫 화면에 갈림길 하나를 둔다 — **「장소·지역 검색」 / 「아직 정하지 못했어요」**.
두 번째를 고르면 마음 상태(5개 중 하나) + 출발지 + 시간 여유를 묻고, R1~R4 로 고친 엔진이
고른 성지를 **「장소 검색」 갈래와 같은 결과 카드**로 보여준다.

- **R1~R4 를 먼저 한다.** 엔진이 믿을 만해지기 전에 갈래를 열지 않는다.
- **「장소 검색」 갈래의 동작은 한 줄도 바꾸지 않는다.** 공모전 대표 기능이다. 갈래를 더하는
  것이지 고치는 것이 아니다 — 기존 흐름의 회귀 테스트가 그대로 통과해야 한다.
- 결과 카드에 **성지 붐빔·한적함을 넣지 않는다** (위 🔴). 카드는 성지 · 거리 · 왜 골랐나 · 데이터 한계 네 칸.
- 갈림길 문구는 50대 이상이 한 번에 이해할 말로. "마음 나침반"이라는 이름을 화면에 쓸지는
  설계에서 정한다 — 이름보다 "무엇을 묻는지"가 먼저 보여야 한다.
- `/compass` 는 안내 페이지 대신 **`/quiet` 의 두 번째 갈래로 리다이렉트**한다. 밖에 퍼진 링크가
  죽지 않게.
- `features/courses/` 의 퀴즈 화면(`HealingQuiz.tsx`)은 그대로 되살리지 않는다. 문항이 2~3 개로
  줄었으니 고요 속으로의 화면 문법에 맞춰 **새로 짧게** 만든다. 엔진(`course-matching.ts`)만 재사용.

동료(2dion)에게 알린다 — 이건 T-R04 를 뒤집는 게 아니라 **"성지 찾기 조건으로 흡수"를
고요 속으로에서 완성하는 것**이다. 합의보다는 공유에 가깝지만, 대표 기능 화면을 건드리므로
착수 전에 한 번 말한다.

- **`/search`(성지 찾기)는 건드리지 않는다.**
- **`/quiet` 의 「장소 검색」 갈래는 동작을 바꾸지 않는다.** 갈래 하나를 _더하는_ 것이지
  기존 흐름을 고치는 것이 아니다. 대표 기능이므로 회귀가 있으면 안 된다.
- **홈·하단 탭에 나침반 입구를 따로 만들지 않는다.** 진입은 고요 속으로 안에서만.
- **AI 가이드(`/ai-guide`)를 되살리지 않는다.** 별개 사안이고, 재기획이 내건 조건
  (출처 표시·정확성 검수·오류 신고·비용 한도)이 아직 갖춰지지 않았다.
- **새 DB 테이블·새 칸을 만들지 않는다.** 위 R6~R8 참고.
- **🔴 TourAPI 응답을 저장하지 않는다.** 매 요청 실시간 호출이어야 한다.
  DB·서비스워커 캐시에 넣으면 공모전 실격 위험이다 (`docs/20-architecture/adr/0002-tourapi-usage.md`).
  코스 매칭이 TourAPI 로 도보권 관광지를 페어링하므로 **이 작업에서 특히 조심한다.**
- **홈 화면에서 TourAPI 를 부르지 않는다.** 재기획 131줄이 "홈 로드마다 TourAPI 7회 호출"을
  문제로 지적해 홈 섹션을 뺐다. 나침반은 **나침반 화면 안에서만** 부른다.
- **없는 값을 추정해 채우지 않는다.** 소요 시간·규모를 설명 길이나 분류로 유추하지 않는다.
  추정값으로 만든 근거는 근거가 아니다.

## 완료 조건 — 무엇을 어떻게 확인하는가

"코드에 있으니 됐다"는 근거가 아니다. **실제로 돌려 본 것**을 `개발기록.md` 에 적는다.

1. **후보가 전체다.** 감정 하나를 골랐을 때 후보 수가 그 감정의 성지 수와 같다
   (위로면 61곳). 정렬 조건 없는 `limit` 이 코드에 남아 있지 않다.
2. **같은 답 → 같은 결과.** 같은 입력으로 여러 번 돌려 결과가 흔들리지 않는다. 테스트로 확인한다.
3. **묻는 문항 수 = 순위에 쓰이는 문항 수.** `설계.md` 에 문항별로 "순위를 어떻게 바꾸는가"가
   적혀 있고 코드가 그대로다. 빼기로 한 문항은 화면에서 사라졌다.
4. **같은 감정 + 다른 시간 여유 → 다른 결과.** 같은 감정 + 다른 동행도 마찬가지. 테스트로 확인한다.
5. **근거 문장에 DB 에 없는 값이 들어가지 않는다.** 소요 시간·규모·실내외를 주장하는 문구가
   화면 어디에도 없다. 화면을 열어 눈으로 확인하고 스크린샷을 남긴다.
6. **새로 넣은 문구가 한국어·영어 둘 다 있다.** 이 브랜치 언어 정책은 검수된 ko/en 만
   노출이다(`LanguagePicker` 테스트). es·fr·pt·it 는 검수 전이라 숨김 — 채우지 않아도 된다.
7. **`npm run verify` 통과.** 출력만 보지 말고 **종료 코드 `0`** 을 확인한다
   (2026-09-08 에 출력만 보고 통과로 착각한 사고가 있었다).
8. **기존 테스트가 깨지지 않는다.** 착수 시점 기준 **377개 통과 / 파일 45개**
   (2026-09-15 실측). 이보다 줄면 안 된다.
9. **고요 속으로 「장소 검색」 갈래가 전과 똑같이 돈다.** 갈래를 더하기 전 스크린샷과 더한 뒤
   스크린샷을 나란히 두고 비교한다. `use-alternatives` 테스트가 그대로 통과한다.
10. **두 갈래의 결과 카드가 같은 형식이다.** 성지 · 거리 · 왜 골랐나 · 데이터 한계 —
    네 칸이 두 갈래 모두에 있다. 스크린샷으로 확인한다.
11. **성지 카드 어디에도 붐빔·한적 배지나 점수가 없다.** 화면을 열어 눈으로 확인한다.
12. **`/compass` 로 들어오면 `/quiet` 두 번째 갈래로 간다.** 주소를 직접 쳐서 확인한다.
13. **묻는 문항이 3개 이하다.** 마음 상태 · 출발지 · 시간 여유. 그 이상 묻는다면 왜인지 `설계.md` 에 근거가 있다.
