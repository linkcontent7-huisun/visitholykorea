# 조사 기록 — T-002 화면 단순화

## 확인 방법 (먼저 밝힘)

`npm run dev` 를 띄워 375px 폭에서 실제로 보지 못했다 — 코드만 읽고 판단했다.
`확인 못 함`으로 표시한 항목은 실제 화면에서 다시 봐야 한다.
아래 "블록 순서"는 각 페이지 `.tsx` 파일을 위에서 아래로 읽은 JSX 렌더 순서다.

---

## 우선순위 (문제 심한 순)

1. **SiteDetailPage** — 세로로 쌓인 구획이 12~16개. 압도적으로 가장 심하다.
2. **MenuPage** — 개수 문제가 아니라 **눌러도 아무 일도 안 나는 버튼 4개**가
   화면에 그대로 떠 있다. `CLAUDE.md` "더미 데이터·작동 안 하는 버튼 금지"
   위반이라 스크롤 문제보다 먼저 고쳐야 한다.
3. RecordsPage(스탬프 탭) — 여권 카드 안에 버튼 2개가 나란히 쌓여 있다.
4. MapPage — 구획 수는 많지만 지도+목록형 화면 특성상 크게 무리는 아니다.
5. ExplorePage — 대체로 괜찮다. 교구 그리드가 15개라 많아 보이지만 "메뉴/색인"
   성격이라 억지로 줄이지 않아도 된다.
6. CompassPage — 이미 좋다. 손댈 것 없음.

## SiteDetailPage.tsx (성지 상세) — 우선순위 1

### 1. 블록 순서 (위→아래)

1. 히어로 이미지 (뒤로가기·찜하기 버튼, 카테고리·WYD 태그, 이름, 주소, 감성태그)
2. "기본 정보" — 주소 카드 + 교구/감성태그 카드 (2칸 그리드)
3. "성지 이야기" — 오디오 도슨트 플레이어(챕터 선택) + 소개 인용문 + 역사 본문
4. "가는 김에 둘러볼 곳" — TourAPI 주변 시설, 그룹별 가로 스크롤 카드 (조건부)
5. "지금 근처에서 열리는 행사" — TourAPI 축제 목록 (조건부)
6. 스탬프 안내 문구(오늘 찍으면 어떤 잉크인지) + "순례 스탬프 찍기" 버튼
7. "오늘 그곳은 어땠나요?" 한 줄 입력창 (스탬프 찍은 후, 아직 한 줄 없을 때만)
8. 내가 남긴 한 줄 + 사진 올리기 (스탬프 찍은 후)
9. "순례자 이야기" — 다른 사람이 남긴 한 줄·사진·신고 버튼 (조건부)
10. VisitEtiquette (들어가기 전 안내)
11. DirectionsCard (찾아가는 길)
12. ContactCard (문의)
13. BarrierFreeCard (무장애 정보, 조건부)
14. NearbyParishesCard (주변 본당)
15. "순례 스탬프 카드 공유하기" 버튼 (스탬프 찍은 후)
16. "○○교구의 다른 성지" 가로 스크롤 카드

조건부를 다 걷어내도(둘러볼 곳·행사·무장애정보·순례자이야기가 없는 성지) 최소
11개 구획이 남는다. 조건이 다 걸리는 인기 성지(WYD 성지 등)는 16개까지 쌓인다.

### 2. 한 번에 판단해야 할 것

- 2번 섹션까지는 정보만 있고 판단은 없다.
- 3번(도슨트)에서 챕터 선택이 판단 1개.
- 4번은 그룹마다(맛집/볼거리/숙박) 카드가 여러 장 — 훑어봐야 할 항목 수는
  많지만 "선택"은 아니고 "구경"이다. 다만 섹션 자체가 있는지 없는지부터
  스크롤해서 확인해야 한다.
- 6번 스탬프 버튼 — 이 페이지의 진짜 주인공. 그런데 시각적으로는 3·4·5·9·10·
  11·12·13·14 섹션과 **똑같은 굵기의 제목**(보라 세로줄 + h2)을 달고 있어서
  "이게 제일 중요한 행동"이라는 신호가 약하다.
- 7·8번은 스탬프 찍은 사람만 보지만, 입력창+사진 업로드+신고 버튼까지 겹치면
  판단 항목이 순식간에 늘어난다.
- 15번(공유) 버튼은 6번(스탬프) 버튼과 기능이 이어져 있는데 화면에서는
  9칸 이상 떨어져 있다 — 스탬프를 막 찍은 사람이 공유하려면 다시 스크롤해야
  할 수 있다(찍은 직후엔 화면 위쪽에 있으니 아래로 내려야 공유 버튼이 나옴).

### 3. 개선 제안 (억지로 넣지 않고, 구체적으로만)

- **주인공을 스탬프 찍기로 고정한다.** 6번 섹션을 3번(성지 이야기) 바로 다음,
  4·5번(주변 정보) 앞으로 옮기거나, 최소한 시각적으로 다른 섹션과 다르게
  (더 크게, 배경색을 넣어) 구분한다. 지금은 12번째 스크롤에 나오는
  ContactCard와 똑같은 무게다.
- **정보성 섹션(4·5·10·11·12·13·14)을 접이식(아코디언)이나 탭으로 묶는다.**
  "가는 김에 둘러볼 곳 / 찾아가는 길 / 문의 / 무장애 정보 / 주변 본당"은
  전부 "이 성지를 실제로 방문할 때 필요한 정보"로 한 그룹이다. 지금처럼
  각각 독립 섹션·독립 제목으로 펼쳐두지 않고 "방문 정보 더 보기" 아래
  묶으면 스크롤 길이가 절반 가까이 줄어든다.
- **"기본 정보"(2번)의 주소는 DirectionsCard·hero 부제와 내용이 겹친다.**
  같은 주소가 화면에 3번 나온다(히어로 부제, 기본정보 카드, 찾아가는 길
  카드). 하나로 합치거나 기본정보 카드를 없애고 교구/감성태그만 태그 형태로
  히어로에 붙이는 방법이 있다.
- **공유 버튼(15번)을 스탬프 버튼(6번) 바로 옆/아래로 옮긴다.** 스탬프를
  찍은 직후의 다음 행동이 "공유"인데 지금은 사이에 방문정보 섹션들이 껴 있다.

### 4. 확인이 필요한 것 (판단 보류)

- "성지 이야기" 도슨트와 "가는 김에 둘러볼 곳"을 접이식으로 묶으면 도슨트
  오디오 재생 상태(재생 중 접힘 등)와 충돌하는지 `DocentPlayer` 컴포넌트
  내부를 더 봐야 한다 — 이번 조사에서는 열지 않았다.
- 방문 정보를 묶는 안이 "성지마다 있는 정보가 다르다"(무장애 정보는 조건부)
  는 사실과 부딪히는지, 즉 접었을 때 "무엇이 있는지" 미리보기가 필요한지는
  사장님 판단이 필요하다.

## MenuPage.tsx (더보기/메뉴) — 우선순위 2

### 1. 블록 순서

1. 프로필 카드 (이름, 로그인 버튼 또는 인사말, 방문 성지 수·여행기 수)
2. "계정 설정" 섹션 — 내 프로필 (로그인 필요)
3. "앱 설정" 섹션 — 언어(select), 큰 글자 모드(토글), 출발지(select), 일반 설정
4. "이용 안내" 섹션 — 서비스 소개, 고객센터, 앱 공유하기
5. 로그아웃/로그인 버튼

### 2. 한 번에 판단해야 할 것

목록형 설정 화면이라 "한 화면에 쌓인 판단"은 원래 많지 않다 (설정 화면은
원래 이런 형태가 맞다). 대신 **더 심각한 문제**를 발견했다.

`MenuPage.tsx:120,126-128` 의 다음 4개 항목은 `MenuItem.onClick` 이
정의돼 있지 않다:

```
{ id: 'settings', icon: Settings, label: t('generalSettings') },          // 120행
{ id: 'intro', icon: Info, label: t('aboutService'), ... },               // 126행
{ id: 'help', icon: ShieldQuestion, label: t('customerSupport'), ... },   // 127행
{ id: 'share', icon: Share2, label: t('shareApp') },                      // 128행
```

렌더 코드(212~227행)를 보면 `item.control` 이 없는 항목은 버튼이 되고,
클릭하면 `item.onClick?.()` 을 부르는데 위 4개는 `onClick` 자체가 없다 —
**눌러도 아무 반응이 없다.** 오른쪽에 화살표(`ChevronRight`)까지 붙어 있어
"누르면 어딘가로 간다"는 신호를 주는데 실제로는 안 간다.

이건 "화면에 판단거리가 많다"는 문제가 아니라 `CLAUDE.md` 의
"작동하지 않는 버튼을 보여주지 않는다(더미 UI 금지)" 규칙 위반이다.
줄이기 전에 먼저 고쳐야 할 항목으로 본다.

### 3. 개선 제안

- 4개 중 실제로 화면/기능이 있는 것은 연결하고, 없는 것은 "준비 중" 배지를
  붙이거나 목록에서 뺀다 (CLAUDE.md 더미 데이터 규칙과 동일한 논리).
- 이건 디자인만으로 끝낼 수 없다 — `onClick` 을 채우려면 대상 화면/링크가
  있어야 하므로 developer 몫이거나, 최소한 "무엇을 만들지" 결정이 먼저다.

### 4. 확인이 필요한 것

- `일반 설정`(`settings`) · `서비스 소개`(`intro`) · `고객센터`(`help`) ·
  `앱 공유하기`(`share`) 각각을 어디로 연결할지(전용 화면을 새로 만들 것인지,
  기존 화면이 있는지) 사장님/오케스트레이터 판단이 필요하다. 코드 전체를
  뒤져 대응하는 라우트가 있는지는 이번 조사 범위 밖이라 확인 못 함.

## RecordsPage.tsx (기록) — 우선순위 3

### 1. 블록 순서

**로그인 전:** 헤더 → 안내(EmptyState) → 로그인 버튼 → 안내 문구 → 지도/성지
둘러보기 링크 2개. (구성 단순, 문제 없음)

**로그인 후 — 여행기 탭:** 헤더+탭 → 여행기 작성 버튼(또는 작성 폼) →
여행기 카드 목록(또는 빈 상태). 단순하다. 문제 없음.

**로그인 후 — 스탬프 탭:**
1. 여권 요약 카드(그라디언트) — 스탬프 수, 진행바, 등급, 다음 등급까지 남은
   수, **"순례 인증서 다운로드" 버튼**, **"나의 순례 별자리 카드 만들기"
   버튼** (둘 다 조건부지만 스탬프가 있으면 거의 항상 뜬다)
2. "교구별 순례 진행" 카드 — 교구 목록 + 각 진행바 + 완주한 교구마다
   **"○○ 완주 카드 만들기" 버튼**
3. 스탬프 그리드(3열) 또는 빈 여권 미리보기

### 2. 한 번에 판단해야 할 것

- 여권 카드 하나에 버튼이 최대 2개(인증서 다운로드·별자리 카드) 나란히
  쌓여 있다. 둘 다 "카드/문서를 만들어 공유"하는 목적이 비슷해서 굳이
  버튼 2개로 나눌 필요가 있는지 의문이다.
- 완주한 교구가 여럿이면 "○○ 완주 카드 만들기" 링크가 교구 수만큼
  반복된다 — 완주 교구가 3~4개면 판단거리가 그만큼 늘어난다.
- 정작 이 화면의 "주인공"인 스탬프 그리드(3번)는 버튼 2개+진행 카드를
  다 지나야 나온다.

### 3. 개선 제안

- 인증서 다운로드와 별자리 카드 버튼을 하나의 "내 순례 기록 내보내기"
  같은 진입점으로 합치고, 누르면 선택지를 보여주는 방식을 검토할 만하다.
  다만 두 기능이 정확히 뭐가 다른지(인증서=등급 증명, 별자리=시각화 지도)
  사용자 조사 없이 합치면 오히려 헷갈릴 수 있어 **억지로 합치라고
  결론 내리지는 않는다.**
- 완주 교구 카드 만들기 버튼은 교구 목록 항목 안에 작은 링크로 이미
  절제되어 있다(각 항목 아래 텍스트 링크 하나뿐) — 이 부분은 괜찮다.

### 4. 확인이 필요한 것

- 인증서 다운로드 vs 별자리 카드, 두 기능을 실제로 얼마나 쓰는지(사용
  로그) 확인 못 함 — 통합 여부는 데이터 없이 결정하지 않는 게 낫다.

## MapPage.tsx (지도) — 우선순위 4

### 1. 블록 순서

1. 헤더 + 진행률 문구 + 넛지 배너(조건부, "거의 다 채운 교구" 안내)
2. 전국 지도(NationalMap) + 범례(MapLegend)
3. 선택한 핀 상세 카드(조건부) — 방문 표시 버튼 + "자세히" 링크
4. "교구별 진행" 목록(DioceseProgressList) — 교구 15개, 누르면 필터
5. 검색창
6. 필터 해제 칩(조건부, 교구를 골랐을 때만)
7. 성지 목록(필터링된 리스트, 나머지 전부)

### 2. 한 번에 판단해야 할 것

- 지도+범례는 "구경"이라 판단이 아니다.
- 3번 카드가 뜨면 그 안에서 판단 2개(방문 표시 / 자세히 보기) — 적절한 양.
- 4번 교구 목록은 15개 버튼이 세로로 쭉 나열된다. ExplorePage 의 3열 그리드와
  달리 여기는 1열 리스트로 보여서(코드상 `DioceseProgressList` 내부 레이아웃은
  확인 못 함 — 컴포넌트를 열어보지 않았다) 세로 길이를 많이 차지할 가능성이
  있다.
- 검색창 + 목록은 지도 화면 아래 "보조 목록"인데, 이미 지도에 다 나온
  정보를 텍스트로 다시 나열하는 구조다. 지도가 안 뜨는 상황(느린 기기,
  스크립트 실패)의 대안이라는 목적은 코드 주석에 이미 적혀 있어 이해된다.

### 3. 개선 제안

- 성지 목록(7번)을 기본은 접어두고 "검색어를 입력했을 때만" 또는 "목록으로
  보기" 토글을 눌렀을 때만 펼치는 방법을 검토할 만하다 — 지도가 이미
  주인공이므로 그 아래 208곳 전체를 매번 다 그릴 필요가 없어 보인다.
  다만 목록이 "지도가 안 될 때의 대안"이라는 설계 의도와 충돌할 수 있어
  **결론은 사장님 판단으로 남긴다.**
- 그 외에는 지도 화면 특성상(개요→상세→목록) 구조가 자연스러워서 억지로
  줄이지 않아도 된다고 본다.

### 4. 확인이 필요한 것

## ExplorePage.tsx (탐색) — 우선순위 5

- 교구를 고른 후는 카테고리 5개 + 정렬 2개 = 최대 7개 선택지가 한 화면에

  얼마나 눌리는지는 실제 화면에서 봐야 한다(확인 못 함).

### 4. 확인이 필요한 것

- 큰 글자 모드에서 교구 그리드 3열이 깨지지 않는지 375px 화면에서
  직접 확인 못 함.
