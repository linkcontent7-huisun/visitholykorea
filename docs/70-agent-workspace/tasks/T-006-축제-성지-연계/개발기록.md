### 판단한 것 (지시서가 정하지 않아 내가 고른 것)

1. **붐빔 배지를 성지별 추가 API 없이 낸다.** 붐빔 피하기는 성지마다 주변 인프라를 1회씩 더
   부르는데, 그러면 완료 조건 6(호출 수가 성지 수에 비례하지 않는다)과 정면으로 부딪힌다.
   그래서 이미 받아 둔 전국 축제 목록만으로 계산한 **축제 압력 축만** 쓰고, 그 사실이
   배지에 「일부」로 드러나게 두었다(`isPartial`). 추정을 숨기지 않는다는 기존 원칙 그대로다.
2. **시·도 칩은 17개를 항상 그린다.** 결과가 있는 지역만 그리는 쪽도 만들어 봤지만,
   완료 조건 4가 "성지 없는 시·도를 실제로 만들어 빈 화면을 확인하라"고 요구하므로
   0건인 지역도 고를 수 있어야 한다. 지시서의 "17개 시·도 칩"과도 그쪽이 맞는다.
3. **칩 라벨의 지역 이름은 한국어 그대로.** 시·도 이름은 화면 문구가 아니라 데이터이고,
   기존 화면(`RegionLandingPage`·`MenuPage`·`HealingQuiz`)도 `REGIONS` 를 그대로 보여준다.
   지역명 6개 국어 표기는 이 작업 범위 밖이라 손대지 않았다.
4. **주소에서 시·도를 못 읽은 축제**는 '전체'에는 나오지만 특정 시·도를 고르면 빠진다.
   다른 지역일 수 있는 것을 그 지역 목록에 섞는 것보다 낫다고 봤다(실측에서는 72건 모두 읽혔다).
5. **정렬은 "가장 가까운 성지까지의 거리" 오름차순.** 이 화면의 값어치는 축제 인기가 아니라
   "여기서 성지가 정말 가깝다"이므로 그 값으로 줄을 세웠다.
6. **홈 칩 줄을 `grid-cols-2` → `grid-cols-3` 으로 바꿨다.** 칩 하나를 더하려면 불가피했고,
   칩 자체의 생김새(테두리·모서리·아이콘·글자 크기)는 기존 두 칩과 똑같이 맞췄다.

### 확인 못 한 것

- **실기기 확인 못 함.** 헤드리스 Chrome 375px 로만 봤다. 아이폰 사파리의 가로 스크롤 관성이나
  실제 터치 크기는 확인하지 못했다.
- **하루 한도(코드 22) 상황의 화면을 실제로 만들어 보지 못했다.** 오류 화면은 일반 오류 문구
  하나로만 처리했다(`festivalsError` + `festivalsErrorHint`). 붐빔 화면처럼 한도 초과를
  따로 안내하는 것은 지시서에 없어 넣지 않았다 — 아래 「제안」에 적어 둔다.
- **다른 에이전트와의 파일 충돌 위험 한 가지.** 사전 검사(조건 7)를 하려고
  `src/shared/i18n/dictionary.ts` 를 백업했다가 되돌렸다(22:33경, 약 2분 사이).
  그 사이 다른 세션이 같은 파일을 고쳤다면 그 변경이 지워졌을 수 있다.
  되돌린 뒤 `git diff` 로 확인한 결과 이 파일의 변경분은 **내가 넣은 축제 키 98줄뿐**이었고,
  이후 `npm run verify` 도 통과했다(없는 키를 부르는 코드가 있었다면 타입 검사에서 걸렸다).
  그래도 지시자가 커밋 전에 이 파일을 한 번 훑어봐 주면 좋겠다.

### 제안 (범위 밖이라 하지 않음)

- 성지 상세(`SiteDetailPage`)에서 반대 방향으로 "이 성지 근처에 오늘 열리는 축제"를 보여주면
  한 쌍이 완성된다. 지시서에 "다음 작업"이라고 적혀 있으니 그대로 남겨 둔다.
- 한도 초과(TourApiError 코드 22)일 때 "잠시 후" 문구로 갈라 주는 처리
  (`isQuotaExceededError` 가 이미 있다. `TodayQuietSection` 과 같은 방식).
- 축제 카드에 `firstimage`(축제 사진)를 쓰면 카드가 살아나는데, TourAPI 이미지는 저장하지
  않는 원칙과 표시 규칙을 먼저 정리해야 해서 이번에는 넣지 않았다(도메인 타입엔 담아 뒀다).
- 시·도 이름 6개 국어 표기(`REGIONS` 라벨 사전). 외국인 이용자에게 「충북」 칩은 읽히지 않는다.
