# 에이전트 작업 규칙

**모든 에이전트는 일을 시작하기 전에 이 문서를 읽는다.**

---

## 왜 파일로 주고받는가

Claude Code 서브에이전트는 **메인 대화 기록을 보지 못하고, 서로 대화할 수도 없다**
(Claude Code 공식 문서). 각자 격리된 방에서 일한다.

그래서 **파일이 유일한 공유 기억**이다. 말로 전달된 것은 다음 에이전트에게
닿지 않는다. 파일에 적히지 않은 것은 없었던 일이다.

MetaGPT 연구(ICLR 2024)도 같은 결론에 이르렀다 — 에이전트끼리 자유로운
대화로 주고받으면 환각이 사슬처럼 번지므로, **정해진 양식의 산출물**로
주고받아야 한다.

## 폴더 구조

```
docs/70-agent-workspace/
├── 규칙.md            ← 지금 이 문서
├── 할일목록.md         ← 사장님이 시킬 일 (사람이 씀)
├── tasks/
│   └── T-001-작업이름/
│       ├── 지시서.md      ← 오케스트레이터가 씀. 시작점
│       ├── 개발기록.md    ← developer 가 씀
│       ├── 디자인기록.md  ← designer 가 씀
│       ├── 검토.md        ← reviewer 가 씀 (회차별로 이어 붙임)
│       └── 완료보고.md    ← 오케스트레이터가 씀
└── reports/
    └── YYYY-MM-DD-보고.md ← 사장님께 드리는 정기 보고
```

## 일이 흐르는 순서

```
  사장님
    │  할일목록.md 에 적음
    ▼
  ORCHESTRATOR (메인 대화창)
    │  지시서.md 작성 — 목표·범위·완료조건·하지 말 것
    ▼
  developer / designer  ──→ 개발기록.md / 디자인기록.md
    │
    ▼
  reviewer ──→ 검토.md 에 [1차] 판정과 코멘트
    │
    ├─ 통과 ──────────────────────────┐
    │                                 │
    └─ 수정 필요 → developer 가 검토.md 를 읽고 고침
                    → 검토.md 에 [2차]                │
                    → 2차에도 통과 못 하면            │
                       사람에게 올린다 (아래 정지 규칙) │
                                                      ▼
                                        ORCHESTRATOR → 완료보고.md
                                                      → reports/ 정기 보고
```

## 🔴 정지 규칙 — 가장 중요하다

버클리 연구(MAST, arXiv 2503.13657)가 멀티 에이전트 실패 1,600건을 분석한
결과, 실패의 **15.7%가 "같은 단계를 반복"**, **12.4%가 "끝난 줄 모름"** 이었다.
검토자와 개발자를 그냥 붙여 두면 무한히 돈다.

그래서 다음을 지킨다.

1. **검토는 최대 2회.** 2차 검토에도 통과하지 못하면 고치지 말고 멈춘다.
   `검토.md` 에 "사람 판단 필요"라고 적고 오케스트레이터에게 넘긴다.
2. **지시서에 없는 일은 하지 않는다.** 좋아 보여도 하지 않는다.
   대신 `검토.md` 나 기록 파일 맨 아래 "제안" 항목에 적어만 둔다.
3. **완료 조건은 지시서에 적힌 것뿐이다.** 스스로 늘리지 않는다.

## 각 에이전트가 지킬 것

- **자기 파일에만 쓴다.** 남의 기록 파일을 고치지 않는다.
- **결과를 요약하지 말고 사실을 적는다.** 무엇을 바꿨는지 파일 경로와
  함께. "개선했다"가 아니라 "`src/x.ts` 의 A 를 B 로 바꿨다".
- **확인하지 못한 것은 "확인 못 함"이라고 적는다.** 추측을 사실처럼 쓰지 않는다.
- **`npm run verify` 를 통과시킨다.** 통과 못 했으면 그 사실을 적는다.
- 프로젝트 전체 규칙은 저장소 루트의 `CLAUDE.md` 를 따른다.
  특히 **TourAPI 응답 저장 금지 · 비밀키 클라이언트 노출 금지 ·
  더미 데이터 금지** 세 가지는 어떤 지시보다 우선한다.

## 외부 자료(신문·논문·다른 사이트)를 근거로 쓸 때

WebSearch·WebFetch 로 찾은 기사·자료를 성지 소개글이나 도슨트 원고에 쓸 때
지킬 것 — Anthropic 공식 가이드가 지적하는 실패를 그대로 옮기지 않기 위해서다.

- **문장을 그대로 옮기지 않는다.** 저작권이 있는 건 기자·필자가 쓴 문장이지
  역사적 사실(연도·인물·사건) 자체가 아니다. 사실만 뽑아 새 문장으로 쓴다.
- 표시 없이 원문 구절을 재현하지 않는다. 인용하고 싶으면 따옴표와 출처를
  명시한다.
- 여러 출처가 같은 사실을 다르게 말하면(예: 순교 장소가 다르게 나옴),
  둘 중 하나를 조용히 골라 쓰지 않는다. 기록에 "출처 A는 ~, 출처 B는 ~라고
  한다"고 남기고 판단은 사람에게 넘긴다.

## 파일 양식

### 지시서.md (오케스트레이터가 씀)

```markdown
# T-001 · 작업 이름

- 작성: 2026-09-04
- 담당: developer / designer / 둘 다
- 마감: 2026-09-10

## 목표
한 문장으로. 무엇이 되면 끝인가.

## 왜 하는가
이 일이 없으면 무엇이 곤란한가.

## 완료 조건 (이것만 하면 끝)
- [ ] 조건 1 — 어떻게 확인하는가
- [ ] 조건 2
- [ ] npm run verify 통과

## 범위 밖 (하지 말 것)
- 하지 말아야 할 것을 명시. 없으면 "없음"

## 참고
- 관련 파일 경로
```

### 개발기록.md / 디자인기록.md (작업자가 씀)

```markdown
# 개발 기록 — T-001

## [1차] 2026-09-04

### 한 일
- `경로/파일.ts` : 무엇을 어떻게 바꿨는지

### 확인한 것
- npm run verify : 통과 / 실패(사유)
- 화면 확인 : 무엇을 어떻게 봤는지

### 확인 못 한 것
- 실기기 확인 못 함 등

### 제안 (범위 밖이라 하지 않음)
- 나중에 하면 좋을 것
```

### 검토.md (reviewer 가 씀)

```markdown
# 검토 — T-001

## [1차] 2026-09-04 · 판정: 수정 필요

### 완료 조건 대조
- [x] 조건 1 — 확인함 (근거: 파일·명령·화면)
- [ ] 조건 2 — 미달. 이유:

### 고쳐야 할 것 (우선순위 순)
1. `경로/파일.ts:12` — 무엇이 왜 문제인가 / 어떻게 고치면 되는가

### 좋았던 것
- 그대로 두어야 할 판단

---

## [2차] ... · 판정: 통과 / 사람 판단 필요
```
